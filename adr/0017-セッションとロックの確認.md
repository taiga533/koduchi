# ADR 0017: セッションとロックの確認

- ステータス: 承認
- 日付: 2026-09-08

## 状況

業務で最も多い「調べもの」の 1 つに、**更新が返ってこないときに誰がロックを握っているのかを突き止める**というものがある。小槌にはその導線が無く、利用者はエディタへ `V$SESSION` を叩く SQL を手で書くしかない。書けたとしても、`BLOCKING_SESSION` を辿って連鎖の根を探す作業は目視であり、そのうえ握っているセッションを止める手段が無い。

`V$SESSION` を読むにあたって、既存の決定と衝突しうる点が 3 つある。

1. **結果セットのカーソルは接続 1 本につき高々 1 つである**（[[0003-結果セットのカーソル保持と接続プール]]）。セッション一覧を取るために利用者が見ている結果セットを閉じてしまってはならない。
2. **`V$SESSION` は参照権限を要する**。`SELECT_CATALOG_ROLE` も `SELECT ANY DICTIONARY` も持たない接続では `ORA-00942` になる。権限が無いことと「セッションが 1 つも無い」ことは、区別して見せなければならない。
3. **読み取り専用モードはデータベース側のトランザクションで保証している**（[[0004-認証情報と接続設定の保存先]]）。ところが `ALTER SYSTEM KILL SESSION` はデータを書かないため、読み取り専用トランザクションの網に掛からない。**読み取り専用と表示しながら他人のセッションを落とせてしまう。**

Oracle のドキュメントで確認した事実:

- `V$SESSION.BLOCKING_SESSION` は待たせている側のセッション ID を持ち、`BLOCKING_INSTANCE` はそのインスタンス番号を持つ。`BLOCKING_SESSION_STATUS` が `VALID` のときだけこの 2 つに意味がある。
- `V$SESSION` は `GV$SESSION` を現インスタンスで絞った定義であり、`INST_ID` 列を持たない。
- `SYS_CONTEXT('USERENV','SID')` と `SYS_CONTEXT('USERENV','INSTANCE')` は **V$ ビューの権限なしで**自分自身のセッション ID とインスタンス番号を返す。
- `ALTER SYSTEM KILL SESSION 'sid,serial#'` は `ALTER SYSTEM` 権限を要する。

## 決定

### `V$SESSION` を 1 度の問い合わせで読み、連鎖は Rust 側で組み立てる

`Driver` trait に `list_sessions()` を足す。`type = 'USER'` の行だけを `SID` の順に読み、`SID` / `SERIAL#` / ユーザー / 状態 / 待機イベント / 待機秒 / `SQL_ID` / プログラム / マシン / OS ユーザー / クライアントプロセス / モジュール / ログオン時刻 / `BLOCKING_SESSION` / `BLOCKING_INSTANCE` を返す。バックグラウンドプロセスは調べものの対象にならないため出さない。

**ブロッキングの連鎖は `src-tauri/src/db/sessions.rs` の純粋な関数が組み立てる。** 一覧を受け取り、待たせている側を根とする木を返す。次の 3 つを取りこぼさない形にしてある。

- **循環**（A が B を、B が A を待つ）。1 度訪れた `SID` は再訪しない。デッドロックそのものは Oracle が片方を落として解くが、`V$SESSION` を読んだ瞬間に循環が写ることはある。
- **一覧に居ない待たせ手**。`BLOCKING_SESSION` が指す先がバックグラウンドプロセスであったり、読んでいる間に消えていたりする。この場合は待っている側を根として立てる。
- **別インスタンスの待たせ手**。`BLOCKING_INSTANCE` が現インスタンスと違うときは連鎖を繋がない（後述）。

木にするのは Rust 側であり、フロントエンドは受け取った木を描くだけである。連鎖の組み立ては境界条件の塊であり、テストを書きやすい側に置く。

### 取得はプールの「結果セットを保持していない接続」で行う

スキーマ取得と実行計画がそうしているのと同じく、`ConnectionPool::background_handle()` が選んだ接続で読む（[[0003-結果セットのカーソル保持と接続プール]]）。この経路は `Connection::query` を直接使い、`OracleDriver` が持つカーソル（`OracleDriver::cursor`）には一切触れない。**利用者が見ている結果セットは、セッション一覧を何度取り直しても壊れない。**

### 権限が無いことを `DbErrorKind::Permission` として区別する

`ORA-00942`（表またはビューが存在しない）と `ORA-01031`（権限が不足）を `DbErrorKind::Permission` へ写し、パネルは「この接続では `V$SESSION` を参照できません」と、必要な権限（`SELECT_CATALOG_ROLE` など）を添えて出す。データベースが返した原文も併せて残す。

**権限が無いときに空の一覧を出さない。** 「誰もロックを握っていない」と「見えていない」を同じ画面で表すのは、[[0004-認証情報と接続設定の保存先]] が退けた「表示が嘘になる」のと同じ害である。

### kill は実装する。関所は 3 つ

`ALTER SYSTEM KILL SESSION 'sid,serial#' IMMEDIATE` を発行する `kill_session()` を `Driver` trait に足す。破壊的な操作であるため、次の 3 つをすべて通さないと届かない。

1. **読み取り専用の接続では発行しない。** `OracleDriver` が `read_only` を見てその場で弾く。**この 1 つだけは、クライアント側の判定に頼らざるを得ない。** `ALTER SYSTEM` はデータを書かないため、[[0004-認証情報と接続設定の保存先]] の読み取り専用トランザクションでは止まらないからである。判定の材料が「接続設定の読み取り専用フラグ」という 1 つの真偽値であり、SQL の中身を解釈しないため、`WITH ... INSERT` のようなすり抜けは起こらない。
2. **小槌自身が張っている接続は弾く。** 発行の直前に一覧を読み直し、対象がその中の「小槌の接続」であれば発行しない。**自分自身だけでは足りない。** ウィンドウは接続を 4 本持ち（[[0003-結果セットのカーソル保持と接続プール]]）、別のウィンドウ（[[0009-ウィンドウモデルとタイトルバー]]）はさらに別の接続を持つ。兄弟の 1 本を落とせば、そのタブで次に実行したときに `ORA-00028` で失敗する。見分けるのは `V$SESSION.PROCESS` と `MACHINE` であり、同じアプリのプロセスから張られた接続はこの 2 つが揃う。自分自身は `SYS_CONTEXT('USERENV','SID')` で必ず分かるため、`PROCESS` が読めない場合でも最低限そこは守れる。
3. **確認ダイアログを挟む。** 対象の `SID` / `SERIAL#` / ユーザー / プログラムを読み上げたうえで尋ねる。押し間違いで他人の仕事を落とさないためである。

1 と 2 は `check_kill_allowed` という純粋な関数に切り出し、Rust 側のテストで直接確かめる。**UI で隠すだけにはしない。** 判定のために `V$SESSION` を 1 回余分に読むが、kill は稀で取り返しのつかない操作であり、往復 1 回とは釣り合う。UI が持っている一覧は古くなりうるうえ、`SID` は使い回される。

### 出す場所はステータスバーの接続メニューから開くオーバーレイ

「接続中」のメニュー（[[0009-ウィンドウモデルとタイトルバー]] の「接続の切断と切り替え」）に「セッションとロック…」を足し、設定画面と同じ作りのオーバーレイを開く。キーバインドは割り当てない。

### 自動更新は既定でオフ、オンにすると 5 秒ごと。パネルを閉じたら止まる

パネルの中のチェックで切り替える。パネルを閉じると部品ごと消えるため、`useEffect` の後片付けで間隔も消える。

### `V$LOCK` は見ない

ロックの種類（`TM` / `TX`）とモード（3 / 6）までは出さない。

### 現インスタンスだけを見る（`GV$SESSION` は使わない）

RAC の他インスタンスのセッションは並べない。`BLOCKING_INSTANCE` が現インスタンスと違うときは、その旨を行に添えるだけで連鎖は繋がない。

## 理由

- **カーソルを壊さない経路が既にある。** スキーマ取得（[[0007-スキーマ取得の段階的ロード]]）と実行計画が通っている `background_handle` に相乗りすれば、新しい接続を張らずに済む。「セッションを見るために接続が 1 本増える」のは、調べたい相手がセッション数の逼迫であるときに特に筋が悪い。
- **連鎖の組み立てを Rust に置く**のは、循環・欠けた待たせ手・別インスタンスという 3 つの境界がすべてデータの形の問題であり、描画とは無関係だからである。純粋な関数にすればデータベース抜きで全パターンを試せる（[[0010-テストとリンタの構成]]）。
- **kill を入れる**のは、「誰が握っているか」を突き止めたあとに何もできないなら、調べる意味が半分しか無いためである。業務では相手の担当者へ連絡する時間が無いこともある。ただし押し間違いの被害が他人に及ぶ唯一の機能であるため、関所を 3 つ重ねる。
- **`V$LOCK` を見ない**のは、`BLOCKING_SESSION` だけで「誰が誰を待たせているか」は確定するためである。ロックのモードまで出しても、読み手が取る行動（待つ・連絡する・落とす）は変わらない。一方で `V$LOCK` は `DBA_OBJECTS` との結合を要し、追加の権限と行数を持ち込む。
- **`GV$SESSION` を使わない**のは、`ALTER SYSTEM KILL SESSION` がそもそもインスタンス 1 つを相手にする命令であり、一覧と操作の見える範囲を揃えるほうが嘘が無いためである。`GV$` は `SELECT_CATALOG_ROLE` を持たない環境で `V$` より通りにくいという実際上の理由もある。
- **自動更新を既定でオフにする**のは、パネルを開いたまま放置されると 5 秒ごとに `V$SESSION` を読み続けるためである。調べものは「今どうなっているか」を数回見れば済むことが多い。

## 却下した案

**結果ペインの新しいタブとして出す**: 結果ペインのタブはエディタタブごとの実行結果に紐付いている（[[0009-ウィンドウモデルとタイトルバー]]）。セッション一覧はどのエディタタブにも属さないため、タブを切り替えるたびに消えたり現れたりする。器の意味が壊れる。

**サイドバーの新しいセグメントとして出す**: サイドバーは 180〜480px であり、`SID` / ユーザー / 待機イベント / プログラムを並べる幅が無い。スキーマツリーのような縦に長い一覧のための場所である。

**別ウィンドウで出す**: 1 接続 = 1 ウィンドウ（[[0009-ウィンドウモデルとタイトルバー]]）という取り決めがあり、接続を持たないウィンドウを増やすとラベルの規約（`connection-` 前置き）と capability の受けも変わる。調べものの間だけ見る画面に、ウィンドウモデルを曲げるほどの値打ちは無い。

**専用の接続をもう 1 本張る**: プールと無関係にセッション監視用の接続を持てば、カーソルの心配は完全に消える。だがセッション数が逼迫している相手に、調べるためだけの接続を足すのは本末転倒である。

**`Driver` trait に足さず Oracle 専用のコマンドにする**: `DBMS_OUTPUT` や tnsnames.ora と同じ扱いにする案。しかし「今どのセッションが何を待っているか」は PostgreSQL にも `pg_stat_activity` / `pg_blocking_pids()` という対応物があり、データベース非依存の概念である。[[0002-接続ごとのアクタースレッドと中止]] の「実装済みの操作だけを載せる」に従い、実装と同時に trait へ足す。

**kill を入れない（一覧の表示だけにする）**: 破壊的な操作を持ち込まずに済む。しかし調べたあとに手が無く、結局 SQL\*Plus を開くことになる。関所を 3 つ重ねれば、押し間違いの余地は確認ダイアログの 1 回に絞れる。

**kill の代わりに `ALTER SYSTEM DISCONNECT SESSION ... POST_TRANSACTION` を使う**: トランザクションの切れ目まで待つため穏やかだが、「返ってこない更新を止めたい」という当の目的には効かない。待っている当人が終わらないから調べているのである。

**kill の可否を UI のボタンの出し分けだけで担保する**: フロントエンドを直せば通ってしまう。読み取り専用の保証は Rust 側に置く（[[0004-認証情報と接続設定の保存先]] と同じ考え方）。

**未コミットの判定と同じく、実行のたびにセッションを読む**: 実行と一覧の鮮度が揃うが、毎回の実行に往復が 1 つ増える。セッションを見たいのは詰まったときだけである。

## 結果

- `Driver` trait のメソッドが 2 つ増えた（`list_sessions` / `kill_session`）。PostgreSQL を足すときは `pg_stat_activity` と `pg_terminate_backend()` で同じ形を満たすことになる。
- `DbErrorKind` に `Permission` が加わった。他の機能でも「権限が無くて見えない」を「空」と混同させたくない場面が出たら、この区分を使う。
- 読み取り専用の接続では、パネルの kill ボタンそのものを出さない。**弾かれるボタンを見せない**ためであり、Rust 側の関所はその裏で二重に効く。
- 自分自身のセッションは一覧の中で「この接続」、同じアプリの他の接続は「小槌」と印を付けて示し、どちらにも kill ボタンを出さない。どれが自分かが分からないと、一覧そのものが読めない。
- `V$SESSION` を読める接続でないとパネルは空のまま終わる。開発用データベースの `koduchi` ユーザーには `SELECT_CATALOG_ROLE` が既に付いている（`dev/oracle/initdb/001_schemas.sql`）。
- 統合テストではセッションを実際に落とさない。落とせば他のテストの接続を巻き添えにする。一覧が自分自身を含むこと、プールの 4 本すべてに印が付くこと、開いたままのカーソルが一覧の取得で壊れないこと、自分自身の kill が弾かれること、読み取り専用の接続で kill が弾かれることまでを確かめる。開発用データベースの `koduchi` ユーザーは `ALTER SYSTEM` 権限を持たないため、kill が実際に通る経路は自動テストでは踏まない。
