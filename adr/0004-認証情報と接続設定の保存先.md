# ADR 0004: 認証情報と接続設定の保存先

- ステータス: 承認
- 日付: 2026-08-30

## 状況

データベースクライアントは接続先の情報とパスワードを保持する必要がある。パスワードを平文でファイルに置くのは、ローカルアプリとはいえ避けたい。

デザインの接続作成フォーム（状態 5g）には「キーチェーンに保存」の表記があり、パスワード欄と分離された設計になっている。

またステータスバーには「読み取り専用」の表示があり、接続を読み取り専用にする機能が想定されている。

## 決定

**パスワードのみ OS キーチェーンに保存し、接続設定は TOML に保存する。**

- パスワード: `keyring` crate 経由で macOS Keychain へ。サービス名は `ninja.taiga533.koduchi`、アカウント名は接続の一意 ID。
- 接続設定: `~/Library/Application Support/ninja.taiga533.koduchi/connections.toml`。パスワードは**書かない**。
- TOML に持つ項目: 一意 ID、表示名、接続方式（EZConnect / TNS）、ホスト、ポート、サービス名、ユーザー、読み取り専用フラグ、スキーマフィルタ設定（[[0007-スキーマ取得の段階的ロード]]）。

読み取り専用モードは、**データベース側に保証させる**。接続確立直後にセッションで読み取り専用トランザクションを開始する（Oracle は `SET TRANSACTION READ ONLY`、PostgreSQL は `default_transaction_read_only`）。

## 理由

- パスワードだけをキーチェーンに逃がせば、TOML は利用者が外部エディタで安全に編集できるプレーンな設定ファイルになる。
- 読み取り専用をクライアント側の先頭キーワード判定で実装すると、`WITH ... INSERT` や無名 PL/SQL ブロックをすり抜ける。「読み取り専用」と表示しながら書き込めてしまうのは最悪の挙動であり、データベース側の保証が必要である。

## 却下した案

**すべてを暗号化せずローカルファイルに保存する**: 実装は最速だが平文パスワードが残る。

**パスワードを保存せず毎回入力させる**: 日常的に使うクライアントとして手数が多すぎる。

**読み取り専用を SQL の先頭キーワード判定で実装する**: 前述のとおりすり抜ける。

**読み取り専用を表示だけにする（機能なし）**: 表示が嘘になる。

## 結果

- 起動時に保存済み接続へ**自動再接続はしない**（[[0005-クエリ履歴とセッション復元のsqlite]]）。キーチェーン取得で OS のダイアログが出る可能性があるため、明示的な接続操作に紐付ける。
- 接続の一意 ID は削除・再作成でキーチェーンの孤児エントリを生まないよう、接続削除時にキーチェーンからも消す。
- デザイン状態 5g の「設定ファイルから読み込む」リンクは実装しない（スコープ判断）。
