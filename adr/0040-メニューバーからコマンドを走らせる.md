# ADR 0040: メニューバーからコマンドを走らせる

- ステータス: 承認
- 日付: 2026-09-27

## 状況

「SQL を整形」（`⇧⌥F`）と「ファイルを開く」（`⌘O`）は、キーとコマンドパレットからしか走らせられない。利用者は macOS のメニューバーからも走らせたいと言っている。

前提は次の 4 つである。

- メニューバーは Tauri の既定のメニューへ項目を差し込む形で組んでいる（ADR 0036）。「設定…」は専用のイベント `koduchi://open-settings` で焦点のあるウィンドウへ届く。
- キーとパレットはコマンドの表（`src/mediator/commands.ts`）の同じ行の `run` を通る（ADR 0035）。
- キーは割り当て直せる（ADR 0037）。ADR 0037 は「**ネイティブのメニューには表のキーをアクセラレータとして付けない**。付けると、割り当て直した後もメニューが古いキーを握り続ける」と申し送っている。メニューのアクセラレータはウェブビューより先に打鍵を取る。
- メニューはアプリに 1 つで、全ウィンドウが共有する。ストアと「今どのタブを選んでいるか」はウィンドウごとにある（ADR 0009）。

## 決定

### 置き場所

- **「ファイルを開く…」は既定の File メニューの先頭**に置き、区切り線を挟んで既存の「Close Window」を下に残す。macOS の File メニューの並び（開く・…・閉じる）に合わせる。
- **「SQL を整形」は既定の Edit メニューの末尾**に区切り線を挟んで足す。整形は本文を書き換える編集の操作であり、取り消しやペーストと並ぶ。新しいメニューは作らない（項目 1 つのためにメニューバーの幅を使わない）。

差し込み先は**名前（`File` / `Edit`）で探す**。位置で決め打ちすると、既定のメニューの並びが Tauri の版上げで変わったときに別のメニューへ入る。見つからなければ**起動を止める**（項目が黙って消えると、気づくのは使ったときである）。

### キーの表記は出さない（アクセラレータを付けない）

2 つの項目にはアクセラレータを付けない。キーの持ち主はこれまでどおりコマンドの表（`⌘O` はウィンドウの `keydown`、`⇧⌥F` は CodeMirror の keymap）である。1 打鍵がメニューとウェブビューの両方に拾われる二重発火は、そもそも起こらない。

キーはコマンドパレットと設定画面のキー割り当ての欄で読める。

### 届け方を一般化する

メニューからのイベントを `koduchi://menu-command` 1 つにし、中身は**コマンドの表の識別子**（`settings` / `open-file` / `format`）にする。フロントエンドは `src/appMenu.ts` の `onMenuCommand` で受け、`App.tsx` が `runCommand(commandById(id), commandScreen)` へ繋ぐ。キー・パレット・メニューの 3 つの入口が同じ行の `run` と `available` を通る。

「設定…」もこの形へ移す。ADR 0036 の `koduchi://open-settings` と `onOpenSettingsRequested` は消す。届け先の選び方（焦点のあるウィンドウ、無ければ `main`、それも無ければラベル順の先頭）と、`⌘,` のアクセラレータをメニューが持つことは変えない。選ぶ関数の名前は `settings_target` から `command_target` に改めた。

メニュー項目の ID とコマンドの識別子の対応は `src-tauri/src/menu.rs` の `MENU_COMMANDS` にある。識別子は言語をまたいで綴りを揃えるしかないため、`src/appMenu.test.ts` が `menu.rs` を読み、どれもコマンドの表に在ることを見張る。

### 押せない状態は、キーと同じく「押しても何も起きない」

項目は常に押せるままにする。今使えるかはキーと同じ判定に任せる。

- 定義タブを選んでいる・未接続でエディタが無いときの「SQL を整形」は、`formatEditor` の口が繋がっていないため何も起きない（ADR 0022・0024。判定は書き足さない）。
- 「ファイルを開く…」はキーの `⌘O` と同じに振る舞う。

## 理由

- **アクセラレータを付けないのは、ADR 0037 の申し送りを守りつつ二重発火を構造で断つためである。**割り当ての変更をメニューへ反映する道（フロントエンドが解決したキーを Rust へ送り、`set_accelerator` で付け替える）は取らなかった。メニューは全ウィンドウで 1 つだが割り当てはウィンドウごとに読み込まれ、設定を変えたウィンドウと他のウィンドウで食い違う間がある。加えて、メニューが先に打鍵を取ると `⇧⌥F` の持ち主が CodeMirror からメニューへ移り、「エディタの中でしか意味を持たないキーは keymap に置く」（ADR README）が崩れる。
- **届け方を一般化するのは、入口ごとに裁定を分けないためである。**専用のイベントを項目ごとに足すと、受け手でも項目ごとに口と裁定の呼び出しを書くことになる。表の識別子を送れば、受け手は表を引くだけで済む。
- **無効にしないのは、メニューが全ウィンドウで 1 つだからである。**無効にするには、焦点・選んでいるタブ・接続が変わるたびに焦点のあるウィンドウから Rust へ状態を送り直す必要がある。焦点が動いた瞬間に古いウィンドウの状態が残る間ができ、押せるのに何も起きない・押せないのに走る、のどちらも起こりうる。キーも同じ状態では何も起きないため、入口の間で振る舞いが揃う。

## 却下した案

**アクセラレータを付け、ウィンドウの `keydown` からその行を外す**: 割り当て直しがメニューへ届かない（ADR 0037 の申し送りそのもの）。

**割り当ての変更をメニューへ反映する**: 上の「理由」を参照。

**項目の名前にキーの表記を文字として混ぜる（`SQL を整形  ⌥⇧F`）**: macOS のメニューは名前とキーの欄を別に揃えて描くため、文字で混ぜると桁が揃わず、割り当て直すと食い違う。

**新しいメニュー（「SQL」など）を作る**: 項目が 1 つしか無い。実行や整形などを集めたメニューを作るなら、そのときに改めて決める。

**「設定…」は専用のイベントのまま残す**: 同じことをする届け方を 2 つ持たない。

## 結果

- メニューに足す項目はこれから `MENU_COMMANDS` に 1 行と `build` での差し込みを足せば、フロントエンドには手が要らない。
- メニューからはキーが読めない。読みたい利用者はパレットか設定画面を見る。
- 定義タブで「SQL を整形」を押しても何も起きず、理由も出ない。キーの `⇧⌥F` と同じである。
- capability は増えない。
