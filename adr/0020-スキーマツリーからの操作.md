# ADR 0020: スキーマツリーからの操作

- ステータス: 承認
- 日付: 2026-09-08

## 状況

スキーマツリー（[[0007-スキーマ取得の段階的ロード]]・[[0014-スキーマツリーのオブジェクト種別拡張]]）でできることは、展開と折りたたみしかない。`SchemaTree.tsx` に `onDoubleClick` も `onContextMenu` も無く、行はどれも開閉のためだけの `button` である。

見つけた表の名前を SQL に書くには、名前を目で読んでエディタへ打ち直すことになる。補完（[[0013-補完の候補生成と識別子の出力スタイル]]）は打ち始めてからでないと効かないため、`ORDER_ITEM_ARCHIVE_2024` のような名前は結局のところ手で写す。ツリーは「探す場所」ではあるが「そこから作業を始める場所」にはなっていない。

決めるべきことは 5 つある。

1. 名前をエディタへ入れる導線と、入れる名前の綴り
2. 表・ビュー・マテビューをダブルクリックしたときに何が起きるか
3. 列を持たない 9 種別をダブルクリックしたときに何が起きるか
4. 右クリックのメニューに何を並べるか
5. 同じことをキーボードでできるか。仮想スクロールの中で焦点をどう扱うか

ツリーの行の上では、単クリック（開閉）とダブルクリック（挿入）が同居する。結果テーブルが「セルの単クリックで選択、ダブルクリックで詳細」を同じ場所へ載せたのと同じ形であり、そこでの割り振り方に倣える。

## 決定

### ダブルクリックは「名前をカーソル位置へ挿入」に割り当てる

種別を問わず、ダブルクリックした行の名前を**今のタブのカーソル位置へ挿入する**。`SELECT * FROM …` は作らない。開いているタブも増やさない。

- スキーマ行 → `koduchi`
- オブジェクト行 → `koduchi.users`（スキーマで修飾する）
- 列行 → `user_id`（**修飾しない**）
- 種別の束・「列情報を読み込み中」の行 → 何も起きない（名前を持たないため）

列を修飾しないのは、列名の主な使い道が `SELECT` の並びと `WHERE` の条件であり、そこでは表の別名で修飾するか修飾しないかのどちらかになるためである。`koduchi.users.user_id` と書ける場面は限られており、要るときは表を先に挿入してから `.` を打てば補完が続きを出す。

逆にオブジェクトを修飾するのは、ツリーが**どのスキーマの下で見つけたか**を知っている唯一の場所だからである。修飾せずに入れた名前は、既定スキーマの違う接続で貼り直したときに黙って別の表を指す。

### 列を持たない種別も同じ扱いにする

索引・トリガー・シノニム・型・DB link・関数・プロシージャ・パッケージ・シーケンスも、ダブルクリックで名前が入る。**種別ごとに違う雛形（`DROP INDEX …` や `EXEC …`）は出さない。**

理由は 2 つある。1 つは、12 種別ぶんの雛形が正しいかどうかを利用者が確かめられないことである。`DROP` を勝手に置くのは、確かめる手立ての無い操作としては重すぎる。もう 1 つは、覚えることを増やさないためである。「ダブルクリック = 名前が入る」は行の種類を問わず 1 つの規則であり、例外がなければ説明も要らない。

[[0014-スキーマツリーのオブジェクト種別拡張]] は「索引とトリガーの名前は SQL 本文に現れない」として補完のカタログから外したが、ここでは外さない。補完は**打っている途中に勧める**ものであり、外れた候補は邪魔になる。ツリーからの挿入は利用者が名指しで選んだものであり、勧めているわけではない。`DROP INDEX` を書くときに索引名を写せることには値打ちがある。

### 挿入する綴りは `identifiers.ts` に委ねる

**綴りと引用符の決まりは書き直さない。**[[0013-補完の候補生成と識別子の出力スタイル]] の `styleIdentifier` をそのまま呼ぶ。引用符なしで書ける名前は接続ごとの設定（小文字 / 大文字 / カタログのまま）へ変え、書けない名前はカタログの綴りのまま引用符で囲む。修飾した名前は要素ごとに判定するため、`koduchi."MyTable"` の形になる。

ツリーからの挿入と補完の挿入が食い違うと、同じ表が 2 通りの綴りで 1 つの SQL に並ぶ。ここは合わせる以外にない。

### 挿入する前に、要るときだけ空白を 1 つ足す

`from` の直後へ入れた名前が `fromkoduchi` になっては使えない。逆にいつでも足すと、行頭や `(` の直後に余分な空白が残る。**カーソルの直前 1 文字だけで決める。**

| 直前の文字               | 空白 |
| ------------------------ | ---- |
| 無い（文書の先頭）       | 足さない |
| 空白・改行               | 足さない |
| `(` `.` `:`              | 足さない |
| それ以外                 | 足す |

`(` は `count(` の直後、`.` は `koduchi.` と修飾を打ちかけた位置、`:` はバインド変数の前置きである。文の構造を読まずに済み、外した場合の害も「空白が 1 つ多い / 少ない」に留まる。

判定は `src/components/editor/insertion.ts` の純粋な関数である。組み立て（どの名前をどの綴りで）と差し込み（どこへ、空白は要るか）を分け、どちらもテストできる形にした。

### 挿入は CodeMirror へ差分として渡す

タブストアの内容を組み直して差し替える手も取れるが、それでは文書を丸ごと置き換えることになる。CodeMirror は置き換えられた範囲の中の位置を変更の末尾へ写すため、**カーソルが文書の末尾へ飛ぶ**。取り消し履歴も 1 段に潰れる。

そこで `SqlEditor` に `insertAtCursor` だけを持つ命令的な口（`SqlEditorHandle`）を開け、`App.tsx` が `ref` で握って `Sidebar` 越しにツリーへ渡す。挿入は `dispatch({ changes, selection })` の 1 回であり、選択があればその範囲を置き換える。

**焦点はエディタへ移さない。**続けて別の列を入れる操作が多く、そのたびに焦点が飛ぶとツリーへ戻る手間が挿入の手間を上回る。焦点が移らないぶんカーソルは挿入した文字列の後ろに残るので、続けて挿入すれば `koduchi.users koduchi.orders` と並ぶ。

### 右クリックのメニューは 3 項目

`ResultContextMenu.tsx` に倣い、「名前をコピー」「エディタへ挿入」「`SELECT` を開く」を出す。見出しに対象の名前を出す（ツリーは 1 行が細く、押した行を取り違えたまま操作しやすい）。

- **名前を持たない行（種別の束・読み込み中）ではメニューを出さない。** 3 項目すべてが無効なメニューを出しても意味がない。
- **「`SELECT` を開く」は列を持つ 3 種別のときだけ出す。** 索引や手続に `select * from` を当てても動く SQL にはならない。
- クリップボードは `src/api/clipboard.ts` 越しに呼ぶ（[[0010-テストとリンタの構成]]）。**コピーする綴りは挿入する綴りと同じにする。**別の窓へ貼るためのものであっても、同じ場所から出た名前が 2 通りに見えるのは分かりにくい。

### 「`SELECT` を開く」は新しいタブに入れるだけで、実行しない

`select * from koduchi.users` を新しいタブへ入れ、そこで止める。実行は利用者が `⌘⏎` で決める。

- **結果セットのカーソルは接続 1 本につき高々 1 つである**（[[0003-結果セットのカーソル保持と接続プール]]）。ここで実行すると、別のタブが見ている結果が閉じられて「結果は破棄されました」になる。メニューの 1 項目が払う代償としては重い。
- 行数の多い表そのものは危なくない。分割取得により最初の 1,000 行しか来ないためである。危ないのは重いビューであり、`ORDER BY` を含むビューは 1,000 行を返すまでに全件を走査する。押した瞬間に戻ってこないメニュー項目は作らない。
- 読み取り専用でない接続でも `SELECT` はデータを書かないが、書かないことと「実行してよい」ことは別である。

キーワードは小文字で書く。エディタのキーワード補完が小文字固定（`upperCaseKeywords: false`）であり、識別子の綴りとは別の話だからである（[[0013-補完の候補生成と識別子の出力スタイル]]）。綴りを大文字にした接続では `select * from KODUCHI.USERS` になる。文末の `;` は付けない。1 文だけを入れた新しいタブであり、`⌘⏎` は区切りが無くても文を切り出せる。

### キーボードでも同じことができる

ツリーの中でだけ意味を持つため、`App.tsx` ではなくツリー自身の `keydown` に置く（`CLAUDE.md` の「キーバインドの置き場所」）。

| キー          | 動作                                       |
| ------------- | ------------------------------------------ |
| `↑` / `↓`     | 隣の行へ焦点を移す                         |
| `→` / `←`     | 開く / 閉じる                              |
| `⏎` / `Space` | 開閉（`button` の既定の押し下げ）          |
| `⌥⏎`          | 名前を挿入（ダブルクリックと同じ）         |
| `⌘C`          | 名前をコピー                               |

`⏎` 単独は開閉に取られているため、挿入には修飾を 1 つ足した。`⌘C` は `App.tsx` の窓全体のキーバインドと衝突しない（`⌘C` は `⌥` 付きのコミットだけを見ている）。結果テーブルの `⌘C` とも、焦点のある場所が違うため食い合わない。

**焦点は 1 行しか持たせない（roving tabindex）。**仮想スクロールで描かれている行がすべてタブ順に並ぶと、ツリーを抜けるのに数十回打鍵することになる。焦点のある行だけ `tabIndex=0` とし、残りは `-1` にする。

**焦点を移すときは、行が描かれるまで待つ。**仮想スクロールでは、`scrollToIndex` を呼んだ時点ではまだ対象の行が DOM に無い。位置だけを状態として持ち、描画のたびに「焦点を当てるべき行」を探して見つかったら当てる、という形にした。見つからなければ次の描画で試し直す。

`⇧F10` によるメニューの呼び出しと、`Home` / `End` による端への跳躍は入れない。前者は macOS で使われる作法ではなく、後者は跳んだ先が描かれるまで焦点が宙に浮く時間が長い。

### マウス操作の割り振り

| 操作                 | 起きること                                        |
| -------------------- | ------------------------------------------------- |
| 行を単クリック       | 開閉する（開けない行では何も起きない）            |
| 行をダブルクリック   | 名前をエディタのカーソル位置へ挿入する            |
| 行を右クリック       | 名前のコピー・挿入・`SELECT` を開くのメニュー     |
| 「定義」を単クリック | テーブル定義ビュー（ADR 0019。別の波で作る）      |

**ダブルクリックは 1 回目と 2 回目の押し下げでそれぞれ `click` が起き、開閉が 2 度切り替わる。**結果として開き具合は元へ戻る。`event.detail` を見て 2 回目を捨てるような細工はしない。細工を入れると「1 回だけ開いた」半端な状態が残り、そちらのほうが説明しにくい。結果テーブルの「ダブルクリックは 1 回目の押し下げで選択も起こる」と同じ扱いである。

この表は**スキーマツリーのマウス操作の持ち主**である。テーブル定義ビュー（ADR 0019）が「定義」の行を埋めるときは、この表に 1 行を足す形になる。

## 理由

- **ダブルクリックに `SELECT` を割り当てなかった**のは、単クリックが開閉に取られている行の上でダブルクリックが誤爆しやすいからである。誤爆の代償が「名前が 1 つ余分に入る」であれば `⌘Z` で消せるが、「別のタブの結果が消える」では取り返しがつかない。重い操作は、押したことがはっきり分かる右クリックのメニューへ置いた。
- **挿入を 1 つの規則にまとめた**のは、ツリーの行が 5 種類（スキーマ / 種別の束 / オブジェクト / 列 / 読み込み中）あり、そのうえオブジェクトが 12 種別に分かれているためである。組み合わせごとに違う動きを与えると、覚えられないものが増えるだけになる。
- **綴りの決まりを共有した**のは、[[0013-補完の候補生成と識別子の出力スタイル]] が引用と綴りに払った注意を、入口が増えるたびに払い直したくないためである。`identifiers.ts` は「カタログの名前 1 つを、どう書くか」に答える唯一の場所であり続ける。

## 却下した案

**ダブルクリックで `SELECT * FROM …` を新しいタブに開き、そのまま実行する**: DBeaver などに近く 1 手減るが、結果セットのカーソルが 1 本しかない（[[0003-結果セットのカーソル保持と接続プール]]）以上、別のタブが見ている結果を巻き添えにする。重いビューでは押した瞬間に待たされる。

**ダブルクリックで `SELECT * FROM …` を入れるが実行はしない**: 実行の危うさは消えるが、「名前だけが欲しい」ときに文ごと消す手間が残る。名前を入れるほうが素材として細かく、`SELECT` が欲しければ右クリックから開ける。細かいほうを既定にした。

**単クリックで挿入し、開閉は三角の印を押したときだけにする**: 挿入が最短になるが、ツリーを辿るいちばん多い操作（開閉）が 13px の的に縮む。ツリーは今も「探す場所」であることをやめない。

**列も `スキーマ.表.列` で修飾して挿入する**: 誤りにはならないが、実際に書く形とかけ離れている。`SELECT` の並びに 3 段の修飾が並ぶ SQL は読めない。

**種別ごとに違う雛形を出す**（索引なら `DROP INDEX …`、手続なら `EXEC …`、シーケンスなら `SELECT ….NEXTVAL FROM DUAL`）: 便利に見えるが、`DROP` を確かめる手立ての無いまま置くのは重い。12 種別ぶんの雛形が正しいかどうかを利用者は確かめられない。

**挿入をタブストアの内容の差し替えで済ませる**: 新しい API を足さずに済むが、文書を丸ごと置き換えるためカーソルが末尾へ飛び、取り消し履歴が潰れる。`ref` を 1 本通すほうが安い。

**挿入したらエディタへ焦点を移す**: 続けて打ちたいときには自然だが、続けて別の名前を入れたいときにツリーへ戻る手間がかかる。ツリーから入れるのは 1 つとは限らない。

**焦点を移さずに `⌘Z` で消せることを頼りに、ダブルクリックでも `SELECT` を実行する**: 実行は `⌘Z` で取り消せない。

**ツリーに `role="tree"` / `role="treeitem"` を与える**: 支援技術への伝わりは良くなるが、行が `button` でなくなると `⏎` と `Space` の押し下げを自前で組み直すことになり、開閉の動きを 2 通り持つことになる。roving tabindex だけを採り、役割は `button` のままにした。

**種別の束にも「すべての名前をコピー」を出す**: 数千件の名前がクリップボードへ入りうる。束が持つのは数だけでよい。

## 結果

- `src/components/editor/insertion.ts` が増えた。名前の組み立て（`qualifiedIdentifier`）・前置きの空白（`withLeadingSpace`）・`SELECT` の組み立て（`selectAllStatement`）の 3 つの純粋な関数である。
- `SqlEditor` が `ref` を受けるようになった。外から呼べるのは `insertAtCursor` の 1 つだけである。`EditorPanel` はそれをそのまま通す。タブを切り替えると `key` でエディタが作り直されるため、口も張り替わる。
- `TreeRow` にスキーマ名と所属オブジェクト名が載った。鍵の文字列（`KODUCHI.USERS`）を `.` で割って取り出す手もあるが、名前に `.` を含む識別子で壊れる。
- `SchemaTree` が接続ストアを読むようになった。挿入する綴りが接続ごとの設定だからである（[[0013-補完の候補生成と識別子の出力スタイル]]）。読むのは `identifierCase` の 1 つだけであり、接続中に変わらない。
- **Rust 側は触っていない。**ツリーからの操作はすべて取得済みの状態の上で完結する。
- テーブル定義ビュー（ADR 0019）は「定義」の入口を別に足す。本 ADR のマウス操作の割り振り表へ 1 行を足す形になり、ダブルクリックと右クリックの割り当ては動かさない。
