# ADR 0003: 結果セットのカーソル保持と接続プール

- ステータス: 承認
- 日付: 2026-08-30

## 状況

結果テーブルは全行を取得できることが要件である。一方、数十万行を一括で IPC に載せると数百 MB の JSON がメインスレッドを固める。

取得方式として「UI のスクロールが下端に近づくたびに 1,000 行ずつ追加取得する」ことを選んだ。これはデータベースの結果セットカーソルを開いたまま保持することを意味し、カーソルが開いている間その接続は占有される。

ウィンドウ内には複数のエディタタブがあり、それぞれが結果を保持しうる。

## 決定

**ウィンドウごとに接続プール（既定 4 本）を持つ**。結果を保持しているタブが 1 本を占有し、5 つ目のタブで実行すると最も古い結果セットを閉じて、そのタブには「結果は破棄されました。再実行してください」を表示する。

行数の表示は 2 段階にする。

1. 取得中: `1,000 行 読み込み済み`
2. カーソルが尽きた時点: `142 行 · 84 ms`（デザインどおりの確定表示）

CSV 保存（`⌥⌘S`）は、**保存時に残りのカーソルを最後まで読み切ってから**書き出す。進捗（`124,000 行 書き出し中`）を表示し、中止できるようにする。

### 閉じたタブへ遅れて届くもの（2026-09-27 追記）

**タブを閉じる前に送った実行と続きの取り出しは、手放し（`release_tab`）より後に届きうる。**Tauri のコマンドは `run_blocking` で別々のスレッドに載るため、到着順は約束されない。フロントエンドでも Rust 側でも、遅れて届いたものに閉じたタブを蘇らせない。

- **フロントエンドの `execution` ストアは、タブの世代で遅れた応答を捨てる**（2026-09-27 追記）。`execute` / `executeScript` は始めるたびにタブの世代を採番し、待ちの後は控えた世代が今も同じときだけ書き戻す。`fetchMore` は同じ結果セットの続きなので、世代を改めずに控える。`releaseTab` と `clear` は世代ごと捨てる。項目の有無だけを見ないのは、手放した後に同じタブで実行し直した場合（切断して繋ぎ直した後など）に、古い応答が新しい実行へ混ざるためである。実行計画は始めたときの項目そのものを印にし、手放された後や取り直された後の応答を捨てる。
- **`patchTab` は項目を作り直さない**（2026-09-27 追記）。項目が無ければ何もしない。項目を作るのは実行を始めたときだけである。作り直すと、閉じたタブの項目が遅れた応答で蘇る。`running` のまま蘇れば、切断が「実行中の文があります」で止まり続ける。
- **閉じたタブではスクリプトの残りの文を投げない**（2026-09-27 追記）。応答を捨てるだけでは、閉じたタブの文がデータベースで走り続ける。
- **`clear` をまたいで返った実行の応答は、未コミットの表示とログへ書かない**（2026-09-27 追記）。未コミットの表示とログはウィンドウに 1 つであり、タブの世代では守れない。閉じた実行中のタブは項目が先に消えるため、実行中の文があっても切断の関所（`selectAnyRunning`）を通れる。その応答が切断の後に返ると、捨てた接続の「未コミット」とログの行が次の接続の画面へ戻る。そこでストア全体の区切りを `clear` で進め、`runStatement` は始めたときの区切りを控える。**履歴には残す。**履歴は接続をまたいで残す「実際に何を流したか」の記録であり（[[0005-クエリ履歴とセッション復元のsqlite]]）、文はデータベースで実際に走っている。
- **Rust 側のプールは、手放したタブを覚えて以後の実行に接続を割り当てない**（2026-09-27 追記）。覚えていなかったときは、手放しが実行より先に届くと閉じたタブに接続が割り当てられ、LRU で剥がされるまで接続とカーソルを握り続けた。タブの ID は使い回されず（UUID）、繋ぎ直しはプールごと作り直すため、覚えたタブがまた使われることは無い。
- **カーソルに触れる命令（実行・続きの取り出し・カーソルを閉じる）は、割り当ての表を握ったままアクタースレッドへ積む**（2026-09-27 追記）。アクタースレッドは積まれた順に処理する（[[0002-接続ごとのアクタースレッドと中止]]）ため、接続ごとの処理の順が表の書き換えの順と揃う。表を離してから積んでいたときは、追い越しが 2 つ起きた。手放しの `close_cursor` が、同じ接続を引き継いだ別のタブの新しいカーソルを閉じる。剥がされたタブの続きの取り出しが、剥がした側のタブの行を 1 かたまり読んで奪う。返事を待つのは表を離してからであり、待ちは `見張る` を通す（[[0026-接続断の検出と回復]]・[[0030-接続が切れていることの気付き方と繋ぎ直し]]）。
- **待った後に割り当てを外すときは、積むときに控えた通し番号の割り当てだけを外す**（2026-09-27 追記）。尽きた実行と、尽きた続きの取り出しは、返事を待った後に割り当てを外す。タブの ID で外すと、待っている間に同じタブが受けた新しい割り当て（実行し直しのカーソル）まで外し、割り当ての無いカーソルが接続を握ったまま残る。割り当てには新しいカーソルを開くたびに採り直す通し番号を持たせ、同じタブが既に持っている接続を使い続ける場合も採り直す。
- **中止はこの決まりの外にある**（2026-09-27 追記）。中止は、塞がっているアクタースレッドへ届かせるために命令の列を通らない（[[0002-接続ごとのアクタースレッドと中止]]）。割り当てを覗いてから中止が届くまでの間に、同じ接続で別のタブの文が走り始めれば、そちらを中止しうる。表を握ったまま中止を送ると、切れた回線で中止が返らないときにプールの全操作が止まる。そのため、この形にはしない。起きても別のタブの文が `ORA-01013` で止まるだけであり、行を取り違えることは無い。

## 理由

- 「1 接続 = 1 ウィンドウ」は*接続設定*が 1 つという意味であり（[[0009-ウィンドウモデルとタイトルバー]]）、物理的な接続本数とは別の話である。4 本あればタブを行き来しながらスクロールできる。
- カーソル方式では総行数が事前に分からない。取得済み行数を出し、尽きた時点で確定値に切り替えるのが、嘘をつかない唯一の表示方法である。
- CSV に取得済みの一部しか入らないのは静かなデータ欠損であり、最悪の事故である。保存時に読み切るコストは受け入れる。

## 却下した案

**接続 1 本のみ**: 別のタブで実行するたびに前のタブの結果が失われ、タブを持つ意味がなくなる。

**最初の 1,000 行だけ取得してカーソルを即座に閉じる**: 全行取得という要件を満たさない。

**サーバーサイドページング（`OFFSET`/`FETCH` を SQL に注入）**: 任意の SQL への書き換え注入となり、`ORDER BY` の無いクエリで結果が不定になるなど事故のもとである。

**CSV 保存時にクエリを再実行して全件取得**: 同じクエリが 2 回走る。`GATHER_PLAN_STATISTICS` を伴う実行（[[0002-接続ごとのアクタースレッドと中止]]）と組み合わせると副作用が二重になる。

**保存時に取得済みの行だけを書き出す**: 一部しか入っていない CSV が生まれる。

**タブを閉じるときは、実行の応答を待ってから `release_tab` を送る**（2026-09-27 追記）: 到着順の問題は起きない。しかし長い問い合わせの最中に閉じたタブが、終わるまで接続とカーソルを握る。閉じる操作を待たせることにもなる。

## 結果

- 実行中の中止（`⌘.`）はチャンク境界で自然に効く。
- 長時間開いたカーソルはデータベース側のリソースを保持し続ける。タブを閉じる、別のクエリを実行する、ウィンドウを閉じるのいずれでもカーソルを明示的に閉じる。
- プールへカーソルに触れるメソッドを足すときは、割り当ての表を握ったまま `ConnectionHandle` の `send_*` で積み、表を離してから `Pending::wait` を `見張る` 越しに待つ（2026-09-27 追記）。`execute` / `fetch_more` / `close_cursor` の待つ形をそのまま使うと、表を離してから積むことになる。
- 読み取り専用トランザクション（[[0004-認証情報と接続設定の保存先]] ではなく本 ADR の範囲）はプールの各接続に対して張る。
