# ADR 0036: 設定画面をメニューバーから開く

- ステータス: 承認
- 日付: 2026-09-27
- 追記: 届け方（イベント `koduchi://open-settings` と `onOpenSettingsRequested`）は ADR 0040 で一般化した。今はコマンドの表の識別子 `settings` を `koduchi://menu-command` で送る。

## 状況

全体設定（`SettingsPanel`）の入口は、ステータスバー右端の「設定」だけだった。macOS のアプリでは、アプリメニュー（「小槌」メニュー）の「設定…」（`⌘,`）から開くのが決まりごとであり、利用者はそこへ移したいと言っている。

確かめた事実は次の 3 つである。

- 小槌は今までメニューを組んでいない。macOS では Tauri が `Menu::default` を自動で当てており、編集メニューの取り消し・やり直し・カット・コピー・ペースト・全選択もそこにある。**WKWebView の `⌘C` / `⌘V` / `⌘A` / `⌘Z` はこの項目が受けている。**メニューを丸ごと差し替えると、書き漏らした項目の打鍵がエディタでも入力欄でも効かなくなる。
- 既定のメニューの中身（tauri 2.11.5）は、アプリメニュー（〜について・サービス・隠す・ほかを隠す・終了）、File（ウィンドウを閉じる）、Edit、View（フルスクリーン）、Window（しまう・拡大 / 縮小・閉じる）、Help である。
- 1 接続 = 1 ウィンドウであり（ADR 0009）、ストアはウィンドウごとに独立している。設定画面もウィンドウごとのオーバーレイである。

## 決定

### 既定のメニューへ 1 項目を差し込む

`src-tauri/src/menu.rs` の `build` が `Menu::default` を作り、先頭のアプリメニューの「〜について」と区切り線の直後へ「設定…」（`CmdOrCtrl+,`）と区切り線を差し込む。それ以外の項目には触れない。

### 届け先は焦点のあるウィンドウ 1 つ

メニューが押されたら、Rust 側が焦点のあるウィンドウを選び、そのウィンドウにだけイベント `koduchi://open-settings` を `emit_to` で送る。焦点のあるウィンドウが無い（すべて最小化した）ときは `main`、それも無ければラベル順で先頭のウィンドウを選び、最小化を解いて前へ出す。選び方は純粋な関数 `settings_target` にある。

フロントエンドは `src/appMenu.ts` の `onOpenSettingsRequested` で**自分のウィンドウに宛てたイベントだけ**を聞き、`ui` ストアの `openSettings` を呼ぶ。

### `App.tsx` は配線するだけ

書き換えるストアは `ui` 1 つであるため、仲介者は通さない（mediator-design の手順 1）。`App.tsx` に足すのは `useEffect(() => onOpenSettingsRequested(openSettings), ...)` の 1 行であり、表示フラグは既存の `ui.settingsOpen` をそのまま使う。

### `⌘,` はコマンドの表に置かない

`⌘,` はネイティブメニューのアクセラレータとして Rust 側が持つ。`src/mediator/commands.ts` の表（ADR 0035）にも同じキーの行を置くと、1 打鍵がウェブビューの `keydown` とメニューの両方に拾われうる。持ち主はメニュー 1 つにする。表に表記だけの行を置く（`owner: 'editor'` と同じ形）ことも、今はしない。コマンドパレットから設定を開く入口は求められていない。

### ステータスバーの入口は消す

依頼は「移す」であり、同じことをする入口を 2 つ持たない（ADR 0007 の再読み込みボタンと同じ考え）。

## 理由

- **既定のメニューに差し込むのは、編集の打鍵を守るためである。**全項目を自前で組み直しても見た目は同じにできるが、それは Tauri の既定の一覧を写し続ける作業になる。Tauri が既定に項目を足しても（たとえば将来の版で）、差し込む形なら自動で追随する。
- **焦点のあるウィンドウへ送るのは、利用者が見ているのがそこだからである。**全ウィンドウへ配ると、裏にある接続のウィンドウにも同じパネルが重なり、閉じて回ることになる。
- **最小化したウィンドウしか無いときにも開くのは、押し損を作らないためである。**メニューの項目は押せるのに何も起きない、は理由が分からない。

## 却下した案

**メニューを `Menu::with_items` で丸ごと組み直す**: 編集メニューの項目を 1 つ書き漏らすと、その打鍵がアプリ全体で効かなくなる。気づくのは使ったときである。

**設定専用のウィンドウを開く**: 全体設定は接続に属さないため筋は通る。しかしストアはウィンドウごとに独立しており（ADR 0009）、設定のウィンドウで変えた外観を他のウィンドウへ配る仕組みが要る。今のオーバーレイの設定画面も同じ問題（あるウィンドウで変えた外観は、他のウィンドウでは再読み込みまで反映されない）を抱えているが、それはこの ADR の範囲の外である。

**全ウィンドウへ `emit` し、フロントエンドで焦点を見て開くか決める**: 焦点の判定がウィンドウの数だけ非同期に走り、メニューを押した瞬間に焦点が動いたときの結果が約束できない。選ぶのは 1 か所（Rust 側）に寄せる。

**ステータスバーの入口を残す**: macOS の利用者はメニューを探す。ステータスバーは接続の状態を出す場所であり、設定だけが性質の違う入口だった。

## 結果

- 項目の名前は「設定…」である。既定のメニューのほかの項目は英語（`About koduchi` / `Edit` など）のままであり、日本語と英語が混ざる。メニュー全体を日本語にするには既定の項目を名前付きで作り直すことになり、上の「丸ごと組み直す」と同じ危うさを負う。今はしない。
- ウィンドウが 1 つも無いときは何もしない。
- capability は増えない（イベントを聞くのは `core:default` に含まれる）。
