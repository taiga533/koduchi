# ADR 0034: 問い合わせ以外の文の結果表示

- ステータス: 承認
- 日付: 2026-09-11

## 状況

`CREATE TABLE` や `ALTER TABLE` を流すと、結果ペインに次のように出る。

```
0 行 · 12 ms
```

本文にも「0 行に影響しました」と出る。**成功したのか、何もしなかったのかが読めない。**

原因は素直である。`ExecuteOutcome::Statement` は影響行数を `u64` で持ち、Oracle の `Statement::row_count` をそのまま載せていた。DDL には「影響を受けた行」という概念そのものが無く、`row_count` は 0 を返す。**1 行も当たらなかった `UPDATE` と、成功した `CREATE TABLE` が、画面の上で同じ文字列になる。**

同じことが DDL 以外でも起きている。

| 流したもの | 今の表示 | 実際に起きたこと |
| ---------------------------- | -------- | ---------------------------- |
| `create table t (id number)` | `0 行`   | 表ができた                   |
| `begin p; end;`              | `0 行`   | 手続きが走った               |
| `alter session set ...`      | `0 行`   | セッションの設定が変わった   |
| `grant select on t to u`     | `0 行`   | 権限が与えられた             |
| `update t set c = 1 where 1=0` | `0 行` | **本当に 1 行も当たらなかった** |

最後の 1 行だけが正しく「0 行」であり、上の 4 つは嘘に近い。

## 決定

### 文の種別は **Oracle から受け取る。**クライアント側で SQL を読まない

`oracle` crate の `Statement::statement_type()` が返す `StatementType` を使う。これは ODPI-C の `dpiStmtInfo.statementType`（元は OCI の `OCI_ATTR_STMT_TYPE`）であり、**Oracle が文を準備した時点で決めた種別**である。文を実行する前に読め、バインドの前後でも変わらない。

**クライアント側で SQL を解析して DDL かどうかを判定する道は採らない。**小槌には `src/sql/statements.ts` と `src/sql/scan.ts` という字句の走査があり、先頭の語を見るだけなら書ける。しかし外れる。

- `q'[create table ...]'` のような代替引用符の中身。走査は `scan.ts` が既に扱っているが、**扱えるかどうかは問題ではない。**外した瞬間に「成功しました」と「0 行」が入れ替わる、という壊れ方が問題である。
- 先頭のコメント（`/* 棚卸し */ update ...`）と改行。
- `create or replace procedure` の本体に `update` が現れる。先頭の語だけを見れば正しいが、「どこまでを先頭と見るか」の規則を小槌が持つことになる。
- `WITH ... INSERT`、`MERGE`、無名 PL/SQL ブロック。

そして何より、**この判定は既に 1 か所で外していない実績のある場所がある。**[[0012-トランザクション制御]] は「クライアント側で DML を数えない。実行のたびに `DBMS_TRANSACTION.LOCAL_TRANSACTION_ID` を読む」と決め、[[0004-認証情報と接続設定の保存先]] の読み取り専用は「クライアント側の SQL 判定ではなくデータベース側のトランザクションで保証する」と決めている。**小槌は「この SQL は何か」を自分で決めない、という筋が既に通っている。**ここだけ例外にする理由が無い。

### 区別するのは **「影響行数に意味があるか」の 1 ビットだけ**

`StatementType` は 15 種あるが、表示に効くのは 1 つの問いだけである。**行を数えたと言ってよいか。**

| `StatementType` | 行数 |
| --------------------------------------- | ---- |
| `Insert` / `Update` / `Delete` / `Merge` | 持つ |
| `Create` / `Alter` / `Drop`              | 持たない |
| `Begin` / `Declare`（PL/SQL ブロック）   | 持たない |
| `Call`                                   | 持たない |
| `Commit` / `Rollback` / `ExplainPlan`    | 持たない |
| `Unknown`                                | 持たない |

判定は `src-tauri/src/db/oracle/mod.rs` の `has_row_count` 1 つに集める。

**`Unknown` を「持たない」に倒すのは、当てずっぽうではない。**OCI が番号を持つ文は上の表で尽きており、`GRANT` / `REVOKE` / `TRUNCATE` / `COMMENT` / `ANALYZE` はすべて `Unknown` で届く。**そのどれも行数の概念を持たない。**将来 Oracle が番号を足した文が現れても、それが行を数える文である見込みは薄く、そのとき出るのは「完了しました」であって嘘ではない。逆に倒すと、知らない文がすべて「0 行」になる。

### 行数を持たない文では **`affected_rows` を `None` にする**

`ExecuteOutcome::Statement` の `affected_rows` を `u64` から `Option<u64>` に変える。**「0 と答える」のではなく「答えない」。**

種別そのものをフロントエンドへ送らないのは、送っても使い道が無いからである。表示に要るのは上の 1 ビットであり、それは `None` かどうかに畳まれている。**判定は種別を知っている側（Rust）に置き、フロントエンドへは結論だけを渡す。**

フロントエンドの `TabExecution` には `isStatement: boolean` を足した。`affectedRows` が `null` のとき、**問い合わせ**なのか**行数の概念が無い文**なのかを分ける必要があるためである（問い合わせの `affectedRows` は元から `null` である）。

### 文言は **「完了しました」**。何を作ったかは言わない

| 状況 | ヘッダー | 本文 |
| ---------------------- | ------------------ | -------------------- |
| 行数を持つ文 | `12 行 · 8 ms` | `12 行に影響しました` |
| 1 行も当たらない DML | `0 行 · 8 ms` | `0 行に影響しました` |
| 行数を持たない文 | `完了しました · 8 ms` | `完了しました` |

**「表 FOO を作成しました」とは出さない。**そう書くには SQL から対象の名前と操作を読み取ることになり、上で退けたクライアント側の解析に逆戻りする。しかも外れ方が悪い。「表 FOO を作成しました」と出て実際は別の名前だった、というのは「0 行」より害が大きい。

「完了しました」は短く、**成功したことだけを言っていて、それ以上は言っていない。**利用者が知りたいのは「通ったのか」であり、何を作ったかは自分の書いた SQL に書いてある。

**1 行も当たらなかった DML の文言は変えない。**「0 行に影響しました」は正しく、しかも**この ADR が守ろうとしている当のもの**である。DDL と区別が付くようになった今、「0 行」は初めて意味のある表示になった。「1 行も更新されませんでした」と言い換える案もあるが、`INSERT` / `DELETE` / `MERGE` で動詞が変わるため文の種別を更に細かく見ることになり、得るものに対して割に合わない。

### スクリプト実行では **行数を持つ文だけを足し上げる**

`⌥⌘⏎` で複数の文を流したときは、これまで影響行数を素朴に足し上げていた。行数を持たない文は足し算に加えず、**1 つも行数を持つ文が無ければ合計そのものを `null` にする。**DDL を並べたスクリプトに「0 行」と出さないためである。

### 履歴にも **`0 行` と書かない**

[[0005-クエリ履歴とセッション復元のsqlite]] の `row_count` は元から `Option<i64>` である。行数を持たない文では `null` を記録する。`0` を書くと、履歴を読み返したときに空振りした DML と見分けが付かない — 画面で解いた問題を保管庫の中で作り直すことになる。

### 未コミットの表示には手を入れない

DDL は暗黙にコミットする。しかし [[0012-トランザクション制御]] が「実行のたびに `DBMS_TRANSACTION.LOCAL_TRANSACTION_ID` を読む」と決めているため、**`in_transaction` は既に正しい。**DDL の後に読めば取引 ID は消えており、ステータスバーの「未コミット」は自然に降りる。

**「DDL は暗黙にコミットされました」という注意書きも足さない。**Oracle を相手にする利用者にとっては前提であり、DDL を流すたびに同じ 1 行が積まれるのは通知ではなく雑音である。

## 理由

- **種別の出どころを Oracle にしたのは、外れたときの壊れ方が最悪だからである。**「成功した」と「何も起きなかった」が入れ替わる表示は、遅い表示や素っ気ない表示よりずっと悪い。小槌が SQL を読んで決めるかぎり、いつか必ず外す。読まなければ外しようがない。
- **1 ビットに畳んだのは、表示が問うているのがその 1 ビットだからである。**15 種の種別をフロントエンドまで運べば、そこで「どれが行を持つか」をもう一度書くことになる。同じ規則が 2 か所にあると、いつか食い違う。
- **`0` ではなく `None` にしたのは、型に嘘を持ち込まないためである。**「意味の無い 0」を運ぶと、受け取った側がそれを数として扱ってよいかを毎回判断することになる。`Option` なら判断は 1 回で済み、しかもコンパイラが見張る。
- **「完了しました」に留めたのは、言えることだけを言うためである。**小槌が確かに知っているのは「エラーにならずに終わった」ことだけである。それ以上を書けば、書いた分だけ外れる余地が生まれる。

## 却下した案

**フロントエンドで SQL の先頭の語を見て DDL かどうかを判定する**: Rust 側に手を入れずに済むが、代替引用符・コメント・PL/SQL の本体で外れる。外れたときに「成功しました」と「0 行」が入れ替わるという、最も質の悪い壊れ方をする。[[0012-トランザクション制御]] と [[0004-認証情報と接続設定の保存先]] が同じ誘惑を退けた筋にも反する。

**`StatementType` をそのままフロントエンドへ送る**: 将来「DDL のときだけ別の文言」を出せるようになるが、今それを要する表示が無い。使い道の無い 15 値をフロントエンドまで運ぶと、「どれが行を持つか」の規則が Rust とフロントエンドの両方に現れる。必要になったときに足せばよい。

**`affected_rows` を `u64` のまま残し、種別の欄を別に足す**: 配線の変更が小さいが、「意味の無い 0」が線の上を流れ続ける。受け取った側が毎回「この 0 は数えた結果か」を判断することになり、判断の置き場所が増える。

**「表 FOO を作成しました」と出す**: 最も親切に見えるが、対象の名前と操作を SQL から読み取ることになる。外れたときに嘘の名前を表示する。退けたクライアント側の解析そのものである。

**「DDL は暗黙にコミットされました」をメッセージタブへ出す**: 親切に見えるが、DDL を流すたびに同じ行が積まれる。Oracle の前提であり、しかも未コミットの表示は既に正しく降りている。[[0026-接続断の検出と回復]] が「報せるのは段階が実際に変わったときだけ」としたのと同じ考えである。

**「1 行も更新されませんでした」のように動詞を入れる**: `UPDATE` では読みやすいが、`INSERT` / `DELETE` / `MERGE` で動詞が変わる。動詞を選ぶために種別をもう 1 段細かく運ぶことになり、この ADR が 1 ビットに畳んだ意味が薄れる。そもそも issue が言っているのは DDL の話であり、広げすぎである。

**`Unknown` を「行数を持つ」に倒す**: 知らない文で数を失わない、という理屈は立つ。しかし実際に `Unknown` で届くのは `GRANT` / `TRUNCATE` / `COMMENT` などであり、どれも行を数えない。**今いる場所（すべてが「0 行」）へ戻るだけである。**

**スクリプトの合計を素朴に足し上げたままにする**: 行数を持たない文の 0 を足しても合計は変わらないため、混ざったスクリプトでは害が無い。しかし DDL だけを並べたスクリプトが「0 行」になる。1 文のときに解いた問題が、複数文のときに残る。

## 結果

- `ExecuteOutcome::Statement.affected_rows` が `Option<u64>` になった。`src/types/db.ts` の `affectedRows` も `number | null` になっている。
- `src-tauri/src/db/oracle/mod.rs` に `has_row_count` が増えた。`StatementType` は純粋な列挙であるため、**データベースに繋がなくても `cargo test` で全種別を確かめられる。**
- `TabExecution` に `isStatement` が増えた。`affectedRows` が `null` のときに問い合わせと区別するためだけの欄である。
- 結果ペインの本文の文言は `formatStatementOutcome`（`src/stores/execution.ts`）に切り出した。ヘッダーの `formatResultSummary` と同じ置き場所である。
- 履歴の `row_count` は、行数を持たない文で `null` になる。既存の行には触れていない。
- Oracle を要する統合テスト（`src-tauri/tests/oracle.rs`）に 3 件を足した。`KODUCHI_TEST_ORACLE_URL` が無い環境ではこれまでどおり飛ばされる。
- **`⌘E` / `⇧⌘E` の実行計画には関係が無い。**`EXPLAIN PLAN FOR` は `explain_plan` の中で組み立てており、`ExecuteOutcome` を通らない。
