# ADR 0019: テーブル定義ビューと DDL の取得

- ステータス: 承認
- 日付: 2026-09-08

## 状況

小槌には**定義を読む道が無い**。スキーマツリー（[[0007-スキーマ取得の段階的ロード]]・[[0014-スキーマツリーのオブジェクト種別拡張]]）は名前と列と型までしか出せず、次のことが分からない。

- **この列は何かの外部キーか。何を指しているのか。** 参照先を辿るには `ALL_CONSTRAINTS` を手で引くしかない。
- **この表にどんな索引が付いているか。どの列をどの順で並べているか。** ツリーは索引の名前しか出さず、しかも自動生成のものは落としている（[[0014-スキーマツリーのオブジェクト種別拡張]]）ため、主キーの索引は 1 件も見えない。
- **このビューの本文はどう書かれているか。この関数は何をしているか。** `DBMS_METADATA.GET_DDL` をどこからも呼んでおらず、本文を見る手段がまったく無い。**パッケージ本体に至っては、ツリーから種別ごと落としてある**（[[0014-スキーマツリーのオブジェクト種別拡張]]）ので、名前すら出てこない。

`adr/README.md` の機能スコープは、テーブル定義ビューを長らく「器だけ（開かない）」に置いてきた。ツリーの行の右には押せない「定義」の札が出ており、`title` に「テーブル定義ビューは未実装です」と書いてある。

[[0014-スキーマツリーのオブジェクト種別拡張]] は制約について明示的な申し送りを残している。「制約はツリーに出さない。テーブル定義ビューを作る波で、そのビューの中に置く」。本 ADR はその波である。

Oracle 側の事情を確かめた。

- **`DBMS_METADATA.GET_DDL` は `CLOB` を返す。** `oracle` crate は既定で `String` として取り出せる。
- **素のままの GET_DDL は読めない。** `PCTFREE 10 INITRANS 1 MAXTRANS 255 ... STORAGE(INITIAL 65536 NEXT 1048576 MINEXTENTS 1 MAXEXTENTS 2147483645 PCTINCREASE 0 FREELISTS 1 FREELIST GROUPS 1 BUFFER_POOL DEFAULT FLASH_CACHE DEFAULT CELL_FLASH_CACHE DEFAULT) TABLESPACE "USERS"` が表と索引の 1 つずつに付き、本文の倍近くを占める。`DBMS_METADATA.SET_TRANSFORM_PARAM` で落とせる。
- **GET_DDL の型名は `ALL_OBJECTS.OBJECT_TYPE` の綴りと一致しない。** `MATERIALIZED VIEW` は `MATERIALIZED_VIEW`、`DATABASE LINK` は `DB_LINK` であり、空白ではなくアンダースコアで繋ぐ。`object_type()` の綴りをそのまま渡すと `ORA-31600` になる。
- **`GET_DDL('PACKAGE', …)` は仕様しか返さない。** 本体は `PACKAGE_BODY` として別に取る。
- **GET_DDL は他人のオブジェクトに対して `ORA-31603`（object not found in schema）を返すことがある。** 実際には権限が無いことを意味する。
- **`ALL_CONSTRAINTS.SEARCH_CONDITION` は `LONG` である。** `oracle` crate では読めない。12c 以降の `SEARCH_CONDITION_VC`（`VARCHAR2(4000)`）がある。
- **`ALL_CONS_COLUMNS.POSITION` は `NULL` になりうる。** 検査制約と `NOT NULL` 制約では列の並び順に意味が無いためである。
- **Oracle は列に付けた `NOT NULL` を検査制約として持つ。** 名前は `SYS_C0012345` になり、実際のデータベースでは制約の過半がこれになる（[[0014-スキーマツリーのオブジェクト種別拡張]] が指摘したとおりである）。

## 決定

### 定義ビューは `SessionsPanel` と同じオーバーレイに出す

**→ この点は [[0022-テーブル定義タブ]] で覆した。**定義はエディタのタブ帯に定義タブとして開くようになり、オーバーレイでも `esc` で閉じるものでもなくなった。**結果ペインの動的タブにしない**という下の判断だけは 0022 も引き継いでいる。以下は覆される前の記録である。

ステータスバーから開くセッションパネル（[[0017-セッションとロックの確認]]）と同じ器に載せる。`TableDefinitionPanel` は `role="dialog"` のオーバーレイであり、`esc` で閉じる。

**結果ペインの動的タブ（[[0009-ウィンドウモデルとタイトルバー]]）にはしない。** [[0017-セッションとロックの確認]] が同じ理由でこれを退けている。結果ペインのタブはエディタタブごとの実行結果に紐付いており、どのエディタタブにも属さないものを置くと、タブを切り替えるたびに現れたり消えたりする。定義はエディタタブに属さない。**サイドバーにも出さない。** 180〜480px では、制約の名前・掛かっている列・参照先の表と列を 1 行に並べられない。**別ウィンドウにもしない。** 1 接続 = 1 ウィンドウ（[[0009-ウィンドウモデルとタイトルバー]]）を曲げるほどの値打ちが無い。

タブは**列 / 制約 / 索引 / DDL** の 4 つで、並びは固定する。

### 入口はツリーの行の右の「定義」1 つだけ

**→ この点は [[0022-テーブル定義タブ]] で覆した。**「定義」のボタンは消え、入口は右クリックのメニューの「定義を開く」（と、ツリーの中の `⌘D`）になった。下で却下している「入口を右クリックのメニューにする」が、[[0020-スキーマツリーからの操作]] がメニューを作り終えたことで通るようになったためである。**「すべての種別の行に出す」という下の判断は 0022 も引き継いでいる。**以下は覆される前の記録である。

ツリーの行に既にある「定義」の札を、押せるボタンにする。**ツリーのマウス操作の割り振りは足さない。** 行のクリックは今までどおり展開であり、「定義」は行とは別の押しどころである。行そのものの意味を変えないため、ツリーからの操作を作る波（ADR 0020）と衝突しない。

**「定義」はすべての種別の行に出す。** 器だった時代は展開できる 3 種別（テーブル・ビュー・マテビュー）にしか出していなかったが、DDL を見る値打ちが最も大きいのはファンクション・プロシージャ・パッケージ・トリガーである。パッケージ本体に至っては、[[0014-スキーマツリーのオブジェクト種別拡張]] が種別ごと落としているため、**本体を見る道はここにしかない。**

### 定義と DDL は別のコマンドに分け、DDL は DDL タブを開いたときに初めて取る

`object_definition`（列・制約・索引）と `object_ddl`（GET_DDL）の 2 つを足す。定義ビューを開いた時点で走るのは前者だけである。

分ける理由は 2 つある。GET_DDL は重い（`DBMS_METADATA` はカタログを広く読む）。そして権限に敏感である。**GET_DDL の権限が無いというだけで、列も制約も索引も見られなくなってはいけない。** 実際、`SELECT ANY TABLE` は持っていても `SELECT_CATALOG_ROLE` を持たない接続は珍しくなく、そこでは `ALL_*` は読めても GET_DDL は通らない。

取った DDL は同じ対象を開いている間だけ覚え、タブを行き来しても取り直さない。別のオブジェクトを開けば捨てる。

### 取得はプールの `background_handle` で行う

スキーマ取得（[[0007-スキーマ取得の段階的ロード]]）・実行計画・セッション一覧（[[0017-セッションとロックの確認]]）と同じ経路に相乗りする。`Connection` を直接使い、`OracleDriver` が持つ結果セットのカーソル（[[0003-結果セットのカーソル保持と接続プール]]）には触れない。**利用者が見ている結果セットは、定義を何度開いても壊れない。**

### `SET_TRANSFORM_PARAM` で 4 つを調整する

GET_DDL の前に `DBMS_METADATA.SESSION_TRANSFORM` へ次を設定する。

| 項目                 | 値 | 理由                                                              |
| -------------------- | ---- | ----------------------------------------------------------------- |
| `SQLTERMINATOR`      | 真 | 末尾に `;`（PL/SQL は `/`）が付く。そのままエディタへ貼って実行できる |
| `PRETTY`             | 真 | 改行と字下げが入る。既定でも真だが明示する                        |
| `SEGMENT_ATTRIBUTES` | 偽 | `PCTFREE` / `INITRANS` / `TABLESPACE` が落ちる                    |
| `STORAGE`            | 偽 | `STORAGE(INITIAL … BUFFER_POOL …)` が落ちる                       |

記憶域の属性を落とすのは、**読むための DDL** だからである。素のままでは本文の倍近くを占め、列の並びを目で追えない。そのまま流せば同じ物理設計が再現される DDL ではなくなるが、それが要るのは移行作業であり、小槌の定義ビューが担うところではない。

設定はセッションに残る。この接続で GET_DDL を使うのはこの経路だけであるため、後始末はしない。設定に失敗しても DDL そのものは取れるため、エラーにはせず整形が既定のまま出る。

### 種別ごとの GET_DDL 型名は `ObjectKind` から引く表にする

`ObjectKind::ddl_object_type()` を 12 種別すべてに定義し、`ddl_body_type()` がパッケージにだけ `PACKAGE_BODY` を返す。`object_type()`（`ALL_OBJECTS` 用）とは**別のメソッド**にする。綴りが違うためであり、片方で済ませようとすると `ORA-31600` を踏む。全種別が型名を持つこと、型名に空白が入らないことをテストで固める。

### 制約はここに置く（[[0014-スキーマツリーのオブジェクト種別拡張]] からの申し送り）

`ALL_CONSTRAINTS` / `ALL_CONS_COLUMNS` から主キー・一意・外部キー・検査の 4 種を取り、定義ビューの「制約」タブに出す。ツリーへはぶら下げない。[[0014-スキーマツリーのオブジェクト種別拡張]] の決定を覆すのではなく、置き場所がここに決まったという形である。

- **外部キーは参照先の表と列まで出す。** `R_OWNER` / `R_CONSTRAINT_NAME` を `ALL_CONSTRAINTS` へ外部結合して表を、`ALL_CONS_COLUMNS` を参照先側で引き直して列を取る。`ON DELETE CASCADE` / `SET NULL` も添える。参照先が見えない（権限が無い）ときは「参照先を参照できません」と出す。**括弧だけを出して黙らない。**
- **検査条件は `SEARCH_CONDITION_VC` から読む。** `SEARCH_CONDITION` は `LONG` で読めない。12c 以降でしか使えないが、[[0001-oracle接続方式]] の対象は 12c 以降である。
- **`NOT NULL` を言っているだけの検査制約は落とす。** 列の一覧に「NULL 可」の欄が既にある以上、同じことを 2 度並べても読み手の手掛かりは増えない。落とさないと、制約タブの過半が `SYS_C0012345` で埋まって外部キーが埋もれる。判定は `is_not_null_check` という純粋な関数であり、`"COL" IS NOT NULL` の形だけを落とす。`"A" IS NOT NULL AND "B" > 0` のような利用者の書いた条件は残す。
- **並びは種別（主キー → 一意 → 外部キー → 検査）、同じ種別の中は名前順**に揃える。`ALL_CONSTRAINTS` の返す順はデータベースの版や統計で変わる。

### 索引は自動生成のものも出す（ツリーとは扱いを変える）

`ALL_INDEXES` / `ALL_IND_COLUMNS` から、列の並び・一意性・種類・状態を出す。**`GENERATED = 'N'` では絞らない。**

[[0014-スキーマツリーのオブジェクト種別拡張]] がツリーで自動生成を落としているのは、`SYS_C0012345` が**利用者の付けた名前ではなく、名前で探せないから**である。ツリーは名前で探す道具であり、そこにこの理屈が効く。定義ビューは違う。ここで読み手が知りたいのは「この列で引けるのか」であって名前ではない。**主キーと一意制約の索引が見えない定義ビューは、その問いに答えられない。** 名前が読めないことは「自動生成」の印で補う。

列は `COLUMN_POSITION` の順に並べ、降順の列にだけ `DESC` を添える。すべてに `ASC` を書くと降順が埋もれる。

### 列は段階 2 のキャッシュを使い回さず、開いたときに引き直す

`schema` ストアは段階 2（[[0007-スキーマ取得の段階的ロード]]）で読んだ列を持っているが、定義ビューはそれを使わない。Rust 側が `ALL_TAB_COLUMNS` をそのオブジェクト 1 つに絞って引き直す。

**段階 2 が終わっていないスキーマを開かれうるためである。** キャッシュを使うと、そのとき列が 0 件で出る。「列が無い表」と「まだ読んでいない表」を同じ画面で表すのは、[[0017-セッションとロックの確認]] が退けた「見えない」と「居ない」の混同と同じ害である。読み込み中の印を出す道もあるが、1 オブジェクトぶんの問い合わせは軽く、待つより速い。

### 引かない種別には問い合わせにも行かない

列を持たない種別（[[0014-スキーマツリーのオブジェクト種別拡張]] の `has_columns()`）では列を引かず、テーブルとマテリアライズドビュー以外（`has_table_details()`）では制約も索引も引かない。ビューは列だけを引く。[[0014-スキーマツリーのオブジェクト種別拡張]] の「落とした種別は問い合わせにも行かない」と同じ考え方である。ファンクションの定義を開いて `ALL_CONSTRAINTS` を 3 本引くのは無駄である。

### 権限不足は `DbErrorKind::Permission` へ写す

[[0017-セッションとロックの確認]] が新設した区分をそのまま使う。GET_DDL では `ORA-00942` / `ORA-01031` に加えて **`ORA-31603` も権限として扱う。** オブジェクト名はスキーマツリーが `ALL_OBJECTS` から取ってきたものであり、存在しないことはまず無い。届かないのは権限の話である。

判定は `oracle::errors` へ切り出した。[[0017-セッションとロックの確認]] が `oracle::sessions` の中に持っていたものを、2 か所で使うため共通化しただけである。

### 絞り込みは列・制約・索引の 3 タブに効かせる

列が数百ある表は珍しくない。開いてからスクロールで探させるのでは、SQL を書く前の確認という用途に足りない。語は列名と型名、制約名と掛かっている列と参照先と検査条件、索引名と並べている列に当てる。**制約と索引にも列名で当たること**が肝心である。「この列は何かの外部キーか」「この列で引ける索引はあるか」は同じ 1 つの問いであり、タブごとに語を打ち直させる理由が無い。

拾い方は大小を区別しない部分一致であり、あいまい一致は使わない（[[0018-保存済みクエリとコマンドパレット]] と同じ）。判定は `src/components/definition/definitionSearch.ts` の純粋な関数に寄せる。

タブの見出しに添える件数は**絞り込む前の総数**である。絞り込んだ数を出すと、語を打つたびに見出しが動いて「元は何件あったのか」が分からなくなる。

### 開閉の状態は `definition` ストアに持つ

設定画面とセッションパネルの開閉は `ui` ストアの真偽値だが、定義ビューは対象（スキーマ名・オブジェクト名・種別）という中身を伴う。中身は取得した定義と一緒に置くほうが素直であるため、8 つ目のストアを作らず `definition` ストアに畳んだ。切断時は `App.tsx` が `clear()` を呼ぶ（[[0017-セッションとロックの確認]] のセッションストアと同じ扱い）。

## 理由

- **定義と DDL を分ける**のが、この ADR で最も効いている判断である。GET_DDL は最も価値が高く（本文が見える）、最も落ちやすい（権限・重さ）。1 つのコマンドにまとめると、落ちやすいほうが価値の確実なほうを道連れにする。
- **`SET_TRANSFORM_PARAM` を調整する**のは、整形しない GET_DDL が事実上使えないためである。「取れてはいるが読めない」は、取れていないのとほとんど変わらない。
- **索引の扱いをツリーと変える**のは、2 つの画面が答えている問いが違うからである。ツリーは「何という名前のものがあるか」、定義ビューは「この表はどう引けるか」。同じ `GENERATED` 列を見て逆の判断をするのは、一貫していないのではなく、判断の根拠が違う。
- **`NOT NULL` の検査制約を落とす**のは、[[0014-スキーマツリーのオブジェクト種別拡張]] が「名前の大半が意味を持たない」としてツリーから制約を外したのと同じ理屈である。ツリーでは制約ごと外したが、ここでは意味のあるものだけを残せる。
- **列を引き直す**のは、段階的ロード（[[0007-スキーマ取得の段階的ロード]]）が「途中の状態がありうる」ことを前提にした仕組みだからである。途中の状態を別の画面へそのまま持ち込むと、その画面は嘘をつく。
- **入口を 1 つに絞る**のは、ツリーのマウス操作を別の波（ADR 0020）が触っているためである。行の意味を変えない場所に足せば、どちらの作業も止まらない。

## 却下した案

**結果ペインの動的タブとして出す**: エディタタブごとの実行結果に紐付いた器であり、どのエディタタブにも属さない定義を置くとタブの意味が壊れる（[[0009-ウィンドウモデルとタイトルバー]]・[[0017-セッションとロックの確認]] と同じ理由）。

**サイドバーのツリーの中に、テーブルの子として制約と索引をぶら下げる**: 「スキーマ → 種別の束 → オブジェクト → 列」の形（[[0014-スキーマツリーのオブジェクト種別拡張]]）に、列と並ぶ第 2 の枝分かれが要る。行数も増える。180〜480px の幅では、外部キーの参照先を 1 行に収められない。

**別ウィンドウで出す**: 1 接続 = 1 ウィンドウ（[[0009-ウィンドウモデルとタイトルバー]]）の取り決めと、`connection-` 前置きのラベル規約・capability の受けを曲げることになる。調べものの間だけ見る画面に見合わない。

**定義ビューを開いた時点で DDL も一緒に取る**: 往復が 1 つ減り、DDL タブの待ちが消える。しかし GET_DDL の権限が無い接続では定義ビュー全体が開けなくなる。最も落ちやすいものを最初に踏むのは筋が悪い。

**GET_DDL の整形を既定のままにする**: 実装は 1 行減る。だが記憶域の属性が本文の倍近くを占め、読むための DDL にならない。整形を利用者の設定にする案もあるが、「読める形」以外を選ぶ理由が思い当たらないため項目を増やさない。

**`SET_TRANSFORM_PARAM` を GET_DDL の後で元へ戻す**: セッションを汚さない。だがこの接続で `DBMS_METADATA` を使うのはこの経路だけであり、戻す先の「元の値」を読む往復のほうが高くつく。

**`ObjectKind::object_type()` を GET_DDL にも使い回す**: メソッドが 1 つ減る。しかし `MATERIALIZED VIEW` と `DATABASE LINK` で `ORA-31600` になる。2 つの綴りが偶然ほとんど一致しているだけであり、同じものと見なすと必ず踏む。

**GET_DDL の `ORA-31603` を「オブジェクトが見つからない」として扱う**: 文言どおりではある。しかし名前は `ALL_OBJECTS` から取っており、消えた直後でもない限り存在する。「見つからない」と出すと、利用者は名前を疑って権限に辿り着けない。

**索引は自動生成のものを落とす（ツリーと揃える）**: 一貫はする。だが主キーの索引が 1 つも見えない定義ビューになる。「この列で引けるのか」に答えられないなら、索引タブを置く意味が薄い。

**`NOT NULL` の検査制約も並べる**: `ALL_CONSTRAINTS` が返したものをそのまま出すのが素直ではある。しかし制約タブの過半が `SYS_C0012345` で埋まり、外部キーが埋もれる。列の一覧が同じことを既に言っている。

**段階 2 のキャッシュから列を使い回す**: 往復が 1 つ減る。しかし読み込みの途中で開かれると列が 0 件で出る。「列が無い」と「まだ読んでいない」を同じ画面で表せない。

**入口を右クリックのメニューにする**: 衝突しにくい案として検討した。しかしツリーに右クリックのメニューはまだ 1 つも無く、ここで作るとツリーからの操作を作る波（ADR 0020）と真正面からぶつかる。行に既にある「定義」の札を押せるようにするほうが、差分も衝突も小さい。**→ [[0020-スキーマツリーからの操作]] がメニューを作り終えたことで却下の理由が消え、[[0022-テーブル定義タブ]] でこの案を採った。**

**行のダブルクリックで開く**: 押しどころを増やさずに済む。しかしダブルクリックはツリーのマウス操作の割り振りに新しい行を足すことであり、ADR 0020 の持ち物に手を入れることになる。

**DDL をエディタの新しいタブへ流し込む**: 貼って直せる。しかし定義ビューの中で列と見比べたいことのほうが多く、タブが増え続ける。DDL は等幅で読めれば足り、必要なら選択してコピーできる。

## 結果

- `Driver` trait のメソッドが 2 つ増えた（`object_definition` / `object_ddl`）。PostgreSQL を足すときは `information_schema` と `pg_get_viewdef()` / `pg_get_functiondef()` で同じ形を満たすことになる。**PostgreSQL には `GET_DDL` に相当する「表の DDL を返す関数」が無い**ため、表については列と制約から組み立てることになる。
- `oracle::sessions` が持っていた権限の判定を `oracle::errors` へ切り出した。[[0017-セッションとロックの確認]] の振る舞いは変えていない。
- `ObjectKind` にメソッドが 4 つ増えた（`has_table_details` / `ddl_object_type` / `ddl_body_type` / `ddl_label`）。**種別を足すときはこの表も埋めること。** 埋め忘れはテストが落とす。
- ツリーの「定義」の札が押せるようになり、`adr/README.md` の機能スコープから「器だけ」が消えた。残る「器だけ」はタイトルバーの Ask AI ボタンだけである。**→ 札そのものは [[0022-テーブル定義タブ]] で消えた。**
- 開発用データベースに `dev/oracle/initdb/006_table_details.sql` を足した。複合の主キーと複合の外部キー・名前を明示した検査制約・複合索引を持つ表が無く、定義ビューの見え方を統合テストで確かめられなかったためである（[[0014-スキーマツリーのオブジェクト種別拡張]] が `005_object_kinds.sql` を足したのと同じ形）。既にボリュームを持っている開発者は、このスクリプトを手で流す必要がある。
- **`ALL_CONS_COLUMNS.POSITION` が `NULL` になることは、実機に当てて初めて分かった。** 検査制約と `NOT NULL` 制約では列の並び順に意味が無いためである。`NULL` は 0 として読む。どちらも列を 1 つしか持たず、並べ替えの結果は変わらない。
- 関数ベースの索引では `ALL_IND_COLUMNS.COLUMN_NAME` が `SYS_NC00007$` になる。式そのものは `ALL_IND_EXPRESSIONS` にあるが、今回は引かない。`FUNCTION-BASED NORMAL` という種類は出るため、「ただの列ではない」ことは読み取れる。
- 列の既定値（`ALL_TAB_COLUMNS.DATA_DEFAULT`）は出さない。`LONG` であり `oracle` crate で読めないためである。DDL タブには出る。
