# ADR 0024: SQL の整形

- ステータス: 承認
- 日付: 2026-09-08

## 状況

業務で書かれた SQL がエディタへ貼り付けられる。改行もインデントも無い長い 1 行がそのまま渡ってくることは珍しくなく、200 桁を超える `select` の中で `from` がどこにあるのかを目で追うところから読み始めることになる。小槌には今のところ整形の手立てが一切無い。

読むための道具である以上、貼り付けたものを読める形へ直せることは要る。決めるべきことは 6 つある。

1. 整形の中身をどこから調達するか。自前で書くのか、既存のものを使うのか
2. その道具が Oracle の書き方（`q'[...]'` 引用符リテラル・バインド変数）を壊さないか
3. 整形できなかったときにどう振る舞うか
4. 書式を設定にするか、決め打ちにするか
5. 選択範囲を整形するとき、周りのインデントとどう折り合うか
6. どの打鍵で始めるか。macOS でその打鍵が拾えるか

## 決定

### `sql-formatter` 15.8.2 をフロントエンドの依存として入れる

整形そのものは自前で書かない。`sql-formatter` を版を固定して入れ、Rust 側には整形を置かない。

整形はエディタの中で完結する操作であり、データベースへ行く必要が無い。**接続していなくても（起動直後でも切断中でも）整形は使える。**フロントエンドに置けばそれがそのまま成り立つ。Rust へ渡すと IPC を 1 往復挟んだうえ、接続が無い状態のためだけの経路を作ることになる。

### 整形が変えてよいのは空白の置き方だけとし、字句の並びで見張る

**これが本 ADR の中心である。**

`sql-formatter` 15.8.2 は Oracle の `q'[...]'` 引用符リテラルに**改行が入っていると壊す**。手を動かして確かめた結果は次のとおりである。

```
入力: select q'[一行目
二行目]' from dual
出力: select
  q '[一行目
二行目]'
from
  dual
```

`q` と `'[...]'` の間に空白が入り、引用符リテラルが「識別子 `q`」と「文字列リテラル」に割れている。Oracle に投げれば別の意味になるか、そのまま落ちる。1 行に収まる `q'[...]'` は無事であり（区切り文字が `[] () {} <>` でも任意の 1 文字でも通る）、バインド変数 `:name` / `:1` も、行コメント・ブロックコメント・オプティマイザヒント `/*+ ... */`・外部結合の `(+)`・`||`・引用符付き識別子・日本語のリテラルも保たれる。壊れるのは**改行を含む `q'[...]'` だけ**である。

とはいえ「今のところ壊れるのはこれだけ」に賭けるわけにはいかない。整形は利用者が書いた SQL を丸ごと置き換える操作であり、黙って壊せば気づかれないまま実行される。そこで**入力と出力を字句の並びで照合し、1 つでも食い違えば整形を取りやめる**。

- 照合は `src/sql/tokens.ts` の `tokenizeSql` が作る並びで行う。空白は落とし、文字列リテラル・引用符付き識別子・`q'[...]'`・コメントは中身ごと 1 つの字句として持ち、それ以外の記号は 1 文字ずつに割る。`a||b` と `a || b` は同じ並びになり、`q'[a\nb]'` と `q` + `'[a\nb]'` は違う並びになる。
- 走査の下ごしらえは `src/sql/scan.ts` へ切り出し、**文の切り出し（`statements.ts`）と同じ判定を通す**。`q'[...]'` の見立てが 2 通りに割れると、`⌘⏎` が実行する範囲と整形が守る範囲がずれる。
- 食い違ったときは、何番目のどの字句が何に変わったかを添えて報せる。

この照合が成り立つのは、**綴りを一切畳まないと決めた**からでもある。`keywordCase` / `identifierCase` / `dataTypeCase` / `functionCase` はすべて `preserve` で通す。識別子の綴りを勝手に変えないのは [[0013-補完の候補生成と識別子の出力スタイル]] の「引用符は必要なときだけ付け、付けるときは綴りを変えない」と同じ考えであり、併せて「空白だけが変わる」という照合の前提を保っている。キーワードを大文字へ畳む案は却下した（後述）。

### 整形できなければ本文には一切触れず、メッセージタブへ報せる

`sql-formatter` は構文を読み取れないと例外を投げる（閉じていない引用符、`&1` のような SQL\*Plus の置換変数など）。投げられたときも、上の照合で食い違いを見つけたときも、**エディタの本文には何も当てない。**

結果の型（`FormatOutcome`）で成否を分け、失敗のときは整形後の文字列を**そもそも返さない**。呼ぶ側が取り違えて書き戻せないようにするためである。

報せの行き先はメッセージタブ 1 つにする。ADR README の「機能スコープ」が「エラー表示はメッセージタブのテキストのみとする」と決めており、エディタの中に別の出し方を作らない。黙って何もしないのは採らなかった。押した本人にとって「効かないアプリ」と「整形できない SQL」の区別が付かない。

`execution` ストアへ `noteFormatFailure` を足し、記録を積んだうえで結果ペインをメッセージタブへ切り替える。併せて `selectResultTabs` の出現条件を直した。これまでは**通知（`DBMS_OUTPUT`）が 1 つも無いとメッセージタブが出なかった**ため、通知を伴わない記録（整形の失敗と、[[0012-トランザクション制御]] のコミットの失敗）は書いても出る先が無かった。

### 書式は決め打ちにする

インデントは空白 2 つ（CodeMirror の既定に合わせる）、文と文の間は 1 行、綴りは畳まない。**設定の項目は 1 つも作らない。**

まず 1 通りで出し、不満が出てから切り出す。`sql-formatter` は 10 を超える選択肢を持つが、そのどれが業務で要るのかは使ってみないと分からない。使われない設定を `settings.toml` に増やすと、置き場所（アプリ共通か接続ごとか）と既定値と画面をその時点で決めることになり、後から動かしにくくなる。整形は結果が目の前に出る操作であり、気に入らなければ `⌘Z` で戻せる。設定を作るのは、戻すのが面倒になってからで間に合う。

方言は `plsql` に固定する。小槌は今のところ Oracle 専用であり、CodeMirror 側の方言（`dialect.ts` の `koduchiOracleDialect`）も Oracle 固定である。**接続の有無や接続種別では切り替えない。**切り替えると、接続していないときに整形が使えないか、あるいは既定の方言を別に決めることになる。PostgreSQL が入るとき（ADR README「機能スコープ」の順序）に、`dialect.ts` と同じ場所で一緒に分岐させる。

### 選択範囲は、選択の始まりの位置へ揃える

選択があればその範囲だけを整形し、無ければ本文全体を整形する。選択範囲を単体の SQL として整形すると行頭が左端へ寄り、周りのインデントから浮く。そこで 2 行目以降に下げ幅を足す。

下げ幅は「選択の始まりが行のどこにあるか」で決める。

- 行頭から選択の始まりまでが空白だけなら、**その空白**を下げ幅にする。選択した塊はもともとその位置に置かれていたのだから、そこへ揃うのが自然である。
- 手前に文字があるなら（`... from (|ここから|)` のような選び方）、**その行の行頭の空白**を下げ幅にする。塊の途中の位置へ揃えると、行が右へ流れていく。

判定は `src/components/editor/formatting.ts` の `selectionIndent` / `indentContinuationLines` という純粋な関数に寄せた。

### 書き換えは差分として当てる

整形した結果と元の本文の**前後の変わらない部分を削り**、変わった所だけを CodeMirror へ渡す（`unchangedEnds`）。

本文を丸ごと置き換えるとカーソルが末尾へ飛ぶ（[[0020-スキーマツリーからの操作]] が挿入について書いたのと同じ理由）。差分にすれば、変わらなかった所に居るカーソルはそのまま残る。前後を削る位置がサロゲートペアの間に落ちないよう 1 単位ぶん戻す。選択して整形したときは、整形し終えた範囲を選び直す。続けて `⇧⌘⏎` で実行できる。

### `⇧⌥F` に割り当て、`event.code` で拾う

`⇧⌘F` はオブジェクトのソース検索（[[0021-オブジェクトのソース検索]]）、`⌥⌘F` はエディタ内の置換で既に埋まっている。空いていて他の作法とも噛み合う `⇧⌥F` を使う。

**この打鍵は CodeMirror の keymap へキーの名前では登録できない。**macOS では `⌥` を伴う打鍵が文字そのものを変え、`⇧⌥F` の `event.key` は US 配列でも JIS 配列でも `Ï` になる。CodeMirror は配列に依らない名前（`keyName` から `base[keyCode]`）へ戻す道を持っているが、**mac で `⌥` だけが付いた組み合わせについてはそれをわざと閉じている**（`Alt` 付きの打鍵は文字入力であることが多いため）。`@codemirror/view` の `runHandlers` にその分岐がある。したがって `Shift-Alt-f` という名前では捕まらない。

そこで keymap の `any` から打鍵を直に見て、**`event.code === 'KeyF'`** で拾う。`code` は打った物理キーであり配列に依らないので US でも JIS でも同じに効く。`⌘` と `⌃` が付いているものは除き、`⌥⌘F`（置換）や `⇧⌘F`（ソース検索）と食い合わないようにする。判定は `isFormatShortcut` という純粋な関数にしてあり、コンポーネントのテストでは実機と同じ `key: 'Ï'` / `code: 'KeyF'` の打鍵を作って確かめている。

置き場所は CodeMirror の keymap である。CLAUDE.md の「キーバインドの置き場所」の規則どおり、エディタの中でしか意味を持たないキーは `App.tsx` の `keydown` に置かない。

### 定義タブでは何も起きない

定義タブを選んでいる間、`EditorPanel` はエディタそのものを描かない（[[0022-テーブル定義タブ]]）。整形の口（`SqlEditorHandle.formatDocument`）はエディタが持つため、定義タブでは繋がらず何も起きない。**判定を書き足す必要が無い。**コマンドパレットの「SQL を整形」も同じ口を通るので、そこからも何も起きない。

## 理由

- **見張りを付けたのは、壊れ方が「静か」だからである。**`q'[...]'` が割れた SQL は見た目には整形されており、実行するまで誰も気づかない。整形を諦めるのは目に見える損だが、黙って壊すのは見えない損である。見えるほうを選んだ。
- **見張りを字句の並びで行ったのは、「空白だけが変わる」が整形の定義そのものだからである。**照合の対象を出力の見た目ではなく入力との関係に置けば、`sql-formatter` の版が上がって整形の書式が変わっても検査は生き続ける。
- **走査を `scan.ts` へ切り出したのは、`q'[...]'` の見立てを 2 通り持たないためである。**片方だけが直されて食い違えば、実行する範囲と整形が守る範囲がずれる。
- **書式を決め打ちにしたのは、設定が「決めないための逃げ道」になりやすいからである。**選択肢を並べれば決めなくて済むが、既定値は結局決めることになり、そのうえ画面と保存先が増える。
- **打鍵を `code` で拾ったのは、`key` が配列と修飾キーで変わるからである。**`Ï` に縛れば US と JIS の両方でたまたま動くが、別の配列で崩れる。物理キーで見れば理由が 1 つで済む。

## 却下した案

**整形を自前で書く**: `statements.ts` に文の切り出しがある以上、その延長で書けなくはない。だが読める整形は「どこで折り返すか」「入れ子をどう下げるか」「`case` 式や副問い合わせをどう畳むか」の集まりであり、切り出しとは規模が違う。`sql-formatter` は Oracle を含む多数の方言で長く使われており、壊れる場所が 1 つ見つかったからといって置き換える値打ちは無い。**その 1 つは見張りで塞げる。**

**Rust 側に整形を置く**: `sqlformat` などの crate はある。だが整形はエディタの中で完結する操作であり、**接続していないときにも使えるべき**という点でフロントエンドに置くのが素直である。Rust へ渡せば IPC を 1 往復挟み、接続の無い状態のための経路を別に作ることになる。字句の照合も、`statements.ts` と同じ走査を使い回せるフロントエンド側のほうが安い。

**壊れる入力を前処理で守る**（`q'[...]'` を目印へ置き換えて整形し、後で戻す）: 改行を含む `q'[...]'` も整形できるようになる。だが目印が元の SQL に現れない保証を作る必要があり、`sql-formatter` が目印そのものを分割したり前後に空白を入れたりしないことも仮定になる。**守り漏らしたときに壊れるのは利用者の SQL である。**「整形できませんでした」と言うほうが害が小さい。改行を含む `q'[...]'` は珍しく、それ 1 つのために仮定を積む理由が無い。

**壊れる入力でも整形して、警告だけ出す**: 警告は読まれない。読まれなかったときに残るのは壊れた SQL である。

**整形できないとき黙って何もしない**: 打鍵に反応が無いだけで、利用者にはアプリが壊れているのか SQL が特殊なのか区別が付かない。ADR README が報せの行き先をメッセージタブと決めている以上、そこへ出せば済む。

**キーワードを大文字へ畳む**（`keywordCase: 'upper'`）: 1 行の SQL は構造だけでなく語の区別も付きにくいので、読みやすさは上がる。だが `level` や `date` のように**キーワードにも列名にもなる語**があり、`sql-formatter` がキーワードと見なした識別子はそこで綴りが変わる。非引用の識別子は Oracle にとって大小同じなので実害は出ないが、[[0013-補完の候補生成と識別子の出力スタイル]] が守ってきた「綴りを変えない」を整形だけが破ることになる。加えて、綴りが変わりうると**字句の並びによる見張りが使えなくなる**。守りを捨てて読みやすさを取る取引には見合わない。

**書式を `settings.toml` の項目にする**: アプリ共通の設定という置き場所は正しい（[[0008-デザイントークンとテーマ実装方式]] のテーマや CSV の書式と同じ棚）。だが今は「どの項目が要るか」の見当が無い。使ってから決める。

**書式を接続ごとの `connections.toml` に持つ**: 整形は接続に依らない操作であり、[[0004-認証情報と接続設定の保存先]] の棚に置く理由が無い。同じ SQL が接続先によって違う形に整形されるのは、貼り付けて読むという用途と噛み合わない。

**保存時に自動で整形する**: 手数は減るが、`.sql` ファイルは他の道具とも共有される。整形は利用者が押したときだけ起きるべきである。

**選択範囲を整形するとき、元の位置の桁数ぶん一律に下げる**: 実装は短いが、選択が行の途中から始まっていると 2 行目以降が大きく右へ流れる。行頭の空白を基準にするほうが、結果が予測できる。

**`⇧⌘F` を整形に割り当てる**（他の道具の作法）: 既にオブジェクトのソース検索（[[0021-オブジェクトのソース検索]]）が使っている。同じ打鍵で別のことが起きるほうが分かりにくい。

**`event.key === 'Ï'` で拾う**: US でも JIS でも `⇧⌥F` は `Ï` になるため、実際には動く。だが「なぜ `Ï` なのか」を毎回説明することになり、他の配列で崩れる。物理キーで見れば理由が 1 つで済む。

**`App.tsx` の `keydown` に置く**: 拾えるが、CLAUDE.md の「キーバインドの置き場所」の規則に反する。整形はエディタの中でしか意味を持たない。

## 結果

- `sql-formatter` 15.8.2 がフロントエンドの依存に増えた。版は固定してある。
- `src/sql/scan.ts` が増えた。リテラルとコメントの読み飛ばしの持ち主である。`statements.ts` からその判定を移し、同じものを `tokens.ts` も使う。`statements.ts` の振る舞いは変えていない（既存のテストがそのまま通る）。
- `src/sql/tokens.ts` が増えた。`tokenizeSql` と `firstTokenDifference` の 2 つで、整形の見張りに使う。
- `src/sql/format.ts` が増えた。`formatSql` は「整形できた / 変化なし / 整形できなかった」の 3 つを返し、**失敗のときは本文を返さない。**
- `src/components/editor/formatting.ts` が増えた。`⇧⌥F` の判定（`isFormatShortcut`）と、本文のどこをどう書き換えるか（`formatEdit` / `selectionIndent` / `indentContinuationLines` / `unchangedEnds`）である。すべて純粋な関数で、CodeMirror に依らない。
- `SqlEditorHandle` に `formatDocument` が増えた。`⇧⌥F` の打鍵とコマンドパレットの「SQL を整形」が同じ口を通る。
- `execution` ストアに `noteFormatFailure` が増えた。併せて `selectResultTabs` の出現条件を直し、**通知を伴わないエラーだけの記録でもメッセージタブが出る**ようにした。コミットの失敗（[[0012-トランザクション制御]]）もこれで出るようになる。
- **Rust 側は触っていない。**整形はフロントエンドで完結する。
- 既知の限界として、**PL/SQL ブロックの整形は見栄えが良くない**（`end loop;` が 2 行に分かれるなど）。字句の並びは保たれるため SQL としては壊れていないが、既に整形されているブロックへ当てると読みにくくなることがある。今回の目的は 1 行の SQL を読める形にすることであり、ここは使ってから判断する。
- テストは、字句の切り出しと照合・整形がバインド変数と `q'[...]'` とコメントと引用符付き識別子を保つこと・改行を含む `q'[...]'` で取りやめること・構文が読めないときに本文へ触れないこと・選択範囲の下げ幅・差分の切り詰め・`⇧⌥F` が macOS の `key: 'Ï'` でも拾えること、を見ている。
