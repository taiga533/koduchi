# ADR 0013: 補完の候補生成と識別子の出力スタイル

- ステータス: 承認
- 日付: 2026-09-08

## 状況

`@codemirror/lang-sql` に取得済みのスキーマ（[[0007-スキーマ取得の段階的ロード]]）を `{ 表名: 列名の並び }` の形で渡し、補完を任せていた。実際に使うと 2 つの穴があった。

**① 挿入される名前が必ず引用符付きになる。** `lang-sql` の内部の `nameCompletion` は、`/^[a-z_][a-z_\d]*$/` に通らない名前へ機械的に `apply: '"NAME"'` を付ける。判定に使う `caseInsensitiveIdentifiers` は `PLSQL` 方言が持たないため偽であり、Oracle のカタログ由来の名前はすべて大文字なので、**表名も列名もスキーマ名も例外なく `"TABLE_NAME"` として挿入される**。読みにくいうえ、貼り付けた SQL の他の部分と綴りが揃わない。

**② 修飾すると候補が消える。** `completeFromSchema` は `level.children[name]` の完全一致で階層を降りる。`koduchi.` と小文字で打つと `children["koduchi"]` が無く、その場で `null` を返す。絞り込みが弱いのではなく**候補が 1 件も出ない**。同じ経路を通る `FROM` 句の別名も、解決先の名前が一致しなければ落ちる。

加えて、渡していた表はトップレベルに**全スキーマ名と全スキーマの非修飾オブジェクト名**を積み、名前の衝突を「先に現れたスキーマ優先」で解いていた。他人のスキーマの表が自分の表を隠しうる。

`PLSQL` 方言そのものにも問題がある。`doubleQuotedStrings: true` が立っており、`"MyTable"` が**文字列として**解析される。Oracle で `"..."` は常に引用符付きの識別子であり、文字列は `'...'` である。

## 決定

### 識別子の候補は自前の補完ソースが出す

`schemaCompletionSource` は使わない。構文木を自分で読み、候補も自分で組み立てる。`lang-sql` へはキーワードの補完だけを任せる（こちらは大文字小文字の問題を持たない）。置き場所は次のとおり。

| ファイル                                | 役割                                                   |
| --------------------------------------- | ------------------------------------------------------ |
| `src/components/editor/dialect.ts`      | `PLSQL` から二重引用符の扱いだけを変えた方言           |
| `src/components/editor/catalog.ts`      | 畳んだ名前で引ける表。`SchemaNode` から組み立てる       |
| `src/components/editor/identifiers.ts`  | 挿入する綴りと引用の要否を決める純粋関数               |
| `src/components/editor/sqlCompletion.ts`| 構文木を読み、カタログを引き、候補を組み立てる         |

### 名前の解決は大文字小文字を区別しない

カタログの鍵は `name.toUpperCase()` に畳む。Oracle は無引用の識別子を大文字へ畳んで解釈するため、利用者がどの綴りで打っても同じものが引ける。`"abc"` として作られた小文字の名前と `ABC` は本来別物だが、補完では区別せず先に登録されたほうを採る。

### 挿入する綴りは接続ごとの設定にする

`SavedConnection` に `completion.identifierCase` を足し、`connections.toml` に保存する（[[0004-認証情報と接続設定の保存先]]）。選択肢は**小文字 / 大文字 / カタログのまま**の 3 つで、既定は「カタログのまま」。置き場所は接続フォームの「読み取り専用」「自動コミット」と同じ並びである。

アプリ全体の設定（`settings.toml`）にしないのは、Oracle はカタログが大文字・PostgreSQL は小文字と、データベースによって自然な綴りが逆だからである。[[0012-トランザクション制御]] が自動コミットを接続の項目にしたのと同じ理由である。

Oracle では「大文字」と「カタログのまま」が同じ結果になる。3 つに分けてあるのは、名前を小文字で持つ PostgreSQL を足したときに意味が分かれるためである。

### 引用は必要なときだけ、そのときは綴りを変えない

**カタログの名前が引用符なしで書けるなら指定された綴りへ変える。書けないならカタログの綴りのまま引用符で囲む。** 引用符なしで書けるのは、`/^[A-Z][A-Z0-9_$#]*$/` に通り、かつ Oracle の予約語でない名前である。

- `ORDER_ITEMS` → 小文字を選べば `order_items`（無引用でも `ORDER_ITEMS` に解決される）
- `MyTable` → 小文字を選んでも `"MyTable"`（小文字化すると別の名前になる）
- `SELECT` → 全大文字だが予約語なので `"SELECT"`

利用者が自分で `"` を打った位置では、綴りを変えずカタログのままの名前を引用符ごと出す。わざわざ引用したのだから、その綴りが望まれている。

### 非修飾で出す表は既定スキーマのものだけ

接続したユーザーと同じ名前のスキーマを既定スキーマとし、修飾のない位置にはそのスキーマのオブジェクトだけを出す。他のスキーマの表は `SCHEMA.` で修飾してから出す。

ただし利用者が**自分で打った**非修飾の名前を解決するときは、既定スキーマを先に見たうえで、無ければ全スキーマを取得順に探す。候補として並べることと、打たれた名前を解釈することは別である。

### `FROM` 句の表の列を非修飾で出す

文の `FROM` 句を走査して表と別名を集め、その列を修飾なしの位置へ並べる。`select ` まで打った時点で列名が出るかどうかが、補完の使い勝手をいちばん左右する。並び順は上から**`FROM` 句の列 → 別名 → 既定スキーマのオブジェクト → スキーマ名**とする。

走査は文の直接の子だけを見る。副問い合わせは括弧の中に入るため引っ掛からない。`ON` / `USING` の後ろは条件式であり、そこに出てくる識別子を表と取り違えない。

### 二重引用符は識別子として解析する

`SQLDialect.define({ ...PLSQL.spec, doubleQuotedStrings: false })` で方言を作り直す。`"MyTable".` と書いたときに列の補完が働くようにするためであり、色付けも正しくなる。`q'[...]'` の扱いは `PLSQL` から引き継ぐ。

**方言を定義し直すと `LRLanguage` も新しくなる。** 補完ソースを言語データへ足すときは、`PLSQL.language` ではなくこの方言の `language` に足すこと。

## 理由

- **`lang-sql` の補完ソースをラップして直すことはできない。** 引用の判定も階層の解決も `completeFromSchema` の中に閉じており、外から差し込む口が無い。名前空間に小文字の別名を足せば ② だけは緩和できるが、候補一覧に同じ名前が二重に並ぶ。150 行ほどを自分で持つほうが安い。
- **綴りを変えるより引用するほうを安全側に倒す**のは、壊れた SQL を静かに作らないためである。`"MyTable"` を `mytable` と挿入すれば `ORA-00942` になる。引用符が残るのは見た目の問題だが、名前が変わるのは誤りである。
- **既定を「カタログのまま」にする**のは、今の挙動（大文字で挿入される）と見た目が変わらない側だからである。綴りを変えたい利用者が明示的に選ぶ。

## 却下した案

**`caseInsensitiveIdentifiers: true` の方言を定義して済ませる**: ① の引用符は消えるが、`nameCompletion` は綴りを変えないため出力スタイルは選べないままである。② も直らない。

**カタログに小文字の別名を登録する**: `KODUCHI` と `koduchi` の両方を鍵にすれば ② は緩和できるが、トップレベルの候補一覧に同じスキーマが 2 回並ぶ。

**出力スタイルをアプリ全体の設定にする**: Oracle と PostgreSQL で自然な綴りが逆であり、1 つの値では両方を満たせない。

**キーワードの綴りも同じ設定で切り替える**: 今は小文字固定（`upperCaseKeywords: false`）のままにした。識別子とキーワードは別の話であり、まとめて 1 つの設定にすると片方を変えたいときに困る。要望が出たら項目を足す。

**列のソートと同じく、補完に出す候補を全スキーマぶん並べる**: 数千件の候補は絞り込みの役に立たない。既定スキーマに絞る代わりに、修飾すれば必ず引けるようにした。

**明示的に補完を開くキーを足す**: `⌃Space` は macOS の入力ソース切替と衝突しやすいが、キーバインドの表（`adr/README.md`）に新しい割り当てを増やす話になるため、この ADR では扱わない。

## 結果

- `@lezer/common` を直接の依存に足した。構文木の節点の型（`SyntaxNode`）を使うためである。
- `stores/schema.ts` の `buildCompletionSchema` は消えた。補完の元を組み立てるのはエディタ側の関心であり、ストアはスキーマツリーの状態だけを持つ。
- `ActiveConnection` に `completion` が載った。Rust へ渡さない値であるため `params` とは分けてある。スキーマフィルタと違って接続中に変わらないため、変える口はストアに持たない。
- Rust 側は `CompletionSettings` を `connections.toml` の往復のためだけに持つ。値の意味を解釈するのはフロントエンドである。
- `connections.toml` に `completion` を持たない古いファイルは、`#[serde(default)]` で「カタログのまま」として読める。
- **文に依らない候補（既定スキーマのオブジェクトとスキーマ名）は補完ソースの中で 1 度だけ作って覚える。** カタログと綴りだけで決まり、打っている文には依らないためである。覚えないと、既定スキーマに 2 万のオブジェクトがある環境で 1 回あたり約 2 ms かかる。`FROM` 句から取る候補は文ごとに変わるため毎回作るが、数は高々「結合した表の列の合計」であり大きくならない。

### 測った値

既定スキーマ 2 万表・他 29 スキーマ各 200 表・全表 20 列（列は計 52 万）で測った目安。

| | 新（自前） | 旧（`lang-sql`） |
| --- | --- | --- |
| 補完の元の組み立て（接続ごとに 1 度） | 31 ms | 17 ms + 候補の構築 1,049 ms |
| 補完 1 回（非修飾） | 0.15 ms | 0.001 ms |
| 補完 1 回（修飾あり） | 0.02 ms | 0.002 ms |

旧実装は候補を**先に全部**作るため 1 度きりの構築が 1 秒かかり、その間 UI が止まる。新実装はそれを打鍵側へ薄く分散させた形であり、1 回あたりは 1 フレーム（16.7 ms）の 1 % 程度に収まる。`validFor` により、候補が出ている間の絞り込みでは補完ソースを呼び直さない。
