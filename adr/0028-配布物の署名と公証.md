# ADR 0028: 配布物の署名と公証

- ステータス: 承認
- 日付: 2026-09-08

## 状況

[[0011-cicdとリリース配布]] は「Apple の Developer Program に加入していない」ことを前提に、**Developer ID では署名せず ad-hoc 署名（`signingIdentity: "-"`）に留める**と決めた。利用者は初回起動で「開発元を確認できません」の警告を受け、システム設定から開く手順を README に書いてある。

Developer Program に加入した。前提が変わったので、この 1 点を覆す。

決めるべきことは 4 つある。

1. 署名だけで足りるか、公証（notarization）まで行うか
2. 公証の認証をどうするか
3. `tauri.conf.json` の `signingIdentity` をどうするか
4. Tauri がどこまでやってくれるのか

## 決定

### 1. 署名・公証・staple まで行う

**署名だけでは足りない。**ダウンロードした dmg には検疫属性が付き、公証の証跡が無ければ Gatekeeper に止められる。それでは README の回避手順を消せず、加入した意味が薄い。

**staple まで行う。**公証の結果はアップルのサーバにも記録されるが、staple しておけばオフラインでも検証できる。

### 2. 公証は App Store Connect API キーで行う

`APPLE_ID` と App 固有パスワードでも公証できるが、**個人の Apple ID に紐づく資格情報を CI に置くことになる。**API キーなら次の点で優る。

- 失効させられる。漏れたときに Apple ID そのものを守れる。
- 二段階認証の影響を受けない。
- 権限を「Developer」に絞れる。

secret は 5 つ、variable は 1 つである。

| 名前                         | 種別     | 中身                                    |
| ---------------------------- | -------- | --------------------------------------- |
| `APPLE_CERTIFICATE`          | secret   | Developer ID Application の `.p12`（base64） |
| `APPLE_CERTIFICATE_PASSWORD` | secret   | `.p12` に付けたパスワード               |
| `APPLE_API_KEY`              | secret   | App Store Connect API の Key ID         |
| `APPLE_API_ISSUER`           | secret   | 同 Issuer ID                            |
| `APPLE_API_KEY_P8`           | secret   | 同 `.p8` 秘密鍵（base64）               |
| `APPLE_TEAM_ID`              | variable | Team ID。秘密ではない。署名の照合に使う |

**`.p8` はファイルのパスで渡す決まりである**（`notarytool` の `--key` も Tauri の `APPLE_API_KEY_PATH` も、中身ではなくパスを取る）。そのためワークフローは secret から一時領域へ書き出し、`if: always()` で必ず消す。

用意の手順は `scripts/setup-signing.sh` が案内する。

### 3. `tauri.conf.json` に `signingIdentity` を書かない

**`"-"` のままにはできない。**tauri-bundler のソースを読んで確かめた 2 つの理由による。

- `sign.rs` の `keychain()` は、`APPLE_CERTIFICATE` があるとき証明書から識別名を取り、**設定に識別名があればそれが証明書名の部分文字列かを検査して、外れていればエラーにする。**`"-"` は通らない。
- `dmg/mod.rs` は識別名が `"-"` のとき **dmg の署名を丸ごと飛ばす**（自己署名の dmg を避けるため）。気づかないまま未署名の dmg を配ることになる。

識別名を書かなければ `APPLE_CERTIFICATE` から取られる。**書かないことを `src-tauri/tests/entitlements.rs` が見張る。**

**代償として、手元の `bun run tauri build` はバンドルに署名しなくなる。**[[0011-cicdとリリース配布]] は「Apple Silicon では未署名のバイナリが動かない」ことを理由に ad-hoc 署名を選んでいたが、実行ファイルそのものはリンカが ad-hoc 署名するため起動する。手元のビルドに署名が要る場面は無い（配るのは CI の成果物だけである）。

### 4. 公証は dmg を 1 回だけ提出する

**Tauri が公証と staple をするのは `.app` だけである。**バンドラのソースで確かめた。

- `macos/app.rs` — 署名したあと `notarize()` を呼び、staple までする。
- `macos/dmg/mod.rs` — **署名しかしない。**公証も staple もしない。

利用者が受け取るのは dmg である。dmg 自身に証跡が無ければ Gatekeeper に止められるので、ビルドのあとに `notarytool submit --wait` と `stapler staple` を自前で当てる。

**そのうえで、Tauri 側の公証は使わない。**`APPLE_API_KEY` / `APPLE_API_ISSUER` をビルドの手順へ渡さないことでそうする。理由は 2 つある。

1. **成果が捨てられる。**`--bundles dmg` は dmg を作り終えた時点で `bundle/macos/*.app` を消す。公証と staple を済ませた `.app` はそこで消え、残るのは dmg だけである。
2. **notary への提出が二重になる。**dmg を提出すれば、notary が中身を展開して `.app` の署名まで検証・記録する。提出は 1 回で足りる。

実測（v0.1.0 のリリース、2026-09-08）: `.app` の公証を含むビルドが **49 分**、dmg の公証と staple が **24 秒**。前者を落とすだけでリリースの所要時間が 1/10 以下になる。

staple が付くのは dmg だけであり、中の `.app` には付かない。**dmg から取り出した `.app` を単独で配り直すなら `.app` 側の公証と staple も要る**が、小槌は dmg でしか配らない。

### 5. 配る前に確かめる

「ビルドが緑だった」では署名も公証も確かめたことにならない。**下書きリリースを作る前に**次を検査し、1 つでも欠けたら落とす。

- `codesign --verify --strict --deep`
- `TeamIdentifier` が `vars.APPLE_TEAM_ID` と一致すること
- `flags` に `runtime` があること（ハードンドランタイム）
- `stapler validate` が dmg で通ること（証跡が付くのは dmg だけである）
- `spctl` の判定が `.app`（`-t exec`）と dmg（`-t open`）の両方で通ること

**確かめる相手は dmg をマウントして取り出した `.app` である。**`--bundles dmg` はビルドの最後に `bundle/macos/*.app` を消すため、手元に残った `.app` は無い。仮に残っていても、見るべきは**配る dmg の中身**であって、ビルドの副産物ではない。

## 理由

- **エンタイトルメントは 2 つとも残すが、理由が変わる。**[[0011-cicdとリリース配布]] は「ad-hoc 署名には Team ID が無いから」ライブラリ検証を切るとした。いまは Developer ID で署名しており Team ID がある。それでも切るのは、**Instant Client が Oracle の別の Team ID で署名されている**ためである（[[0001-oracle接続方式]]）。ハードンドランタイムのライブラリ検証は、正規の署名であっても自分と違う Team ID の dylib を弾く。公証はこのエンタイトルメントを許している。
- **検査を配布の手前に置く**のは、イミュータブルリリースが公開後の訂正を許さないためである（[[0011-cicdとリリース配布]]）。署名や公証の欠落は、dmg を開くまで目に見えない。
- **秘密をログに出さない。**`.p8` のパスは環境変数に置くが、パスは秘密ではない。中身は base64 のまま secret に留め、書き出したファイルは必ず消す。

## 却下した案

**Apple ID と App 固有パスワードで公証する**: 手数は少ないが、個人の Apple ID に紐づく資格情報を CI に置くことになる。失効の粒度も粗い。

**`tauri-action` に移る**: 署名と公証の環境変数を渡すだけで済むようになるが、[[0011-cicdとリリース配布]] が自前のワークフローを選んだ理由（下書きの作り直し・タグ検査・公開を人間が押す運用）は変わっていない。移る値打ちが無い。

**`signingIdentity` に識別名を書く**: 動きはするが、氏名と Team ID をリポジトリに焼き付けることになり、証明書を入れ替えるたびに設定も直すことになる。`APPLE_CERTIFICATE` から取れるものを二重に持たない。

**dmg の公証を省き、`.app` の staple だけで済ませる**: 利用者が dmg を開く時点で Gatekeeper に止められる。中の `.app` を取り出せば動くが、それは README の回避手順が別の形で残るだけである。

**手元のビルドでも Developer ID で署名する**: 証明書を手元に置き続けることになり、CI と手元で成果物の出どころが分かれる。配るのは CI の成果物だけと決めている。

## 結果

- `tauri.conf.json` から `signingIdentity` が消えた。**手元のビルドはバンドルに署名しない。**
- `release.yml` に、API キーの書き出し・署名つきビルド・dmg の公証と staple・検査・鍵の後始末の 5 手順が増えた。
- `scripts/setup-signing.sh` が資格情報の用意を案内する。`.cer` をダブルクリックすると System キーチェーンに入り、ログインキーチェーンにある秘密鍵と対にならない（`security find-identity` が 0 を返す）ため、**取り込み先を明示して入れる。**中間証明書（Developer ID Certification Authority G2）も入れる。
- README から「開発元を確認できません」の回避手順を消した。
- [[0011-cicdとリリース配布]] の「署名しない」という決定はこの ADR が覆した。それ以外（ワークフローの構成・タグの検査・下書きで止めること・aarch64 のみ）は変えていない。
