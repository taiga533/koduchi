# ADR 0023: タブの並べ替えと閉じる

- ステータス: 承認
- 日付: 2026-09-08

## 状況

エディタのタブ帯（デザイン 3a の 34px の帯）には 2 つの穴がある。

### 未保存のタブが閉じられない

`TabBar.tsx` はタブの右端で、未保存の `●` 印と `✕` の閉じるボタンを**排他に**出していた。

```tsx
{tab.dirty ? <span aria-label="未保存" /> : <button aria-label="… を閉じる" />}
```

`dirty` になった時点で閉じるボタンが消える。起動直後の `無題-1.sql` は何か打てば `dirty` になるため、以後どうやっても閉じられない。`⌘W` は生きているが、ボタンが無い以上そこには辿り着けない利用者が居る。

排他にしたのは場所の節約であって、そういう仕様ではない。[[0005-クエリ履歴とセッション復元のsqlite]] は「未保存の状態でタブを閉じたりアプリを終了したりすることが前提の設計である」と書いており、**閉じられることは初めから前提だった**。

さらにテーブル定義ビューのタブ化（ADR 0022、別途進行中）で、定義のタブが同じ並びに混ざる。定義タブは `content` も `dirty` も持たないため、閉じるボタンの有無を `dirty` で分ける作りはそこでも破綻する。

### タブを並べ替えられない

タブは開いた順に並ぶだけで、動かせない。同じ接続で 5 枚も 6 枚も開くのは日常であり、関係する 2 枚を隣に置きたくなる。並びは `session_tab.position` としてセッションへ保存され再起動で復元される（[[0005-クエリ履歴とセッション復元のsqlite]]）ため、一度並べた順は残る。

決めるべきことは 5 つある。

1. 未保存の印と閉じるボタンをどう同居させるか
2. 未保存のタブを閉じるときに確認を挟むか
3. 最後の 1 枚を閉じたときにどうするか
4. 並べ替えの入力をどう扱うか（Pointer Events か HTML5 drag and drop か、ライブラリを足すか）
5. キーボードでも並べ替えられるか

## 決定

### 印は名前の左、閉じるボタンは常に右に出す

`● 無題-1.sql ✕` の形にする。**閉じるボタンはタブの種類にも `dirty` にもよらず必ず出す。**印が無いときも 7px の場所だけは空けておき、打ち始めた瞬間にタブの幅が動かないようにする。

- 未保存かどうかは**ホバーしなくても**一目で分かる。デザインが `●` に負わせていた役目はそのまま残る。
- 閉じるボタンの有無が状態に依存しない。`dirty` を持たない定義タブが並びに混ざっても、判定が要らない。
- 閉じる直前まで `●` が見えている。次に述べる確認を出すかどうかの判断材料が、押す瞬間に消えない。

### 未保存のタブを閉じるときは、失うものがあるときだけ確認する

`dirty` かつ**本文が空白だけではない**タブを閉じるときに限り、「保存していない変更があります。閉じると失われます。」を出す。空のタブと保存済みのタブは今までどおり 1 押しで閉じる。

[[0005-クエリ履歴とセッション復元のsqlite]] は未保存のバッファを SQLite へ保存し、再起動でタブごと復元すると決めた。ただしそれが効くのは**閉じずにアプリを終了したとき**だけである。セッションへ書き出すのはその時点で開いているタブだけ（`selectSession`）なので、**タブを閉じた瞬間にその内容はセッションからも消える。**書きかけの SQL は本当に失われ、`⌘Z` でも再起動でも戻らない。

同じ ADR が「保存していないタブを終了時に破棄する（確認ダイアログを出す）」を却下しているが、あれは**終了時に全タブをまとめて**尋ねる話である。ここで尋ねるのは、利用者が名指しで 1 枚を閉じたときだけであり、`●` を残す設計とも噛み合う。

**尋ねるのを「失うものがあるとき」に絞る**のは、確認がただの手数になった瞬間に読まずに押されるようになるからである。`⌘T` で開いてすぐ閉じるタブや、ツリーから名前を 1 つ挿入して気が変わったタブまで引き止める値打ちは無い。判定は `src/components/editor/closing.ts` の `needsCloseConfirmation` という純粋な関数に寄せてある。

**関所は `App.tsx` の `closeTabAndRelease` 1 つである。**タブの `✕` も `⌘W` も既にここを通っており（開いたままのカーソルを手放すため。[[0003-結果セットのカーソル保持と接続プール]]）、確認もここに置けば経路が増えても漏れない。[[0012-トランザクション制御]] が未コミットの関所を `resolvePendingTransaction` 1 箇所に置いたのと同じ形である。

確認そのものは差し替えられる境界にした（`setCloseTabDialog`）。ネイティブのダイアログは jsdom では開けないため、テストはこの境界を差し替えて確かめる（[[0010-テストとリンタの構成]]・`transaction/pendingChanges.ts` と同じ考え方）。

### 最後の 1 枚を閉じたら新しい空のタブが開く（今のまま）

`closeTab` は残りが 0 枚になったら新しい空のタブを作る。**これは変えない。**タブが 1 枚も無いエディタは、`⌘T` を知らないと何も打てない行き止まりである。結果ペインもステータスバーも「今のタブ」を前提にしている。

### 並べ替えは Pointer Events で行い、ライブラリは足さない

`Splitter.tsx` が採った作法にそのまま倣う。`pointerdown` / `pointermove` / `pointerup` と `setPointerCapture` を使い、`mousemove` を `window` に貼らない。ドラッグ中は `document.body` に `user-select: none` を当てる。4px 動かすまでは掴んだと見なさず、ただの押し下げとして扱う。

**HTML5 の drag and drop API は使わない。**ドラッグ中の見た目がブラウザ任せになり、Tauri の WebView は WebKit なので `dragover` / `dropEffect` の癖をこちらで見切れない。加えて `Splitter` が既に Pointer Events で同じ形の操作を作っており、アプリの中に作法を 2 つ持ちたくない。

**`dnd-kit` などのライブラリも足さない。**必要なのは「横 1 列・数枚・入れ替えるだけ」であり、実際に書いた量は純粋な関数 2 つ（`moveItem` / `dropIndex`）と `TabBar` の中の 60 行ほどである。この ADR 群は tnsnames パーサ（[[0006-tnsnames解決を自前パースで行う]]）も SQL の文切り出しも補完ソース（[[0013-補完の候補生成と識別子の出力スタイル]]）も自前で書いてきた。ここで依存を増やすと、WebKit での挙動を追う相手が 1 つ増える。

**落とす位置の計算は純粋な関数に寄せる**（`src/components/editor/tabOrder.ts`）。

- `moveItem(items, from, to)` — 何番目を何番目へ動かしたら並びはどうなるか
- `dropIndex(rects, draggingId, pointerX)` — 今のポインタ位置はどの位置へ落とすことになるか

判定は**隣のタブの中心を越えたとき**に入れ替える。タブの幅は名前の長さで変わるため、中心は実測した位置から測る。端まで一息に動かしたときに途中のタブを飛ばして落とせるよう、掴んだ位置から遠いほうから順に見る。入れ替えはドラッグ中に随時行い（`moveTab`）、落とした時点でまとめて動かすことはしない。動いていく様子がそのまま結果になる。

閉じるボタンの上から始めた動きでは掴まない。判定は「押した場所が `data-tab-action` を持つ要素の中か」だけで、[[0020-スキーマツリーからの操作]] の `data-row-action` と同じ形である。

### `⌥←` / `⌥→` で並べ替える

タブ帯の中でしか意味を持たないため、`App.tsx` ではなく `TabBar` の `keydown` に置く（`CLAUDE.md` の「キーバインドの置き場所」）。ペインの区切りの矢印キー、スキーマツリーの `↑` / `↓`（[[0020-スキーマツリーからの操作]]）と同じ扱いであり、ADR README のキーバインド表には載せない。

`⌥` を選んだのは、`⌘` 側が `⌘T` / `⌘W` で埋まっており、`⌘K` と `⌘I` が予約済み（[[0018-保存済みクエリとコマンドパレット]]）だからである。焦点がタブにあるときだけ効くので、エディタの中の `⌥←`（単語単位の移動）とは食い合わない。

焦点は動かしたタブに残る。React はキー付きの子を並べ替えるときに DOM の要素そのものを動かすため、`⌥→` を続けて打てばタブは端まで歩いていく。roving tabindex は入れない。タブは数枚であり、仮想スクロールもしていない。

### 並べ替えた順序は今の仕組みのまま保存される

**Rust 側は触っていない。**`session_tab` は初めから `position` 列を持ち、`save_session` は配列の順に、`load_session` は `order by position` で読み書きしている。`selectSession` はストアのタブ配列をそのまま書き出すので、並べ替えた順序は何も足さずにセッションへ乗る。列を足していないため、古い `history.sqlite3` を開いても落ちない。

### 引き剥がしとの境目

ADR README の「ペインの大きさ」節は「ペインの分割・入れ替え・タブの引き剥がしは行わない」と決めている。**この決定は覆さない。**

そこで断ったのは**ウィンドウのレイアウトを利用者が組み替えること**である。1 接続 = 1 ウィンドウ（[[0009-ウィンドウモデルとタイトルバー]]）という土台の上で、ペインを割ったりタブを別ウィンドウへ引き出したりすれば、「今どの接続で何を見ているか」がウィンドウの見た目から読めなくなる。結果セットのカーソルは接続 1 本につき高々 1 つであり（[[0003-結果セットのカーソル保持と接続プール]]）、同じ接続の結果を 2 枚並べることもできない。

**タブ帯の中で順序を入れ替えることは、そのどれにも触れない。**タブは 1 つの帯の中に留まり、ウィンドウは増えず、器の数も形も変わらない。動くのは並びだけであり、`session_tab.position` という既にある値の書き換えである。同じ理由で**タブを別ウィンドウへ引き出す操作は作らない**。ドラッグの落とし先はタブ帯の中だけであり、帯の外へ出しても何も起きない。

## 理由

- **バグの正体は「排他にしたこと」そのものである。**印とボタンのどちらを出すかを状態で決める作りは、状態が増えるたびに壊れる。定義タブ（ADR 0022）が来る前に、両方を常に置く形へ直しておくのが安い。
- **確認を「失うものがあるときだけ」に絞った**のは、確認の値打ちがその頻度に反比例するからである。毎回出る確認は読まれない。
- **並べ替えの計算を純粋な関数に切り出した**のは、境目（端から端へ、同じ位置へ落とす、幅の違うタブ）が描画抜きで確かめられるからである。`selection.ts` / `columnSizing.ts` と同じ形である。
- **入力の作法を `Splitter` に揃えた**のは、ポインタの捕捉と `user-select` の扱いを 2 通り持たないためである。

## 却下した案

**ホバーしたときだけ `●` を `✕` に入れ替える**（VS Code の作法）: 帯は狭く保てるが、閉じるボタンが見えない状態が既定になる。キーボードだけで辿る利用者には焦点を当てるまで存在しないのと同じであり、触れる面が指の太さより小さい環境では押しどころが分からない。加えて**閉じる直前に未保存の印が消える**。確認を出すかどうかの手掛かりが、いちばん要る瞬間に無くなる。

**`●` を閉じるボタンの中に描き、押すと閉じる**: 場所は最も小さく済むが、「印」と「押しどころ」が同じものになる。未保存を確かめようと目を留めた場所が閉じるボタンだった、という誤爆を招く。

**印を出さず、タブ名を斜体や色で未保存と示す**: 場所は空くが、`●` はデザイン 3a の指定である（[[0005-クエリ履歴とセッション復元のsqlite]] が前提にしている）。読み替える理由が無い。

**未保存のタブを閉じるときは必ず確認する**: 漏れは無いが、`⌘T` で開いて 1 文字打っただけのタブでも止められる。確認が手数になれば読まずに押されるようになり、本当に守りたい場面で効かなくなる。

**確認せず、閉じたタブを `⇧⌘T` で開き直せるようにする**: 手を止めずに取り返せる形であり筋は良いが、閉じたタブを何枚ぶん覚えるか・接続を切り替えたときどうするか・セッションへ持ち越すかを新たに決めることになる。今回の穴は「閉じられない」ことであり、そこを直すために持ち込む決定としては大きい。将来入れるなら、確認と入れ替えるのではなく重ねられる。

**HTML5 の drag and drop API を使う**: `dragstart` / `dragover` / `drop` だけで書けて手数は少ないが、ドラッグ中の見た目（ドラッグ画像・カーソル・落とし先の印）がブラウザ任せになる。Tauri の WebView は WebKit であり、`setDragImage` の効き方も `dragover` の発火頻度も他のエンジンと違う。`Splitter` で既に Pointer Events の作法を持っている以上、読みにくいほうを新しく持ち込む理由が無い。

**`dnd-kit` などの並べ替えライブラリを入れる**: キーボード操作もスクリーンリーダーへの通知も付いてくるが、横 1 列を入れ替えるだけの用に対して API と依存が重い。自前で書いた量は純粋な関数 2 つと 60 行ほどであり、WebKit で挙動を追う相手を増やす代償に見合わない。

**落とした時点でまとめて動かし、ドラッグ中は挿入位置の線だけ出す**: 実装は素直だが、線がどの隙間を指しているのかは幅の違うタブが並ぶと読みにくい。動いていく様子がそのまま結果になるほうが、確かめる手間が要らない。

**タブを帯の外へ落としたら新しいウィンドウにする**: ADR README の「タブの引き剥がしは行わない」に真っ向から反する。1 接続 = 1 ウィンドウ（[[0009-ウィンドウモデルとタイトルバー]]）が崩れ、結果セットのカーソルが 1 本しかない（[[0003-結果セットのカーソル保持と接続プール]]）以上、引き剥がした先で結果を見ることもできない。

**並べ替えに `⌘⇧[` / `⌘⇧]` を割り当てる**（ブラウザの作法）: 一般的だが、あれは多くのブラウザで**タブの切り替え**であって並べ替えではない。同じ打鍵で別のことが起きるほうが分かりにくい。

**タブ帯に `role="tablist"` / `role="tab"` を与える**: 支援技術への伝わりは良くなるが、`tablist` は `←` / `→` で選択が動くことを前提にした役割であり、そこへ `⌥←` の並べ替えを重ねると打鍵の意味が 2 段になる。役割の整理は入れ替えの話とは別に扱う。

## 結果

- `src/components/editor/tabOrder.ts` が増えた。`moveItem` と `dropIndex` の 2 つの純粋な関数である。並べ替えの境目はここだけで確かめられる。
- `src/components/editor/closing.ts` が増えた。`needsCloseConfirmation` の判定と、差し替えられる確認の境界（`setCloseTabDialog`）である。
- `tab` ストアに `moveTab(id, toIndex)` が増えた。動かなかったときは同じ配列を返し、参照が変わらないので再描画も起きない。`selectTab` も、既に選ばれているタブでは状態を作り直さないようにした。
- `TabBar` がタブの器に `data-tab-id` を持つようになった。並べ替えの判定に横位置の実測が要るためである。閉じるボタンには `data-tab-action` が付き、そこから始めた動きでは掴まない。
- `App.tsx` の `closeTabAndRelease` が非同期になった。確認を挟むためである。`⌘W` の側は `void` で呼ぶ。
- **Rust 側は触っていない。**`session_tab.position` が初めから並び順を持っており、列は 1 つも増えていない。古い `history.sqlite3` はそのまま読める。
- テストは、未保存のタブに閉じるボタンが出ること（再発を止める直の検査）・`dirty` を持たないタブでも出ること・ドラッグとキーボードでの並べ替え・確認の分岐・並べ替えた順序が Rust 側で往復すること、を見ている。jsdom はレイアウトを行わず `getBoundingClientRect` が 0 を返すため、タブの横位置だけをテスト側で与える。
