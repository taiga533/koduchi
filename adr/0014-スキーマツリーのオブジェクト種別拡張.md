# ADR 0014: スキーマツリーのオブジェクト種別の拡張

- ステータス: 承認
- 日付: 2026-09-08

## 状況

スキーマツリー（[[0007-スキーマ取得の段階的ロード]]）に出る種別は 7 つ — テーブル / ビュー / マテリアライズドビュー / ファンクション / プロシージャ / パッケージ / シーケンス — しかない。索引・制約・トリガー・シノニム・型・DB link は 1 件も出ない。

出ないと困る場面ははっきりしている。「この表にどんな索引が付いているか」「この名前はシノニムなのか実体なのか」「更新が勝手に書き換わるのはトリガーのせいではないか」は、SQL を書く前に確かめたいことばかりである。今はそのたびに `ALL_INDEXES` を手で引くことになる。

一方で、種別を足すと 1 スキーマあたりのオブジェクト数が跳ね上がる。索引は表と同程度かそれ以上の数があり、シノニムは所有者を `PUBLIC` まで広げると 1 データベースで数万件に達する。[[0007-スキーマ取得の段階的ロード]] は「段階 1 でオブジェクト名まで取り、数千行・1〜2 秒」という見積もりの上に立っており、この前提を壊さずに種別を増やす必要がある。

Oracle 側の事情も一様ではない。

- 索引・トリガー・シノニム・型は `ALL_OBJECTS` に `OBJECT_TYPE` として並ぶ。
- **DB link は `ALL_OBJECTS` の所有者の考え方と噛み合わない。** 列挙元は `ALL_DB_LINKS` であり、所有者は `PUBLIC` かユーザー名のどちらかになる。
- **制約は `ALL_OBJECTS` に出てこない。** `ALL_CONSTRAINTS` を別に引く必要がある。
- `ALL_OBJECTS` から素直に索引を取ると、主キーや一意制約や LOB のために自動生成された `SYS_C0012345` / `SYS_IL0000123C00004$$` が並ぶ。利用者が付けた名前ではない。

## 決定

### 種別を 5 つ足して 12 種別にする

`ObjectKind` に **索引 / トリガー / シノニム / 型 / DB link** を足す。`has_columns()` が真になる種別は変えない（テーブル・ビュー・マテリアライズドビュー）。列を持つのは `ALL_TAB_COLUMNS` で引ける 3 つだけである。シノニムは指す先が列を持つが、シノニム名では `ALL_TAB_COLUMNS` を引けないため含めない。

`PACKAGE BODY` と `TYPE BODY` は落とす。仕様と同じ名前で 2 行並ぶだけで、区別が付かない。

### 制約は今回入れない

**制約はツリーに出さない。** 理由は 3 つある。

1. **名前の大半が意味を持たない。** 名前を明示せずに書かれた `NOT NULL` や主キーの制約は `SYS_C0012345` になる。実際のデータベースでは制約の過半がこれであり、並べても読めない。
2. **置き場所がツリーの形と合わない。** 制約はスキーマ直下の存在ではなく表に属する。ツリーへ正しく置くなら「スキーマ → テーブル → 制約 / 列」という段が要り、今の「スキーマ → 種別の束 → オブジェクト → 列」とは別の枝分かれになる。テーブル定義ビュー（今は器のみ。`adr/README.md` の機能スコープ）が開くようになれば、制約はそちらの持ち物である。
3. **段階が合わない。** `ALL_CONSTRAINTS` は `ALL_TAB_COLUMNS` と同じくらい行数が多く、段階 1 では取れない。取るなら段階 2 と同じスキーマ単位の流し込みになり、列と制約で 2 系統を並行して回すことになる。

したがって制約は、テーブル定義ビューを作る波で、そのビューの中に置く。ツリーへぶら下げる案は採らない。

### 列挙元は 3 つに分ける

段階 1 は `ALL_USERS` に加えて次の 3 つを引く。

| ビュー         | 取るもの                                                                     |
| -------------- | ---------------------------------------------------------------------------- |
| `ALL_OBJECTS`  | 表・ビュー・マテビュー・トリガー・順序・シノニム・型・関数・手続（9 種別）    |
| `ALL_INDEXES`  | 索引。`GENERATED = 'N'` のものだけ                                           |
| `ALL_DB_LINKS` | DB link                                                                      |

索引を `ALL_OBJECTS` ではなく `ALL_INDEXES` から取るのは、`GENERATED` 列が `ALL_OBJECTS` に無いためである。自動生成の索引を落とすにはこの列が要る。

**所有者が `PUBLIC` のオブジェクトは列挙しない。** `PUBLIC` は `ALL_USERS` に載らない擬似的な所有者であり、そこに公開シノニムが数万件ぶら下がる。`ALL_OBJECTS` と `ALL_DB_LINKS` の両方に `owner <> 'PUBLIC'` を付ける。

列挙元が分かれた結果、スキーマの中の並びはビューごとのかたまりになる。Rust 側で名前順（同名は種別順）に整え直してから返す。

### ツリーは種別ごとに束ねる

スキーマとオブジェクトの間に**種別の束**を 1 段挟む。

```
KODUCHI  142
  テーブル   12
    USERS
      USER_ID  NUMBER(12)
  索引       38
  トリガー    3
```

束ねる理由は行数である。束が無いと、索引まで載せたスキーマを開いた瞬間に数千行が平らに並び、テーブルがどこにあるか分からなくなる。束ねてあれば、スキーマを開いて増える行は**種別の数（高々 12）**に収まる。仮想スクロールに載せる行の総数も同じ理屈で抑えられる。

束の並びは `OBJECT_KIND_ORDER`（Rust の `ObjectKind` の宣言順と同じ）で固定し、1 件も無い種別は束ごと出さない。

**絞り込み中は束を既定で開く。** 当たったオブジェクトへ辿り着くのに束をいちいち開かせるのでは、検索の意味が薄れる。束を自分で閉じたときはその指定が勝つ（そのために `toggle` は開閉の値を受け取れるようにした）。

### 種別ごとの表示可否をフィルタに足す

`SchemaFilter` に `kinds`（種別 → 真偽の表）を足し、絞り込みメニューへ 12 個のチェックを並べる。既定はすべて真。設定は他の 2 条件と同じく `connections.toml` の接続エントリへ保存する（[[0004-認証情報と接続設定の保存先]]）。

**落とした種別は問い合わせにも行かない。** `ALL_OBJECTS` の `in (...)` はフィルタから組み立て、索引と DB link はそれぞれのビューを引くこと自体を飛ばす。表示だけ抑えても段階 1 の重さは変わらないためである。

項目ごとに `#[serde(default = "default_true")]` を付けてある。後から種別を足したとき、既存の `connections.toml` でもその種別が見えるようにするためである。

### 補完に流すのは 9 種別だけ

**索引・トリガー・DB link は補完のカタログに入れない**（[[0013-補完の候補生成と識別子の出力スタイル]]）。索引とトリガーの名前は SQL 本文に現れない（`DROP INDEX` のような DDL でしか使わない）。DB link は `表@リンク名` の形でしか使えず、この補完ソースは `@` を解さないため、裸の名前を並べても誤った綴りを勧めるだけになる。

シノニムと型は入れる。シノニムは表と同じ位置に書け、型は PL/SQL の宣言で使う。カタログは補完のためだけの表であり、引けない名前を抱えても嵩むだけである。

## 理由

- **束ねる**という一手で、「種別を増やしたい」と「1 スキーマの行数を抑えたい」が同時に立つ。フィルタだけでは、既定を全部オンにした利用者が最初に見るのが数千行の平らな並びになる。フィルタだけを既定オフにすると、足した種別が誰の目にも触れない。
- **種別フィルタは問い合わせの段で効かせる。** [[0007-スキーマ取得の段階的ロード]] の段階 1 が守っているのは「接続直後に固まらないこと」であり、守るべきは表示の行数ではなく取得の行数である。
- **索引の自動生成を落とす**のは、`SYS_C0012345` が利用者の付けた名前ではないからである。名前で探せないものをツリーに並べても、束の件数を水増しするだけになる。
- **`PUBLIC` を外す**のは、ツリーがスキーマを軸にした形だからである。`PUBLIC` はスキーマではない。

## 却下した案

**制約を `ALL_CONSTRAINTS` から取ってスキーマ直下に並べる**: 名前の過半が `SYS_C0012345` であり、スキーマ直下に並べても「どの表の制約か」が分からない。ツリーの形と制約の性質が合っていない。

**制約をテーブル配下に列と並べてぶら下げる**: 形としては自然だが、段階 2 と同じ流し込みをもう 1 系統回すことになり、進捗表示（`列情報を読み込み中 8/23 スキーマ`）の意味も曖昧になる。テーブル定義ビューを作る波でまとめて扱うほうが筋が良い。

**`PUBLIC` を擬似的なスキーマとしてツリーに足す**: 公開シノニムと公開 DB link を見せられるが、`ALL_USERS` に無い名前をスキーマ行として出すことになり、「システムスキーマを除外」との噛み合わせを説明できない。数万件の公開シノニムを段階 1 で取る重さも見合わない。

**索引を `ALL_OBJECTS` から取り、名前が `SYS_` で始まるものを落とす**: `GENERATED` 列を見るのが正しい判定であり、名前の綴りで代用すると `SYS_` で始まる利用者の索引まで落とす。ビューを 1 つ増やす代わりに正確さを取った。

**種別ごとの束を作らず、フィルタの既定で索引を落とす**: 足した種別のうち最も数の多いものが既定で見えないのでは、足した意味が薄い。束ねれば既定を全部オンにできる。

**種別の可否を `Vec<ObjectKind>` として保存する**: TOML には短く書けるが、後から種別を足したときに既存の設定ファイルでその種別が現れない。項目ごとに既定を持てる構造体を選んだ。

**索引やトリガーも補完の候補に出す**: 候補一覧が名前で埋まるだけで、SQL 本文に書ける名前ではない。

## 結果

- 段階 1 の問い合わせが 2 本から最大 4 本に増える。`ALL_INDEXES` は `ALL_OBJECTS` と同程度の重さがあり、既定のまま繋ぐと接続直後の待ちが伸びる。伸びが気になるデータベースでは索引を落とせる、というのが種別フィルタの主な使い道である。
- スキーマ行の右に出る数（`object_count`）は、隠している種別を含まない。取得しないものは数えられないためであり、フィルタを変えると数も変わる。
- `flattenSchemas` の戻り値に `kindGroup` の行が増えた。行の高さの見積もりと `Row` の描き分けもこの種類を持つ。
- `nodeKey` と衝突しない束の鍵として `kindGroupKey`（`KODUCHI.#table`）を足した。Oracle の無引用の識別子は `#` で始まれないため、実在の名前と重ならない。
- 開発用データベース（`dev/oracle/initdb/005_object_kinds.sql`）に型・シノニム・トリガーを足した。DB link だけは `CREATE DATABASE LINK` がスキーマ修飾を受け付けず、必ず接続中のユーザーのスキーマに作られるため、権限だけを与えて統合テストが自分で作って自分で消す。
- 制約をツリーへ出す判断は、テーブル定義ビューを作る波へ持ち越す。そのとき本 ADR の「制約は今回入れない」を覆すのではなく、置き場所がそちらに決まったという形になる。
