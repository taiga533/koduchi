# ADR 0005: クエリ履歴とセッション復元に SQLite を使う

- ステータス: 承認
- 日付: 2026-08-30

## 状況

クエリ履歴の保持は本アプリの主要機能の 1 つである。デザインのサイドバーには履歴セグメントがあり、「この接続のみ / 全接続」のスコープ切替を持つ。したがって履歴は全接続を横断する 1 つの保管庫である必要がある。

また `.sql` ファイルの開く/保存に対応するが、デザインのタブには未保存を示す `●` マークがある。つまり未保存の状態でタブを閉じたりアプリを終了したりすることが前提の設計である。

## 決定

**`rusqlite` による SQLite を、履歴とセッション復元の両方の保管庫として使う。**

履歴に記録する項目:

- SQL 全文
- 接続名
- 開始時刻
- 所要ミリ秒
- 行数
- 成否
- エラーメッセージ

記録の対象は成功・失敗を問わず全て。ただし `⌘E` / `⇧⌘E` による実行計画の生成は記録しない。保持期間は**無制限**とし、設定画面からの一括削除と、履歴 1 件ごとの個別削除を用意する。

セッション復元のために保存するもの:

- エディタタブ（ファイルパス（任意）、バッファ内容、未保存フラグ、並び順、選択中のタブ）
- サイドバーの選択セグメント

ウィンドウの位置とサイズは `tauri-plugin-window-state` に任せる。

復元しないもの: 結果セット、スキーマツリーの展開状態、データベースへの接続そのもの。起動時はデザイン状態 5g の空状態から接続を選ばせる。

## 理由

- 履歴を「保持する」と謳う以上、再起動をまたいで残り、検索できる必要がある。JSON ファイルへの追記では数千件で全読み込みが辛くなる。
- 接続横断のスコープ切替が要件にある以上、保管庫は 1 つでなければならない。
- 未保存バッファの永続化はタブの `●` マークが前提としている挙動であり、履歴用の SQLite が既にあるので追加コストはテーブル 1 つ分にすぎない。
- 結果セットは再接続なしに復元できないため、復元対象から外すのが正直である。

## 却下した案

**JSON ファイルへの追記**: 数千件で全読み込みが辛い。検索も自前実装になる。

**メモリのみ（アプリ終了で消える）**: 履歴保持という要件を満たさない。

**保持期間を直近 1 万件 / 90 日に制限する**: SQLite なら数十万件でも問題なく、古い履歴が消えることの害のほうが大きい。

**保存していないタブを終了時に破棄する（確認ダイアログを出す）**: `●` マークのある設計と噛み合わない。

**起動時に保存済み接続へ自動再接続する**: キーチェーン取得で OS のダイアログが不意に出る。

## 結果

- `alter user ... identified by 'xxx'` のような SQL は履歴に平文で残る。これを避けるために履歴を削るほうが害が大きいと判断し、代わりに**個別削除の操作**を用意する。
- 結果ペインの履歴タブは廃止し、サイドバーに一本化する（[[0008-デザイントークンとテーマ実装方式]] ではなく本 ADR の範囲）。デザインが 2 箇所に履歴を置いていたのは密度の違う 2 つの見え方を意図したものだが、サイドバー側でスコープ切替まで持つため役割が重複する。
