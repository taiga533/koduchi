# ADR 0031: オーバーレイの `esc` と document のスクロール

- ステータス: 承認
- 日付: 2026-09-11

## 状況

見た目の不具合が 2 件挙がった（issue #36・#37）。どちらも「触っていると気持ちが悪い」類だが、原因は別の場所にあり、どちらも**同じ穴を次の人がもう一度開けられる形**で残っている。1 本の ADR にまとめるのは、2 件がともに「アプリの器の決めごとが 1 箇所に無い」ことに帰着するためである。

### issue #36 — コマンドパレットが `esc` で閉じないことがある

> コマンドパレットが最前面に来てるときに、画面上のいずれの要素にもフォーカスが当たってない状態で ESC を押してもコマンドパレットを閉じれない

`CommandPalette` は `esc` を**器の `onKeyDown`** で受けていた。React の合成 event は DOM の伝播に乗るため、焦点が器の中にあるあいだしか届かない。

焦点が抜ける道は塞いだつもりでも残る。実際に起きているのはこれである。

1. パレットの暗幕（`absolute inset-0` の `div`）を押す。
2. `div` は焦点を持てないため、押し下げで入力欄の焦点が外れ、`document.activeElement` が `<body>` に戻る。
3. 暗幕には「押したら閉じる」も無いため、パレットは開いたまま残る。
4. 以後 `esc` も `↑` `↓` も `⏎` も届かない。**閉じる道が無くなる。**

同じ形のオーバーレイを数え上げたところ、`esc` の扱いは 3 通りに割れていた。

| 受け方 | 部品 | 焦点が外れたとき |
| --- | --- | --- |
| 器の `onKeyDown` | `CommandPalette` / `BindValuesDialog` / `SaveQueryDialog` | **閉じない** |
| `window` の `keydown` を自前で張る | `SessionsPanel` / `SourceSearchPanel` / `CellDetailPanel` | 閉じる |
| 何も無い | `SettingsPanel` / `CsvSaveDialog` / `DisconnectBlockedDialog` / `SchemaTreeContextMenu` / `ResultContextMenu` | **そもそも `esc` が効かない** |

2 番目の作り（`window` に自前で張る）にも別の穴がある。**開いているオーバーレイ全部に同じ 1 打鍵が届く。**セルの詳細パネルの上にコマンドパレットが重なっているとき、`esc` 1 回で両方が消えるのは「1 つ戻る」ではない。

### issue #37 — スクロールすると下部に謎の余白が出る

> 画面をスクロールすると下部に謎の余白が出る
> 上にスクロールすると画面が下に降りようとする挙動もする

まず**どの要素がスクロールしているのか**を測った。`bun run dev` を立て、開発者ツールから各段の高さを読んだ（1100 × 700 の窓、接続していない画面）。

| 要素 | `clientHeight` | `scrollHeight` | `overflow-y` | `overscroll-behavior-y` |
| --- | --- | --- | --- | --- |
| `html` | 700 | 700 | `visible` | `auto` |
| `body` | 700 | 700 | `visible` | `auto` |
| `#root` | 700 | 700 | `visible` | `auto` |
| `Shell` の器 | 700 | 700 | `visible` | `auto` |

**接続していない画面でははみ出しが 0px である。**900 × 320 まで縮めて本体が溢れる状態を作っても `documentElement.scrollHeight` は 320 のままで、溢れは `CenteredPanel` の `overflow-auto` が引き受けていた。`100vh` は src のどこにも使っていない。

**ここで止めたのが誤りであった。**接続していない画面は、この不具合が起きる画面ではない。実物の `WKWebView` を立てて**接続した状態**を測り直したところ、答えが変わった（1138 × 679 の窓）。

| | `html.scrollHeight` | `body.scrollHeight` | `clientHeight` | 送れる量 |
| --- | --- | --- | --- | --- |
| 接続前 | 679 | 679 | 679 | 0px |
| **接続後** | 679 | **1358** | 679 | **679px** |

**`body` がビューポートちょうど 2 枚ぶんの高さになっている。**`html` が 679 に見えるのは `overflow: hidden` が伏せていたからで、それを外して測り直すと `html.scrollHeight` も 1358、`scrollTop` は **679px まで送れた**。つまり**本当に document がスクロールしていた**のであり、ラバーバンドではない。

下へ伸ばしている要素は 1 つだけである。

```
DIV.ͼ1 ͼ2 ͼ11   top=679  height=679  position=relative  offsetParent=BODY
```

`ͼ…` は CodeMirror が作るテーマの class である。犯人は `SqlEditor` の次の 1 行にある。

```ts
// 補完の候補は編集領域の外（本体直下）へ出す。
tooltips({ parent: document.body }),
```

`@codemirror/view` は `parent` を渡されると、補完の候補を入れるための `div` を**本体直下に 1 枚**作る（`createContainer`）。

```js
this.container = document.createElement("div")
this.container.style.position = "relative"
this.container.className = this.view.themeClasses   // ← "ͼ1 ͼ2 ͼ11"
this.parent.appendChild(this.container)
```

与えるのは `position: relative` と**エディタと同じテーマの class** だけである。一方エディタのテーマ（`src/components/editor/theme.ts`）は

```ts
'&': {
  height: '100%',
  backgroundColor: 'var(--panel)',
  ...
}
```

と書いてあった。**`&` はテーマの class そのものを指す。**したがってこの空の入れ物にも `height: 100%` と `background: var(--panel)` が当たり、**`<body>` の 100%、つまりビューポートちょうど 1 枚ぶんの白い帯**が本体の下に生まれる。

**これが「謎の余白」である。高さは 679px = ビューポート 1 枚ぶんであり、数字で説明が付く。**色は地の `--bg` ではなく `--panel`（白）である。「上にスクロールすると画面が下に降りようとする」も、ラバーバンドではなく **679px ぶん本当にスクロールできる document を上へ戻している**だけであった。

タイトルバーの 42px でもステータスバーの 26px でも `100vh` と窓の高さの差でもない、という当初の結論だけは正しかった。

## 決定

### 1. `esc` は器ではなく `window` で受け、受け手を積みで 1 つに絞る

**オーバーレイの器に `onKeyDown` を付けない。**`src/input/useEscapeKey.ts` の `useEscapeKey(onClose)` 1 つを通す。

- 打鍵は `window` の `keydown` で受ける。焦点が `<body>` に戻っていても届く。これが**閉じる道の保証**である。
- 受け手は `src/input/escapeStack.ts` の積みに入れ、**いちばん後に開いたものだけ**を走らせる。重なったオーバーレイが 1 打鍵でまとめて消えない。
- `window` の listener は受け手が 1 つ以上あるあいだだけ張る。

見る順は 3 つで、どれも飛ばさない。

1. **`event.defaultPrevented`** — より近い所（入力欄・CodeMirror・結果テーブルの検索欄）が既に処理した `esc` は二重に扱わない。`App.tsx` の `keydown` と同じ作法である。
2. **`isComposingKey`**（[[0025-入力欄における変換中の打鍵]]） — 変換中の `esc` は変換の取り消しであって「閉じる」ではない。`window` で受ける以上、この関所はここにも要る。
3. **積みの末尾** — 手前の 1 つだけが閉じる。

渡された関数は描画のたびに別物になりうるが、**積みに入る受け手の同一性は `useRef` で保つ。**描画のたびに積み直すと、後ろに居たはずのオーバーレイが手前へ繰り上がってしまう。

**上の表に挙げた 11 個すべてをこの 1 つへ寄せた。**`esc` を持っていなかった 5 個（設定・CSV 保存・切断できない知らせ・ツリーの右クリックメニュー・結果の右クリックメニュー）にも付く。オーバーレイを足す人が `useEscapeKey` を呼べば済み、`window` に自分で張る形はもう要らない。

`SessionsPanel` と `SourceSearchPanel` の「まず中の状態だけを解き、次に閉じる」2 段の動きはそのまま残す（渡す関数の中で分岐する）。

#### 焦点が抜ける道そのものも塞ぐ（ただし保証にはしない）

`CommandPalette` の暗幕は、自分自身が押されたときだけ `mousedown` の既定動作を止める。押しても入力欄の焦点が外れないため、`↑` `↓` `⏎` も効いたままになる。**これは原因の側の手当てであって、閉じる道の保証ではない。**焦点が抜ける道は塞いだつもりでも残る（メニューの外を押す、ネイティブのダイアログから戻る、ウィンドウの外から戻る）。だから保証は `useEscapeKey` が別に持つ。

#### 退けた案

- **焦点の罠を張る（外れたら入力欄へ引き戻す）。** 引き戻す先が 1 つに決まらない。`SessionsPanel` のように入力欄が複数ある部品では、利用者が選んだ欄を奪い返すことになる。`CellDetailPanel` のように「焦点を奪わないこと」が持ち味の部品もある。
- **器に `tabIndex={-1}` を持たせて器で拾う。** 器自身に焦点を当てる誰かが要る。当て損ねればまた同じ穴であり、`autoFocus` の付いた入力欄と焦点を取り合う。
- **`App.tsx` に `esc` の枝を 1 本足す。** どのオーバーレイが開いているかを `App.tsx` が全部知ることになる。オーバーレイを足すたびに `App.tsx` へ 1 行足す形は、まさに今 3 通りに割れた原因である。

### 2. エディタのテーマの `&` に寸法を書かない

**直すのはテーマの側である。**高さを `&` から `&.cm-editor` へ移す。

```ts
'&.cm-editor': {
  height: '100%',
},
'&': {
  fontSize: 'var(--fs-editor)',
  color: 'var(--fg)',
  backgroundColor: 'var(--panel)',
},
```

`.cm-editor` は編集領域そのものにしか付かない（入れ物に付くのは `themeClasses` だけである）ため、併記すれば入れ物には当たらない。実物の `WKWebView` で測り直すと、入れ物は `height=679` から **`height=0`** になり、`body.scrollHeight` は 1358 から **679** へ戻った。`overflow` を外して送ろうとしても **0px** である。

`fontSize` と `color` は `&` のままにしてある。**入れ物に付いてよい**どころか、中に出る補完の候補がそれを継ぐので付いていたほうがよい。`backgroundColor` も高さが 0 なら何も塗らない。

**`&` へ寸法（`height` / `width` / `padding` / `margin` / `position` / `display` …）を書き足さない。**この決まりは `src/components/editor/theme.test.ts` が見張る。**`tooltips({ parent: document.body })` の判断（ADR にはないが `SqlEditor` の註釈にある「入力の最中に DOM が動いて変換に割り込む」）は覆さない。**

#### 退けた案

- **`parent: document.body` をやめる。** 補完の候補を編集領域の中へ出すと、打鍵のたびに DOM が動いて IME の変換に割り込む（[[0025-入力欄における変換中の打鍵]] が扱っている領域である）。入れ物が要ること自体は正しい。
- **`app.css` で入れ物を名指しして潰す。** 名指しできない。入れ物に付く class は `ͼ1 ͼ2 ͼ11` のような生成された名前だけで、版が変われば変わる。

### 3. document はスクロールさせない（守り。直しではない）

`src/app.css` の `html` と `body` に 2 つ足す。

```css
html,
body {
  overflow: hidden;
  overscroll-behavior: none;
}
```

**これは直しではなく守りである。**上の 2 で溢れそのものが無くなっており、この 2 行が無くても issue #37 は直っている。それでも置くのは、デスクトップアプリで document がスクロールするのは常に誤りであり、溢れを引き受けるのは常にその場の器だからである。

- **`overscroll-behavior: none`** が WKWebView の弾み（ラバーバンド）を止め、器の中から document へのスクロールの伝播も断つ。**器の中のスクロールそのものには影響しない。**実物の `WKWebView` で `overscroll-behavior-y` が `none` と算出されることを確かめた（この property が解されずに黙って無視される、というのが唯一の現実的な失敗であった）。
- **`overflow: hidden`** は、将来どこかが溢れても document をスクロールさせない。

**`html` と `body` の両方へ書く。**ビューポートのスクロールの持ち主は実装によってどちらにもなる。

高さの出どころは既にある `height: 100%` の連なり 1 本のままにし、**`100vh` にも `100dvh` にも替えない。**測ったとおり連なりはウィンドウの高さとぴったり一致している。`100vh` は macOS のウィンドウの実際の高さと必ずしも一致せず、差がそのままはみ出しになる。

[[0009-ウィンドウモデルとタイトルバー]] の `trafficLightPosition` と `src/components/titlebar/geometry.ts` には**手を触れていない。**余白はタイトルバーの寸法とは無関係であった。

#### この 2 行の代償を承知しておく

**`overflow: hidden` は今回の不具合を実際に覆い隠した。**接続後の `html.scrollHeight` が 679 に見えたのはこの宣言のせいであり、`body` を見なければ 1358 に気付けなかった。守りとして置く以上、**原因の側を捕まえる見張りは別に要る。**それが `theme.test.ts` である。`app.css.test.ts` が見張るのは「決めた宣言が消えていないこと」だけであって、溢れが無いことではない。**この 2 つを取り違えない。**

## 帰結

- オーバーレイを足す人は `useEscapeKey(onClose)` を呼ぶだけでよい。**`window` に自分で `keydown` を張らない。器に `onKeyDown` を付けない。**
- `esc` が効くオーバーレイが 6 個から 11 個へ増えた。設定画面と CSV 保存ダイアログと 2 つの右クリックメニューは、これまで `esc` で閉じられなかった。
- 重なったオーバーレイは 1 打鍵で 1 つずつ閉じる。これまでは `window` に張っていた 3 つが同時に消えていた。
- **エディタのテーマの `&` は「エディタ本体」を指さない。**補完の入れ物も同じ class を持つ。寸法は `&.cm-editor` へ書く。
- document はスクロールしない。仮想スクロールは器の中のままである。
- **確かめ方。** `esc` の側は jsdom で確かめられる（焦点を `<body>` へ落として `window` へ `esc` を送る）。余白の側は jsdom がレイアウトを持たないため確かめられないので、**実物の `WKWebView` を立てて測った**うえで、原因の側を `theme.test.ts` が、`app.css` の決めごとを `app.css.test.ts` が見張る。
- **測る画面を間違えない。**この不具合は接続した後の画面にしか出ない。接続していない画面だけを測って「はみ出しは 0px」と結論すると、原因を取り逃してラバーバンドのせいにしてしまう（実際に一度そうなった）。

### 実物の WKWebView で測った結果

`bun run dev` の出す画面を `WKWebView`（wry が使うのと同じ class）へ読み込ませ、接続・ツリーの展開・400 行 × 24 列の結果テーブル・オーバーレイまで一通り出して測った。1138 × 679 と 700 × 400 の 2 つの窓で同じである。

| 見たもの | 結果 |
| --- | --- |
| `html` / `body` の `scrollHeight` | どの場面でも `clientHeight` と等しい（送れる量 0px） |
| 溢れているのに自分では送れない器 | 結果テーブルの見出しの帯だけ（`scrollLeft` を本体と揃える作りで、元からそうである） |
| 結果テーブルの器 | 縦 8,975px / 横 3,006px の余りを**端まで送れる** |
| スキーマツリーの器 | 700 × 400 で縦 136px の余りを**端まで送れる** |
| コマンドパレットの一覧 | 縦 474px の余りを**端まで送れる** |
| `overscroll-behavior-y` の算出値 | `none`（WebKit が解している） |
| 焦点を `<body>` へ落としてからの `esc` | パレットが閉じた |
