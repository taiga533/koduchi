# ADR 0007: スキーマ取得の段階的ロード

- ステータス: 承認
- 日付: 2026-08-30

## 状況

デザインのサイドバーは「スキーマ 5」としてスキーマを列挙し、各行の右にオブジェクト数（`14`, `9`, `6` …）を表示する。テーブルを展開すると列名と型が並ぶ。さらにスキーマ内の検索（絞り込み入力）があり、検索は列名にも効くことが望ましい。

Oracle には固有の事情がある。

- 「スキーマ = ユーザー」であり、`ALL_TABLES` を素直に引くと `SYS` を含む数十〜数百のスキーマが返る。
- `ALL_TAB_COLUMNS` は中規模のデータベースでも 10 万行を超える。接続時に一括取得すると数十秒フリーズする。
- `ALL_*` ビューは**そもそも権限のあるオブジェクトしか返さない**。一方 `ALL_USERS` は権限に関わらず全スキーマを列挙する。

## 決定

**列挙元は `ALL_USERS`** とし、フィルタで絞る。フィルタ UI はスキーマ検索入力の横のアイコンから開き、条件は 2 つ。

1. **システムスキーマを除外**（既定 ON）。Oracle は `SYS` / `SYSTEM` / `XDB` / `OUTLN` 等の既知リスト、PostgreSQL は `pg_catalog` / `information_schema` / `pg_toast`。
2. **参照可能なオブジェクトが無いスキーマを隠す**（既定 ON）。PostgreSQL 側は `has_schema_privilege(nspname, 'USAGE')` で同等の判定を行う。

フィルタ設定は接続ごとに `connections.toml` の接続エントリ内へ保存する（[[0004-認証情報と接続設定の保存先]]）。

**取得は 3 段階のバックグラウンドロード**とする。

1. 接続直後: スキーマ名 + 各スキーマのオブジェクト数（`GROUP BY owner` の 1 クエリ）+ テーブル / ビュー / 関数の**名前**一覧。ここまでで数千行、1〜2 秒。この時点でツリーと検索が使える。
2. その後: 列情報をバックグラウンドで段階的に流し込む。サイドバー下部に `列情報を読み込み中 8/23 スキーマ` を表示。
3. 読み込み済みの範囲から検索できる。最終的にはすべての列名が検索対象になる。

キャッシュはフロントエンドで保持し、手動リロードで破棄する。

## 理由

- 「検索のためにすべて欲しい」と「起動が固まってはいけない」を両立できるのは段階的ロードだけである。
- 列挙元を `ALL_USERS` にすることで、フィルタのチェックボックスが意味を持つ。`ALL_TABLES` の `DISTINCT owner` から列挙すると常に権限のあるスキーマだけになり、切り替える余地がなくなる。
- データベースクライアントとして他スキーマを覗けないのは不便であり、既知の内蔵スキーマ除外リストはメンテナンス可能な規模である。
- スキーマ行のオブジェクト数はデザインが表示している以上、一覧取得前に必要になる。`GROUP BY owner` の 1 クエリで賄える。

## 却下した案

**接続時に列まで含めて一括取得する**: 大きなデータベースに繋いだ瞬間にアプリが無反応になる。

**3 段階の遅延ロード（展開時に初めて取得）**: スキーマ内検索が列名に効かなくなる。

**`USER_*` ビューのみを使う（接続ユーザー自身のスキーマだけ）**: 他スキーマを参照できず、クライアントとして不便。

**接続設定に「表示するスキーマ」を手書きさせる**: フィルタ UI のほうが操作として自然で、手書きの手間もない。

**「空のスキーマを隠す」を独立した条件にする**: 「参照可能なオブジェクトが無いスキーマを隠す」と実質的に重複する。

## 結果

- 取得済みのスキーマ情報は CodeMirror の補完にもそのまま渡す（[[0008-デザイントークンとテーマ実装方式]] ではなくエディタ側の話だが、データ源は本 ADR のキャッシュである）。
- 列情報の読み込み完了前に検索した場合、まだ読み込まれていないスキーマの列はヒットしない。進捗表示でその状態を伝える。
