# ADR 0025: 入力欄における変換中の打鍵

- ステータス: 承認
- 日付: 2026-09-08

## 状況

日本語を打つとき、`⏎` はほとんどの場合「決定」ではない。「ゆーざ」と打って `⏎` を押すのは**変換を確定する**操作であって、その先の実行・保存・送信を頼んだわけではない。`esc` も同じで、変換中は「変換を取り消して元の読みに戻す」操作である。`↑` `↓` は変換候補を選ぶ操作である。

小槌はこれを一切見ていなかった。実際に次のことが起きる。

- コマンドパレット（`⌘K`、[[0018-保存済みクエリとコマンドパレット]]）で「ユーザ」と打って変換を確定すると、**まだ何も選んでいないのに先頭の候補が実行される**。`esc` で変換を取り消そうとするとパレットごと閉じ、`↑` `↓` で候補を選ぼうとすると裏でパレットの選択が動く。
- 保存済みクエリの名前を日本語で付け直そうとすると、**変換を確定した時点で名前が確定して編集が終わる**。
- 接続を作る画面（`ConnectionForm`）は「名前」も「グループ」も日本語で打つ欄であり、その `<form>` が変換確定の `⏎` で送信される。

アプリ全体で `isComposing` を見ていたのは `src/components/editor/search.tsx` の 1 箇所だけだった。あれは `@codemirror/search` が入力欄の `keyup` ごとに検索を作り直すのを、パネルの捕捉相で止めているものである。

決めるべきことは 4 つある。

1. `<form>` の暗黙の送信は、WKWebView で本当に変換確定の `⏎` に反応するのか
2. 判定を共通のヘルパにするか、各所で `event.nativeEvent.isComposing` を直書きするか
3. `isComposing` だけで足りるか（`keyCode === 229` や「確定直後の 1 打鍵を捨てる」手当ては要るか）
4. 絞り込みの入力欄で、変換中の 1 文字ごとに処理を走らせてよいか

## 決定

### 1. WKWebView の実挙動を測ってから決めた

**推測せずに実機で測った。**仕様上、ブラウザは変換中の `⏎` で暗黙の送信をしないはずだが、WebKit の実装は歴史的にぶれがある。jsdom には本物の IME が無いため vitest では確かめられない。

そこで `WKWebView` を 1 枚だけ載せた小さな Objective-C のプログラムを書き、`NSTextInputClient` の `setMarkedText:` で**本物の変換中の状態**を作り、`NSEvent` の `Return` をそのウィンドウへ送って、ページ側で `keydown` / `keypress` / `submit` / `composition*` を記録した。IME が WKWebView へ話しかける経路そのものである。測った結果は次のとおり。

| 場面                             | `keydown`                                       | 暗黙の送信 |
| -------------------------------- | ----------------------------------------------- | ---------- |
| 変換中でない `⏎`                 | `key=Enter` `keyCode=13` `isComposing=false`     | **する**   |
| **変換中の `⏎`**                 | `key=Enter` `keyCode=13` **`isComposing=true`**  | **する**   |
| 変換中の `esc`                   | `key=Escape` `keyCode=27` `isComposing=true`     | —          |
| 変換中の `↓`                     | `key=ArrowDown` `keyCode=40` `isComposing=true`  | —          |
| `compositionend` の**次**の `⏎`  | `key=Enter` `keyCode=13` `isComposing=false`     | する       |
| 変換中の `⏎` を `preventDefault` | 同上                                            | **しない** |

読み取れることは 4 つある。

- **`<form>` は変換確定の `⏎` で暗黙の送信をしてしまう。**仕様がどうであれ、小槌が載る WebView はそう動く。**5 つの `<form>` すべてに手当てが要る。**

### 1-2. 【訂正】本物の IME で測り直したら、上の結論の半分が誤りだった

上の測定は `setMarkedText:` で**合成した**変換状態でのものであり、この ADR は当初「本物の Kotoeri での打鍵は再現していない」と断ったうえで結論を出していた。**その残した一段が、実際には結論を覆すものだった。**

利用者の環境（macOS の Kotoeri）で、動いているアプリに打鍵の記録を仕込んで測り直した結果は次のとおりである。

| 場面                     | `key`   | `keyCode` | `isComposing` |
| ------------------------ | ------- | --------- | ------------- |
| **変換を確定する `⏎`**   | `Enter` | **229**   | **`false`**   |
| 変換中でない `esc`       | `Escape`| 27        | `false`       |

**合成の変換状態で出た「`isComposing` が真になる / `keyCode` は 229 にならない」は、本物の IME には当てはまらない。**変換の確定は composition の**終わり**でもあるため、その打鍵はもう「変換中」とは報されない。代わりに `keyCode` が 229 になる。

したがって決まりを次のように改める。

- **`isComposing` と `keyCode === 229` の両方を見る。**変換の途中（候補を選んでいる間）は `isComposing` が真で届き、変換を**確定する** `⏎` は `isComposing` が偽・`keyCode` が 229 で届く。片方だけでは確定の打鍵を取りこぼす。
- 下の「却下した案」にある **「`keyCode === 229` も併せて見る」は却下を取り消す。**却下の理由が誤った測定に拠っていた。

**教訓として残す。**`setMarkedText:` は IME が WebView へ話しかける経路そのものではあるが、**経路が同じであることと、実際の IME が同じ順序・同じ値で話しかけることは別である。**この ADR は測れなかった一段を正直に書き残しており、そのおかげで誤りの在り処がすぐに分かった。書き残しておくこと自体に値打ちがあった。
- **`key` は `Enter` のまま届き、`keyCode` は 13 である。**Chromium の流儀（変換中は `keyCode` を 229 にし、`key` を `Process` にする）とは違う。**`keyCode === 229` を併せて見る意味は無い。**
- **`isComposing` は正しく真になる。**変換中かを見分ける手立てはこれだけであり、これで足りる。
- **`preventDefault()` が効く。**暗黙の送信はその `keydown` の既定の動作として起きるため、`keydown` の段階で断てば `submit` は起きない。

測ったプログラムは一時ファイルであり、リポジトリには残していない。**本物の日本語 IME を使った打鍵は再現していない**（作業機に日本語の入力ソースが 1 つも有効化されておらず、利用者の macOS の入力ソース設定を勝手に足すことは避けた）。`setMarkedText:` で作った変換中の状態は IME が使う経路そのものであり、上の 3 つの結論はそこから直に導けるが、**「実際に Kotoeri で打ったら本当にそうなる」ところまでは確かめていない。**

### 1-3. 【追記】穴が空いていたのは検索パネルだけだった

当初の監査は React のハンドラと `<form>` だけを見ており、CodeMirror の内側を見ていなかった。そこで実 CodeMirror で測り直した。

**結論から言えば、塞ぐ必要があったのは `⌘F` の検索パネルの 1 か所だけである。**

**本文（`contentDOM`）には手当てが要らない。**`@codemirror/view` の `InputState.ignoreDuringComposition` が変換中の打鍵を既に捨てており、しかも **WebKit で `compositionend` の後に `⏎` が届く癖**まで面倒を見ている（`browser.safari && this.compositionPendingKey && Date.now() - this.compositionEndedAt < 100`）。ライブラリ側のコメントも、この ADR が踏んだのと同じ IME の事情を挙げている。

**測るときは event の順序を間違えないこと。**最初の測定では `keydown` → `compositionend` の順で送ってしまい、「本文で変換を確定すると改行が入る」という**存在しない不具合**を見た。実機の順序は `compositionend` → `keydown` である（変換確定の `⏎` が `isComposing = false` で届くのがその証拠。「1-2」の測定）。正しい順序で送ると改行は入らない。

| 送った順序                              | 本文の中身   |
| --------------------------------------- | ------------ |
| `compositionend` → `keydown`（**実機**） | `"-- "`      |
| `keydown` → `compositionend`（誤り）    | `"-- \n"`    |

**検索パネルだけは対象外である。**`ignoreDuringComposition` が効くのはエディタ本文に属する打鍵だけで（`eventBelongsToEditor`）、パネルは `contentDOM` の外にある。パネルは `esc` を自前の `keydown` で受けて閉じるため、**変換を取り消すつもりの `esc` で打ちかけの検索語ごとパネルが消える。**

塞ぎ方は `search.tsx` に既にあった仕掛けを広げるだけでよい。あそこは変換中の `keyup` をパネルの捕捉相で止めていたので、`keydown` も同じ関所へ通す。**`preventDefault()` は使わない**（変換の確定そのものへ影響しかねないうえ、要るのは「パネルに横取りさせない」ことだけである）。

当初「走る」と見立てていた 2 つは**走らなかった**。理由まで書き残す。

- 検索パネルの `findNext` は走らない。パネルの `keydown` が `e.keyCode == 13` を見ており、変換確定の **229 は素通りする**（偶然の防護であって意図した作りではないため、関所は `⏎` も通さないままにしてある）。
- 補完の `acceptCompletion` も走らない。本文の打鍵は上記のとおり CodeMirror が捨てている。

**教訓。**「ライブラリは何もしてくれていないはずだ」と決めてかかると、要らない関所を足すことになる。**まず測り、次に測り方が実機と同じかを疑う。**

### 2. 共通のヘルパを 1 つ作る — `src/input/ime.ts`

`event.nativeEvent.isComposing` の直書きは、置き場所が 9 ファイルに散り、React の型に `isComposing` が無い理由を各所で書き直すことになる。判定は 1 箇所に置く。

置き場所は `src/input/ime.ts` にした。`src/components/` の下ではないのは、使い手が `palette/` `sidebar/` `editor/` `source/` `connection/` `sessions/` `results/` の 7 つに跨るためである。特定のコンポーネントの隣に置けば、他の 6 つがそこを覗きに行くことになる。`src/transaction/pendingChanges.ts`（[[0012-トランザクション制御]]）が同じ理由で `src/` の直下に居るのと同じ形である。

書き出すのは 2 つだけである。

- **`isComposingKey(event)`** — その打鍵が変換中に起きたものかを返す純粋な関数。DOM の `KeyboardEvent`（`window` に付けた listener が受け取る）と React の合成 event（`nativeEvent` の下に持つ）の両方を受ける。
- **`blockComposingSubmit(event)`** — `<form>` の `onKeyDown` にそのまま渡す関所。変換中の `⏎` だけ `preventDefault()` する。

送信の event 自体は変換中かどうかを持たない。だから `onSubmit` では判定できず、**送信になる前の `keydown` で断つ**しかない。`<form>` 側に `onCompositionStart` / `onCompositionEnd` で状態を持たせる形も採れるが、コンポーネントに状態が 1 つ増えるうえ、`keydown` 1 本で足りることが測って分かっている。

### 3. 決まりは 1 つ —「変換中の打鍵は何も起こさない」

`⏎` だけを特別扱いしない。**変換中の `keydown` は、その画面の操作としては一切扱わない。**打鍵を受けるハンドラの先頭で `isComposingKey(event)` を見て、真なら何もせずに戻る。

`esc` も `↑` `↓` も同じ扱いにするのは、どれも変換中には IME のものだからである。`esc` は変換の取り消し、`↑` `↓` は候補の選択であり、画面の側が横取りしてよい打鍵ではない。`⏎` だけ直しても、パレットで「ユーザ」を変換しながら候補を選ぼうとすれば裏で選択が動く。

変換中の `↑` `↓` を握り潰すと、パレットで日本語を打っている間は候補の移動ができなくなる。**この手触りでよいことは利用者に確認を取った**（変換中は IME の候補選択に専念させるほうがよく、裏でパレットの選択が動くほうが混乱する、という理由である）。

**確定直後の 1 打鍵を捨てるような手当ては入れない。**「一部の IME では確定直後の `keydown` で `isComposing` が既に偽になっている」という話があるため測ったが、WKWebView では `compositionend` の**次**の `⏎` が `isComposing=false` で届いており、これは正しい。ここで時間や回数で打鍵を捨てると、**「日本語を打った直後だけ `⏎` が効かない」という別の不具合**になる。線はここに引く。

### 4. 絞り込みの入力欄には手当てを入れない

サイドバーの絞り込み（`Sidebar.tsx`）・セッション一覧の絞り込み（`SessionsPanel.tsx`）・定義タブの絞り込み（`TableDefinitionPanel.tsx`）・ソース検索の検索語（`SourceSearchPanel.tsx`）には、**変換中の入力を止める手当てを入れない。**

- 前の 3 つは**既に手元にある配列を篩に掛けるだけ**である。データベースへは行かず、IPC も起きない。未確定の「ゆ」「ゆー」で一瞬絞られても、確定した瞬間に正しい結果へ落ち着く。英字を打つときと同じ挙動である。
- ソース検索は**打鍵のたびには投げない**作りが初めから入っている（[[0021-オブジェクトのソース検索]]）。`ALL_SOURCE` は数十万〜数百万行あるため、検索は送信のときにだけ走る。ここに要るのは暗黙の送信の関所だけで、入力を止める手当てではない。
- 止めれば、変換している間だけ一覧が固まる。得るものが無いのに手触りが変わる。

`search.tsx` が止めているのは、`@codemirror/search` が**入力欄の `keyup` ごとに文書全体の検索を作り直す**ためであり、篩とは重さが違う。**同じ手当てを機械的に全部へ当てない。**

アプリ内の `<input>` / `<textarea>` / `<form>` と、打鍵を受けるすべてのハンドラを 1 つずつ確かめた。`<textarea>` は 1 つも無い（SQL の編集は CodeMirror である）。

### 後日の移設（[[0031-オーバーレイのescとdocumentのスクロール]]）

**オーバーレイの `esc` は、上の表の書きぶりのまま「それぞれのハンドラの先頭で見る」形ではなくなった。**受け口が `src/input/useEscapeKey.ts` の 1 つへ寄り、関所もそこに 1 つだけ置いてある。表のうち次の 6 行がこれに当たる。

- `palette/CommandPalette.tsx`（`esc` の部分のみ。`⏎` と `↑↓` は今までどおり器のハンドラの先頭で見る）
- `source/SourceSearchPanel.tsx`（`esc`）
- `sessions/SessionsPanel.tsx`（`esc`）
- `results/CellDetailPanel.tsx`（`esc`）
- `editor/BindValuesDialog.tsx`（`esc` の部分のみ。`<form>` の関所はそのまま）
- `editor/SaveQueryDialog.tsx`（同上）

**この ADR の決まりそのものは変わっていない。**変換中の `esc` で何も起こさないという結論も、`isComposing` と `keyCode === 229` の両方を見る判定も同じである。置き場所が 1 つになっただけであり、オーバーレイを足す人は `useEscapeKey` を呼べば関所ごと付いてくる。**表に `esc` だけを見る行を新しく足す必要はもう無い。**`⏎` `↑` `↓` と `<form>` については、今までどおりここに 1 行を足す。

手当てを入れなかったものの理由。

- **`App.tsx` の `keydown` は `event.metaKey` が偽なら即座に戻る。**変換確定の素の `⏎` はここに辿り着かない。`⌘` を押しながらの打鍵は IME の変換操作ではない。**この経路には手を入れていない。**
- **`SchemaTree` / `TabBar` / `ResultTable` / `Splitter` のハンドラは、文字を打てる欄の中に無い。**絞り込みの入力欄は `SchemaTree` の外側（`Sidebar` の見出しの中）に居るため、そこでの変換は `SchemaTree` の `keydown` に届かない。`TabBar` は `⌥` 必須、`ResultTable` は `⌘` 必須である。
- **`ResultSearchBar`（[[0027-結果テーブルの検索]]）は `<form>` にしていない。**`⏎` で次の当たりへ、`⇧⏎` で前の当たりへ、`esc` で閉じるという 3 つを同じ `onKeyDown` で受けるため、暗黙の送信そのものが起きない。関所はハンドラの先頭 1 か所で足り、上の決まりの 1 だけを守ればよい。**結果テーブルの値は日本語を含みうるので、ここは日本語を打つ欄である。**
- **`ConnectionPicker` の `<form>` はパスワード欄 1 つだけ**で、macOS はパスワード欄で IME を働かせないため変換は起きない。それでも関所を置いたのは、**「`<form>` には必ず関所を置く」ほうが「IME の効く欄を含む `<form>` だけ置く」より守りやすい**からである。後からこの `<form>` に別の欄が増えても漏れない。

## 今後の決まり

**入力欄や `<form>` を新しく足すときは、次の 2 つを必ず守る。**

1. `⏎` / `esc` / `↑` / `↓` など**修飾キーの付かない打鍵**を扱うハンドラは、先頭で `isComposingKey(event)` を見て、真なら何もせずに戻る。
2. `<form>` には `onKeyDown={blockComposingSubmit}` を付ける。中の欄が日本語を打つ欄かどうかで判断しない。

`⌘` や `⌥` を必須にする打鍵（`⌘K` `⌥⏎` など）には要らない。変換の操作と衝突しないためである。上の監査の表が**この決まりの持ち主**であり、入力欄を足したらここに 1 行を足す。

## 理由

- **推測ではなく測ったこと**がこの ADR の中心である。「仕様上は暗黙の送信をしないはず」で済ませていたら、5 つの `<form>` すべてに残ったままになっていた。実際には WKWebView は送信する。
- **決まりを「`⏎` の扱い」ではなく「変換中の打鍵の扱い」にした**のは、`esc` と `↑` `↓` が同じ穴だからである。`⏎` だけ塞ぐと、同じ画面の同じ入力欄で別の形の同じ不具合が残る。
- **判定を 1 つの純粋な関数に寄せた**のは、`closing.ts` / `selection.ts` / `tabOrder.ts` と同じ理由である。React の型に `isComposing` が無いという事情も、WKWebView が `keyCode` を 229 にしないという事情も、書く場所は 1 箇所でよい。
- **過剰な手当てを入れなかった**のは、それが別の不具合になるからである。確定直後の打鍵を捨てれば `⏎` が効かなくなり、絞り込みを止めれば入力欄が固まる。どちらも「日本語を打つときだけ挙動が違う」という、直そうとしていたものと同じ種類の傷である。

## 却下した案

**各所で `event.nativeEvent.isComposing` を直書きする**: ヘルパを足さずに済むが、React の合成 event と DOM の `KeyboardEvent` で書き方が変わり（`nativeEvent` の有無）、`window` に付けた listener と混ざる場所で取り違える。WKWebView の癖を説明するコメントも散る。

~~**`keyCode === 229` も併せて見る**: Chromium ではそれが変換中の印だが、**測ったところ WKWebView は 13 を返す。**対象は macOS だけ（`tauri.conf.json`）であり、効かない判定を足せば「なぜこれがあるのか」が分からない行が残る。~~ → **この却下は取り消した。**合成した変換状態では 13 だったが、**本物の Kotoeri では 229 で届く**（上の「1-2」）。今は両方を見ている。

**`compositionend` の直後の一定時間（数十 ms）は `⏎` を捨てる**: 「確定と同時に `⏎` が漏れる」という報告への手当てだが、WKWebView では `compositionend` の次の `⏎` が正しく `isComposing=false` で届いている。入れれば**日本語を打った直後だけ `⏎` が効かない**という体感になり、確定してすぐ実行したい場面（バインド変数に日本語を入れて `⏎`）で必ず踏む。

**`<form>` 側に `onCompositionStart` / `onCompositionEnd` で変換中かを持たせ、`onSubmit` で見る**: 送信そのものの場所で判定できて筋は通るが、コンポーネントごとに状態が 1 つ増える。`keydown` で `preventDefault()` すれば送信が起きないことは測って分かっており、状態を持たない側を採る。

**`<form>` をやめて送信ボタンの `onClick` だけにする**: 暗黙の送信は根から消えるが、**変換していないときの `⏎` で送信できなくなる**。あれは日本語を打たない利用者が日常的に使っている操作であり、IME の不具合を直すために英語入力の操作を壊すのは筋が悪い。`Enter` を自前で拾い直せば結局同じ判定が要る。

**`window` に 1 つだけ捕捉相の listener を置き、変換中の打鍵をアプリ全体で握り潰す**: 手当ては 1 箇所で済むが、**エディタ（CodeMirror）にも届かなくなる。**CodeMirror は自前で変換を扱っており、そこへ横から手を出すと日本語のコメントが打てなくなる。効く範囲を絞れない道具は使わない。

**絞り込みの入力欄でも変換中は篩を止める**: `search.tsx` に揃うが、あれは文書全体の検索を作り直す重さがあるからそうしている。篩は手元の配列を舐めるだけであり、止めれば入力欄が固まったように見えるだけで得るものが無い。

**日本語 IME を作業機に有効化して実際に打って確かめる**: いちばん確かだが、利用者の macOS の入力ソース設定を勝手に足すことになる。`setMarkedText:` は IME が WKWebView へ話しかける経路そのものであり、そこまでは測れた。**残る一段（実際の Kotoeri での確定操作）は測れていない**ことを、この ADR に明記して残す。

## 結果

- `src/input/ime.ts` が増えた。`isComposingKey` と `blockComposingSubmit` の 2 つである。`src/input/` という置き場所も新しい。
- 変換中の打鍵を扱わなくなったコンポーネントは**上の監査の表のとおり**である。`<form>` には `blockComposingSubmit` の関所が付き、`⏎` / `esc` / `↑` `↓` を扱うハンドラには先頭の判定が入った。数はここに書かない。入力欄を足せば増えるものであり、表と数字の 2 箇所を合わせ続けることになるためである。
- **`App.tsx` と Rust 側は触っていない。**`App.tsx` の `keydown` が `⌘` を必須にしていることを確かめたうえでの判断である。
- テストは、**変換中は発火しないことと、変換していないときは今までどおり発火することの両方**を見ている。片方だけだと `⏎` を丸ごと殺す実装がテストを通ってしまう。jsdom には本物の IME が無いため、`isComposing` を立てた `KeyboardEvent` を組み立てて発火させる形になる。**それが実機を写している保証は、上に書いた WKWebView での実測から取っている**（`isComposing` が真になること・`preventDefault()` で送信が止まること）。テストが通ることと実機で直っていることは別であり、この ADR の測定がその橋である。
- 暗黙の送信を止めたことの検査は、`fireEvent` の戻り値（`preventDefault()` されたら偽）で見ている。jsdom は暗黙の送信そのものを行わないため、送信されなかったことを直に見ることはできない。
