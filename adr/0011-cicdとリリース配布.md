# ADR 0011: CI/CD とリリース配布

- ステータス: 承認（「署名しない」の 1 点のみ [0028](0028-配布物の署名と公証.md) が覆した）
- 日付: 2026-09-02

## 状況

小槌は macOS 向けのデスクトップアプリであり、配布物は `.dmg` である。手元でビルドして手で配ると、ビルドした環境の差が成果物に混ざり、どのコミットから作ったのかも残らない。GitHub Actions で作って GitHub Releases に置く。

配布先は GitHub の**イミュータブルリリース**を想定する。これは公開したリリースのタグとアセットを凍結する仕組みで、後から差し替えも削除もできない。取り返しがつかないぶん、公開前の検査と手順の設計に重みがある。

Apple の Developer Program には加入していない。したがって Developer ID による署名も公証（notarization）もできない。**この前提は後に変わった。**加入したため、署名と公証は [0028](0028-配布物の署名と公証.md) で行うようにした。以下の「署名しない」に関わる記述はその範囲で覆っている。

## 決定

### ワークフローは 2 本

- `ci.yml` — プルリクエスト（全ブランチ）と `main` への push で走る検査。
- `release.yml` — `v*` タグの push で走る配布物の作成。

CD 側で検査を再実行しない。CI が緑であることを確かめてからタグを打つ運用にする。

### CI の中身

| ジョブ           | ランナー     | 内容                                                                        |
| ---------------- | ------------ | --------------------------------------------------------------------------- |
| フロントエンド   | ubuntu-latest | `bun run build`（`tsc` + vite） / `vitest` / `oxlint` / `prettier --check` |
| Rust とスクリプト | macos-15     | `cargo fmt --check` / `cargo clippy -D warnings` / `cargo test` / `scripts/check-release-tag.test.sh` |

`oxlint` は `--deny-warnings`、`clippy` は `-D warnings` を付け、警告 1 件で赤にする。導入時点でどちらも警告ゼロであり、締めるなら今が一番安い。

Oracle の統合テストは CI では走らせない。`KODUCHI_TEST_ORACLE_URL` を設定しないので、[[0010-テストとリンタの構成]] の取り決めどおり自動で飛ばされる。カバレッジも計測しない。

Tauri のフルビルドは CI に含めない。リリース時にだけ行う。

### リリースの手順

1. `scripts/check-release-tag.sh <タグ>` でタグを検査する（後述）。
2. `bun run tauri build --target aarch64-apple-darwin --bundles dmg`。
3. 同じタグの**下書き**リリースが残っていれば削除する。**公開済み**なら何もせず落とす。
4. `gh release create <タグ> --draft --generate-notes` で下書きを作り、dmg を添付する。
5. **公開は人間が GitHub 上で行う。**

対象は Apple Silicon（aarch64）のみ。成果物は dmg 1 つで、ファイル名は Tauri の既定（`koduchi_<バージョン>_aarch64.dmg`）のまま使う。リリース名はタグ名と同じにする。

**Developer ID では署名しない。** 利用者は初回起動時に「開発元を確認できません」の警告を受けるので、システム設定から開く手順を README に書く。ただし ad-hoc 署名（`signingIdentity: "-"`）は付ける。Apple Silicon では未署名のバイナリがそもそも動かないためである。

### 対応 OS とビルドに使う Xcode

**対応 OS は macOS 26.2 以降とする。** `tauri.conf.json` の `bundle.macOS.minimumSystemVersion` に `26.2` を書く。これは `Info.plist` の `LSMinimumSystemVersion` だけでなく、実行ファイルの deployment target にも効く（実測: `LC_BUILD_VERSION` が `minos 26.2` / `sdk 26.2`）。書かなければ Tauri の既定の `10.13` が入る。

**リリースのビルドは Xcode 26.3 で行う。** ランナーは `macos-15` のまま据え置き、`DEVELOPER_DIR` で Xcode だけを選ぶ。macOS 26 の Liquid Glass のアイコン（`src-tauri/icons/Koduchi.icon`）を `Assets.car` へ焼くには `actool` 26 以上が要り、`macos-15` の既定が Xcode 16.4 だからである（そのランナーには 26.3 も入っている）。

**この 2 つは対になっている。** Xcode 26.3 で組むと SDK が macOS 26.2 に上がるため、対応 OS の下限もそこへ合わせる。

**落ちても気づけないので、`release.yml` に検査を 2 つ置く。** `actool` が無い、または 26 未満でも、Tauri は警告を 1 行出して `icon.icns` へ落ちるだけでビルドは緑のまま通り、配布物だけが古い作りになる。ビルドの前に `DEVELOPER_DIR` が実在するかを見て、配る dmg の中身に `Assets.car` と `CFBundleIconName` があるかを見る（[0028](0028-配布物の署名と公証.md) が署名と公証に対して取ったのと同じ考え方である）。

### 配布物のエンタイトルメント

`src-tauri/entitlements.plist` を置き、`tauri.conf.json` の `bundle.macOS.entitlements` から指す。中身は次の 2 つだけとする。

| キー                                                    | 要る理由                                                                                         |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `com.apple.security.cs.disable-library-validation`       | 別途インストールされた Instant Client（`libclntsh.dylib`）を読み込むため（[[0001-oracle接続方式]]） |
| `com.apple.security.cs.allow-dyld-environment-variables` | ODPI-C が見る `DYLD_LIBRARY_PATH` を効かせるため                                                 |

**エンタイトルメントの plist に XML のコメントを書いてはいけない。** `codesign` が使う AMFI のパーサはコメントを構文誤りとして弾き、`Failed to parse entitlements: AMFIUnserializeXML: syntax error near line N` でリリースのビルドだけが落ちる。意図はこの ADR に書く。

`src-tauri/tests/entitlements.rs` が、設定がファイルを指していること・2 つのキーがあること・キーが増えていないこと・コメントが無いことを見張る。

自動アップデータ（Tauri updater）は入れない。成果物の来歴証明（artifact attestation）も付けない。

### バージョンの単一情報源

`tauri.conf.json` の `version` を `"../package.json"` に変え、バージョンの実体を `package.json` と `src-tauri/Cargo.toml` の 2 箇所に減らす。この 2 つとタグ名が一致することを `scripts/check-release-tag.sh` が検査する。同スクリプトはタグの指すコミットが `main` に含まれていることも確かめる。テストは `scripts/check-release-tag.test.sh` にある。

### 版の固定

- Rust は `rust-toolchain.toml` に `1.98.0` を書く。ランナーの `rustup` がこれを読むので、ツールチェインを入れる Action は使わない。
- bun は `oven-sh/setup-bun` に `1.3.11` を明示する。
- macOS ランナーは `macos-15` に固定する。Linux は `ubuntu-latest` のままにする。
- リリースのビルドに使う Xcode は `DEVELOPER_DIR` で `/Applications/Xcode_26.3.app` に固定する（前述の「対応 OS とビルドに使う Xcode」）。
- GitHub Actions はすべて commit SHA でピン留めし、`.github/dependabot.yml` の `github-actions` を週次で回して更新する。

## 理由

- **draft で止める**のは、イミュータブルリリースが公開後の訂正を許さないためである。dmg が実際に開けるかを手元で確かめてから公開ボタンを押せる余地が要る。
- **タグを唯一の引き金**にすると、リリースの意思が履歴に残る。`workflow_dispatch` は誤爆の余地が増えるだけで、間違えたら次のパッチ版を出せば済む。
- **aarch64 のみ**にするのは、個人利用の macOS クライアントで Intel Mac を切り捨てても実害が薄く、ランナー 1 台で完結して構成が最小になるためである。
- **対応 OS を macOS 26.2 以降にする**のは、Liquid Glass のアイコンのために SDK が上がるためである。新しい SDK で組んだものが古い OS でそのまま動く保証は無く、`10.13` を名乗ったまま配ると、利用者の手元で起動してから壊れる。下限を宣言すれば Finder が先に止める。個人利用の macOS クライアントで切り捨ての実害が薄いのは、Intel Mac を切ったのと同じ理屈である。
- **署名しない**のは、年 $99 の Developer Program に加入していないためである。README の手順で回避できる範囲の不便に留まる。
- **エンタイトルメントを付ける**のは、Tauri が macOS の署名で必ずハードンドランタイムを有効にするためである（`hardenedRuntime` の既定が真で、`codesign --options runtime` が付く）。ハードンドランタイムはライブラリ検証を伴い、プロセスは同じ Team ID で署名されたライブラリと Apple のものしか読み込めなくなる。ad-hoc 署名には Team ID が無いため（実測: `flags=0x10002(adhoc,runtime)` / `TeamIdentifier=not set`）、検証を切らないと Instant Client を一切読み込めない。**この壊れ方は手元の `bun run tauri dev` では起きない**（署名を通らないため）ので、リリースしてはじめて気づくことになる。
- **エンタイトルメントを 2 つに絞る**のは、緩めるほど守りが減るためである。JIT 系（`allow-jit` / `allow-unsigned-executable-memory`）は WKWebView が別プロセスで JavaScript を動かすので要らない。App Sandbox を使っていないため、`network.client` や `files.user-selected` も効果を持たない。
- **CI にフルビルドを含めない**のは、PR ごとに数分を払う価値が今の段階では無いためである。リリース時のビルド失敗はタグを打ち直せば回復できる（公開前に落ちるので、イミュータブルリリースとも衝突しない）。
- **版を固定する**のは、CLAUDE.md の「依存関係は必ずバージョンを指定する」に一貫させるためであり、新しい clippy の lint やランナーの更新で、こちらが何もしていないのに CI が赤くなる事態を避けるためである。上げるときは意図して上げる。
- **Dependabot を Actions だけに絞る**のは、npm と cargo まで広げると個人プロジェクトには PR が多すぎるためである。そちらはバージョンを明示して手で上げる運用が既に回っている。

## 却下した案

**`tauri-apps/tauri-action` を使う**: 公式のアクションで、ビルドから下書きリリースの作成・アセット添付までを引き受けてくれる。却下したのは、それが引き受ける複雑さ（多プラットフォームの行列・updater の `latest.json` 生成・署名鍵の受け渡し）を今回どれも使わないためである。やることが「ビルドして dmg を 1 個上げる」だけなら、4 手が YAML にそのまま並ぶほうが読んで分かる。

将来 updater や多プラットフォームに手を伸ばすなら移行する。そのときは `release.yml` の「dmg をビルドする」から「dmg を添付する」までの 4 ステップを `tauri-action` 1 つに置き換える。`releaseDraft: true` を渡せば下書きで止まる点は変わらず、`args: --target aarch64-apple-darwin --bundles dmg` で成果物も同じ名前になる。タグ検査のステップはその前段にそのまま残す。

**自動アップデータを入れる**: Tauri の updater は Apple の署名とは別の minisign 鍵で動くので、未署名でも成立はする。却下したのは、`latest.json` を「常に最新を指す URL」として置く先が要り、公開後に差し替えられないイミュータブルリリースと素直に噛み合わないためである。未署名アプリの自動更新は Gatekeeper との相性も悪い。入れるときは別の ADR を立てる。

**成果物に来歴証明（`actions/attest-build-provenance`）を付ける**: 未署名のアプリを配る個人プロジェクトで、利用者が `gh attestation verify` を実行する場面は想定しにくい。イミュータブルリリースによる凍結で足りると見た。

**タグから 3 つのファイルのバージョンを自動で書き換えてコミットする**: タグとコミットの前後関係がねじれる。検査して落とすほうが単純である。

**Oracle の統合テストを CI で走らせる**: Linux ランナー上で Oracle コンテナ（初回起動が数分）と Instant Client の導入が要る。[[0010-テストとリンタの構成]] が「Docker が無い環境でも `cargo test` は緑」と決めている以上、CI もその前提に乗るのが素直である。必要になったら `main` への push とタグのときだけ走る別ジョブとして足す。

**カバレッジに閾値を設ける**: 閾値は、無ければ数字を見るだけで終わり、あればテストのための無意味なテストを誘発する。

**GitHub Actions をメジャータグ（`@v4`）で参照する**: 更新は楽だが、タグは動かせるので参照先の中身が変わりうる。Dependabot が SHA も面倒を見てくれるため、ピン留めの負担は実質ない。

## 結果

- イミュータブルリリースの有効化（リポジトリの Settings）は、1 本目のリリースを通して dmg が開けることを確かめてから行う。有効化する前は下書きだけでなく公開済みリリースも削除できるが、`release.yml` は有効化後と同じ前提で動く（公開済みのタグには触らない）。
- 利用者は初回起動で警告を受ける。Developer Program に加入したら、`release.yml` のビルドステップに署名の環境変数を足し、公証のステップを継ぎ足せばこの ADR の他の決定は動かさずに済む。
- 対応 OS の下限とビルドに使う Xcode の版は対になっている。**片方だけを動かさないこと。**Xcode を下げれば Liquid Glass のアイコンが黙って落ち、下限だけを下げれば新しい SDK で組んだものを古い OS へ配ることになる。
- Rust の版を上げるときは `rust-toolchain.toml` を書き換える。Dependabot は Rust のツールチェインを見ないので、気づくのは人間の仕事である。
