# ADR 0022: テーブル定義タブ

- ステータス: 承認
- 日付: 2026-09-08

## 状況

テーブル定義ビュー（[[0019-テーブル定義ビューとddlの取得]]）は 2 つのことを同時に決めた。**何を出すか**（列・制約・索引・DDL の 4 つ）と、**どこに出すか**（ツリーの行の右の「定義」から開くオーバーレイ）である。前者は使われている。後者に不満が出た。

利用者の言葉をそのまま引く。

1. 「右クリックメニューでテーブル定義を開く的な項目が欲しい」
2. 「逆に定義ボタンいらないな」
3. 「テーブル定義 view は新しいタブで開いてほしい」

3 つは別々の要望に見えるが、根は 1 つである。**定義ビューは「ちらっと見る」ものではなく「開いたまま作業する」ものだった。**

- オーバーレイは画面を覆う。定義を見ながら SQL を書けない。閉じて、書いて、また開く。
- オーバーレイは 1 枚しか開けない。`ORDERS` と `SHIPMENTS` の列を見比べるには、行き来しながら覚えておくしかない。
- ツリーの行の右の「定義」は、幅 180〜480px のサイドバーで**長い名前に押し潰される**。`ORDER_ITEM_ARCHIVE_2024` の右に 20px の札を置けば、名前のほうが削れる。
- [[0020-スキーマツリーからの操作]] が右クリックのメニューを作った。[[0019-テーブル定義ビューとddlの取得]] が「入口を右クリックにする」を却下したのは、**そのときツリーに右クリックのメニューが 1 つも無かったから**である（「ここで作るとツリーからの操作を作る波と真正面からぶつかる」）。その理由は 0020 が済んだ今、消えている。

決めるべきことは 6 つある。

1. どの器に載せるか（エディタのタブ帯 / 結果ペインのタブ / オーバーレイのまま）
2. タブが 2 種類になったとき、タブの並びをどう表すか
3. 定義タブをセッション（[[0005-クエリ履歴とセッション復元のsqlite]]）に保存するか
4. 同じオブジェクトの定義タブを 2 枚開かせるか
5. `definition` ストアが前提にしていた「開いている定義は高々 1 つ」をどう解くか
6. ツリーの入口をどう変えるか（右クリックの項目・「定義」ボタンの後始末・キーボード）

なお、タブ帯そのもの（`TabBar.tsx`）と並び替え（ADR 0023）は別の波が触っている。**この ADR はタブの「種類」だけを足し、並び順・選択・閉じるの手続きには手を入れない。**

## 決定

### 定義はエディタのタブ帯に、定義タブとして開く

`無題-1.sql` が並ぶ 34px の帯（`TabBar.tsx`）に、SQL タブと横並びで置く。**[[0019-テーブル定義ビューとddlの取得]] の「オーバーレイに出す」は、この ADR で覆す。**

タブ帯を選んだのは、定義が**開いたまま作業するもの**だからである。タブは小槌の中で唯一「開いたまま、行き来しながら使う」ことになっている器である。何枚でも開け、並び替えられ（ADR 0023）、`⌘W` で閉じられる。オーバーレイに足りなかったものが全部ここにある。

**結果ペインの動的タブにはしない。**この点だけは 0019 の判断を引き継ぐ。あの器はエディタタブごとの実行結果に紐付いており、どのエディタタブにも属さない定義を置くと、タブを切り替えるたびに現れたり消えたりする（[[0009-ウィンドウモデルとタイトルバー]]・[[0017-セッションとロックの確認]] と同じ理由）。**サイドバーにも別ウィンドウにもしない。**理由は 0019 のまま変わらない。

### 定義タブを選んでいる間は、エディタも結果ペインも出さない

本体の領域をまるごと定義ビューが使う。SQL タブへ戻れば、これまでどおりエディタと結果ペインが出る。

結果ペインを残す道もあった。だが**定義は実行の結果ではない。**定義タブには実行するものが無く、結果ペインは「SQL を実行すると、ここに結果が出ます」を出したまま画面の下半分を占め続ける。エディタも同じで、定義タブに紐付く SQL は存在しない。空の器を 2 つ並べて場所を取るより、定義に全部渡すほうが読める。

そのため、`⌘S`（保存）・`⇧⌘S`（クエリを保存）・`⌥⌘S`（CSV）・`⌘E` / `⇧⌘E`（実行計画）・実行のすべては、定義タブを選んでいる間は**何もしない**。判定は `selectActiveSqlTab` の 1 か所に寄せ、「今のタブの SQL」を要る操作はすべてそこを通す。例外は履歴と保存済みクエリの「エディタへ入れる」だけで、これは**新しい SQL タブを開いてそこへ入れる**。押しても何も起きない項目にするより素直である。

### タブは判別つきの union にし、並びは 1 本のままにする

```
type EditorTab = SqlTab | DefinitionEditorTab
```

`kind` で判別し、`tabs: EditorTab[]` という 1 本の配列に混ぜて並べる。SQL タブは内容・保存先・未保存の印を持ち、定義タブは対象（所有者・名前・種別）だけを持つ。

**2 本の配列に分けない。**分けると「タブ帯に出す順番」を第 3 の情報として別に持つことになり、並び替え（ADR 0023）がその 3 つを同時に守る羽目になる。1 本の配列であれば、並び替えも選択も閉じるも**種類を知らないまま**書ける。実際、`closeTab` / `selectTab` には 1 行も足していない。

種類による振り分けは `src/stores/tabKinds.ts` の純粋な関数へ寄せた（`isSqlTab` / `isDirty` / `openDefinitionTab` / `toSessionTabs` / `fromSessionTabs`）。ストアの手続きから切り離してあるのは、混ざった並びの扱いをテストで固めるためである。

### 定義タブはセッションに保存しない

再起動すると定義タブは消え、SQL タブだけが戻る。

**定義は接続に属するからである。**[[0019-テーブル定義ビューとddlの取得]] は切断時に定義を捨てると決め、`App.tsx` が `clearDefinition()` を呼んでいる。一方セッション（[[0005-クエリ履歴とセッション復元のsqlite]]）は**接続を復元しない**。小槌は起動すると接続を選ぶ画面から始まる。定義タブを保存すれば、起動直後には中身を出せない空のタブが並ぶ。しかも次に繋ぐ先が別の接続なら、そのオブジェクトは存在すらしない。

SQL タブを保存するのは、それが**書きかけの文章**であり、接続に依らず利用者だけが持っているものだからである。定義タブが持っているのは `KODUCHI.SHIPMENTS` という 3 語だけで、失っても右クリック 2 回で戻る。**保存する値打ちと、嘘の状態で復元する害が釣り合わない。**

落とす場所は**書き出す側**にした。`toSessionTabs` が SQL タブだけを選び出す。定義タブを選んだまま終えたときは、その選択も落とす（並びに居ないタブを指したまま保存しない）。読む側で振り分けないのは、SQLite に定義タブが 1 行も入らない以上、振り分ける相手が居ないためである。**Rust 側（`session_tab` / `session_state`）には手を入れていない。**列も増えず、古い `history.sqlite3` の扱いも変わらない。

### 同じオブジェクトの定義タブは 2 枚開かない

既に開いているタブがあれば、そのタブへ移る。判定は所有者・名前・種別の 3 つがすべて一致したときだけである（同名で種別の違うオブジェクト — 表とその索引 — は別の対象である）。

定義は**読むだけの画面**であり、2 枚並べても片方は必ずもう片方と同じものを映す。編集できるものが 2 枚あるなら別々の状態に意味があるが、ここには無い。開いたぶんだけ `ALL_TAB_COLUMNS` などへの問い合わせが増える点も、同じものを 2 度取る理由にならない。

`openFile` が同じファイルのタブへ移るのと同じ振る舞いである。タブ帯の中で規則が揃う。

### `definition` ストアはタブごとに持つ

`target` 1 つを持つ形をやめ、**タブの ID を鍵にした表**（`byTab`）にする。列・制約・索引・DDL・絞り込み語・開いている内訳のタブを、タブ 1 枚につき 1 組ずつ持つ。取得の世代もタブごとに数える。

- タブを閉じたら `drop(tabId)` でそのタブぶんを捨てる。`App.tsx` の `closeTabAndRelease` が呼ぶ（結果セットの解放・列幅の忘却と同じ場所である）。
- 切断したら `clear()` ですべて捨てる。[[0019-テーブル定義ビューとddlの取得]] のままである。
- **一度読んだ定義は取り直さない。**タブを選び直すたびに問い合わせては、開いた枚数だけ往復が増える。読み直したいときはタブを閉じて開き直す。
- **閉じたあとに届いた取得の結果は捨てる。**書き込みは「そのタブが今もある」ときだけ通す。消えたタブが取得の完了で蘇ってはいけない。

取得の経路は変えていない。プールの `background_handle` で取り、利用者の結果セットのカーソル（[[0003-結果セットのカーソル保持と接続プール]]）には触れない。**定義タブを何枚開いても、実行中の結果は壊れない。**

### `esc` では閉じない

定義タブは `⌘W` で閉じる。`esc` は何もしない。

設定画面・セッションパネル（[[0017-セッションとロックの確認]]）・ソース検索（[[0021-オブジェクトのソース検索]]）が `esc` で閉じるのは、それらが**画面に重なっているもの**だからである。重なったものを退けるのが `esc` の役目であり、タブは重なっていない。SQL タブが `esc` で閉じない以上、隣に並ぶ定義タブだけが閉じるのは説明できない。

### タブの名前はオブジェクト名 1 つ、見分けはアイコンで付ける

`SHIPMENTS` と出し、名前の左に `lucide-react` の `TableProperties` を 12px で添える。所有者と種別はタブ帯には出さず、定義ビューの見出しに出す。

**`SHIPMENTS の定義` にはしない。**タブ 1 枚は細く、「の定義」の 3 文字ぶん名前が削れる。10 枚も開けば全部が「…の定義」で終わり、肝心の名前が読めない。**`KODUCHI.SHIPMENTS` とも書かない。**同じ理由である。

SQL タブとの見分けはアイコンが担う。SQL タブの名前は必ず `.sql` で終わる（`無題-1.sql` かファイル名）ため文字でも見分けは付くが、アイコンのほうが速い。支援技術には `aria-label` で `SHIPMENTS の定義` と伝える。

**定義タブに `●` の印は出さない。**編集できないため未保存になりようがなく、閉じるボタンが常に出る。

### 入口は右クリックのメニューの「定義を開く」1 つ

`SchemaTreeContextMenu` に 4 つめの項目として足す。**並びは末尾**である。

- 先に入っていた 3 項目（[[0020-スキーマツリーからの操作]] の「名前をコピー」「エディタへ挿入」「`SELECT` を開く」）の位置を動かさない。
- 「`SELECT` を開く」と同じく**タブが増える**操作であり、その手前に軽い 2 つが並ぶ形は保たれる。

**オブジェクトの行にだけ出す。**12 種別すべてに出し、例外は設けない（[[0019-テーブル定義ビューとddlの取得]] の「すべての種別の行に出す」をそのまま引き継ぐ。制約と索引の内訳が空になる種別はあるが、DDL の値打ちが最も大きいのはむしろファンクション・プロシージャ・パッケージである）。スキーマの行と列の行は定義を持たないため出さない。未接続のときも出さない。

判定は `canOpenDefinition` と `definitionTargetOf` という純粋な関数で、`canOpenSelect` と同じ場所（`SchemaTree.tsx`）に置く。

### 「定義」のボタンと `data-row-action` の仕組みは消す

ボタンを消し、それを支えていた `ROW_ACTION`（`data-row-action` を持つ要素の上ではダブルクリックの挿入を起こさない細工）も一緒に消す。オブジェクトの行は、行そのものだけを持つ 1 つの `button` へ戻る。

**使う人が居なくなった仕組みを、将来のために残さない。**残せば「なぜこの分岐があるのか」を読む人が毎回確かめることになり、確かめた末に「今は誰も使っていない」と分かる。その代わり、**行の右に押しどころを足すときの作法は [[0020-スキーマツリーからの操作]] に書いてある**（表に 1 行を足し、`data-row-action` を付けてダブルクリックの対象から外す）。必要になったら 3 行で戻せる。

副産物として、オブジェクトの行の焦点が 1 つに戻った。[[0020-スキーマツリーからの操作]] は「焦点は行そのものが持ち、『定義』へは `Tab` で降りる」としていたが、降りる先が無くなった。roving tabindex の枠は行 1 つぶんのままである。

### ツリーの中の `⌘D` で定義を開く

[[0020-スキーマツリーからの操作]] がツリーに置いた `⌥⏎`（挿入）/ `⌘C`（コピー）に 1 つ足す。焦点のある行の定義タブを開く。

ツリーの中でしか意味を持たないため、`App.tsx` ではなく `SchemaTree` の `keydown` に置く（`CLAUDE.md` の「キーバインドの置き場所」）。`⌘D` はどこにも割り当てられておらず、`⌘K`（コマンドパレット）・`⌘I`（予約）・`⇧⌘F`（ソース検索）とも食い合わない。`D` は Definition の頭文字である。

**マウス操作の割り振りには 1 行も足さない。**単クリックは開閉、ダブルクリックは挿入、右クリックはメニュー。表はむしろ 3 行減った（「定義」の 3 行が消えた）。

## 理由

- **器を変えただけで、中身は変えていない。**列・制約・索引・DDL の出し方、`SET_TRANSFORM_PARAM`、`GET_DDL` の型名、`NOT NULL` の検査制約を落とす判断、索引を自動生成も含めて出す判断 — [[0019-テーブル定義ビューとddlの取得]] が決めたことは 1 つも覆していない。覆したのは「どこに出すか」だけである。ADR を「後から 1 件だけ覆す」単位で切ってあることが効いた。
- **タブの union を選んだ**のは、定義タブが持つものと SQL タブが持つものに重なりがほとんど無いからである。1 つの型に全部の項目を詰めて `content` を空文字列にする手もあるが、それでは「定義タブの内容を書き換える」が型の上で書けてしまう。書けないことを型で言えるなら、そちらを選ぶ。
- **セッションに保存しない**のは、保存したものを**正しく戻せない**からである。接続を復元しない以上、定義タブは復元先を持たない。戻せないものを保存するのは、利用者に「戻るはずだ」と思わせるぶんだけ害がある。
- **ストアをタブごとにした**のは、器が「高々 1 つ」から「何枚でも」へ変わった以上、状態の形もそれに合わせるほかないためである。ここを単数のまま「選ばれたタブのぶんだけ取りにいく」形にすると、タブを切り替えるたびに問い合わせが飛ぶ。
- **入口を右クリックへ移した**のは、利用者の求めそのものであると同時に、**ツリーの行の幅を名前に返す**ためでもある。サイドバーは 180px まで狭められる。
- **`data-row-action` を消した**のは、[[0020-スキーマツリーからの操作]] がその作法を文章として残しているためである。仕組みは消せるが、決定は残る。

## 却下した案

**オーバーレイのままにして、右クリックの項目だけを足す**: 差分は最小になる。しかし 3 つの要望のうち 1 つしか満たさない。定義を見ながら SQL を書けないことも、2 つの表を見比べられないことも、そのまま残る。

**結果ペインの動的タブとして出す**: [[0019-テーブル定義ビューとddlの取得]] が却下したとおりである。エディタタブごとの実行結果に紐付いた器であり、どのエディタタブにも属さない定義を置くと、タブを切り替えるたびに現れたり消えたりする。この点は 0022 でも覆さない。

**定義タブでも結果ペインを出したままにする**: 画面の切り替わりが小さく、目が驚かない。しかし定義タブには実行するものが無く、結果ペインは空のまま下半分を占め続ける。利用者も「この場合結果ペインはいらないかな」と言っている。

**タブを 2 本の配列（SQL タブと定義タブ）で持つ**: それぞれの型が素直になる。しかしタブ帯に出す順番を第 3 の情報として持つことになり、並び替え（ADR 0023）が 3 つを同時に守ることになる。混ぜたほうが、並び替えも選択も閉じるも種類を知らずに書ける。

**SQL タブの型に定義用の項目を足す（`content` は空文字列、`target` は省略可）**: 型が 1 つで済む。だが「定義タブの内容を書き換える」が型の上で書けてしまい、書けてしまうものはいつか書かれる。

**定義タブをセッションに保存する**: 再起動しても続きから読める、ように見える。しかし小槌は接続を復元しない（[[0005-クエリ履歴とセッション復元のsqlite]]）。起動直後の定義タブは中身を出せず、次に繋ぐ先が別の接続ならオブジェクトごと存在しない。「戻ってきたが空」は、戻ってこないより分かりにくい。

**定義タブを保存し、復元時に接続まで復元する**: 筋は通る。だが 1 接続 = 1 ウィンドウ（[[0009-ウィンドウモデルとタイトルバー]]）で、接続にはキーチェーンからのパスワード取得と Instant Client の初期化が要る。起動のたびに勝手に繋ぐのは、[[0004-認証情報と接続設定の保存先]] が「接続は利用者が選ぶ」としてきた形を変えることになる。定義タブ 1 つのために動かす決定ではない。

**同じオブジェクトの定義タブを何枚でも開かせる**: `⌘T` が何枚でも空のタブを開くのと揃う。しかし定義は読むだけの画面であり、2 枚目は必ず 1 枚目と同じものを映す。同じ問い合わせを 2 度打つ理由も無い。

**タブ名を `SHIPMENTS の定義` にする**: SQL タブとの見分けが文字だけで付く。しかしタブ 1 枚は細く、10 枚開けば全部が「…の定義」で終わって名前が読めない。見分けはアイコンで足りる。

**`esc` で定義タブを閉じる**: オーバーレイ時代の指が覚えている。しかし `esc` は重なったものを退けるキーであり、タブは重なっていない。SQL タブが `esc` で閉じない以上、隣のタブだけが閉じるのは説明できない。

**`data-row-action` の仕組みを将来のために残す**: 次に行の右へ何かを足すときにそのまま使える。しかし使う人の居ない分岐は、読む人が毎回「誰が使っているのか」を確かめる代償を払う。作法は [[0020-スキーマツリーからの操作]] に文章で残っており、3 行で戻せる。

**右クリックの「定義を開く」を先頭に置く**: 最も押される項目なら最短にすべきではある。しかし [[0020-スキーマツリーからの操作]] が決めた 3 項目の位置が全部 1 つずつ下へずれる。既に指が覚えている並びを、後から入る項目のために動かさない。

**行のダブルクリックで定義を開く**: 押しどころを増やさずに済む。しかしダブルクリックは [[0020-スキーマツリーからの操作]] が挿入に割り当て済みであり、その決定を覆す理由が無い（挿入のほうが軽く、誤爆の代償も小さい）。

**キーを足さない**: 覚えるものが増えない。しかしツリーはキーボードだけで辿れるように作ってある（[[0020-スキーマツリーからの操作]] の `↑` / `↓` / `→` / `←` / `⌥⏎` / `⌘C`）。そこに右クリックでしか届かない操作を 1 つ置くと、キーボードだけの道が途切れる。

## 結果

- `EditorTab` が union になった。`tab` ストアの `updateContent` / `markSaved` / `openFile` は SQL タブだけを触るようになったが、**`closeTab` / `selectTab` には 1 行も足していない**。並び替え（ADR 0023）が入っても混ざらない。
- `src/stores/tabKinds.ts` が増えた。混ざった並びの扱い（見分け・足す・セッションへ出す・戻す）の純粋な関数だけを置く場所である。
- `selectActiveSqlTab` が増えた。**「今のタブの SQL」を要る操作はすべてここを通す。**足し忘れると、定義タブを選んだまま実行や保存が走る。
- `definition` ストアが `byTab` になった。`open` / `setSearch` / `selectTab` / `drop` のすべてがタブの ID を取る。`close` は無くなった（タブを閉じることが定義を閉じることである）。
- `TableDefinitionPanel` はオーバーレイではなくなり、`role="dialog"` と閉じるボタンと `esc` の受けを落とした。`connectionId` に加えて `tabId` を取る。**中身（4 つの内訳・絞り込み・件数・権限不足の見せ方）は変えていない。**
- `TabBar.tsx` への差分は分岐 2 つ（アイコンと `aria-label`、`●` 印の判定を `isDirty` へ）に留めた。タブ帯の構造には手を入れていない（ADR 0023 の持ち物である）。
- `SchemaTree` が `connectionId` を受け取らなくなり、代わりに `onOpenDefinition` を受け取る。定義ストアを直接触らなくなったぶん、結合が 1 本減った。
- **ツリーのマウス操作の割り振りが 3 行減った。**「定義」を単クリック / ダブルクリック / 右クリックの 3 行が消え、残るのは行に対する 3 つだけである。`CLAUDE.md` の表もそれに合わせた。
- [[0019-テーブル定義ビューとddlの取得]] の「定義ビューは `SessionsPanel` と同じオーバーレイに出す」「入口はツリーの行の右の『定義』1 つだけ」に、この ADR で覆した旨を追記した（[[0009-ウィンドウモデルとタイトルバー]] に [[0018-保存済みクエリとコマンドパレット]] が同じことをした先例がある）。
- 定義タブを開いたまま `⌘S` を押しても何も起きない。**保存されないことを利用者に伝える表示は出していない。**タブ帯を見れば SQL でないことは分かるためである。ここは実際に使ってみて足りなければ足す。
