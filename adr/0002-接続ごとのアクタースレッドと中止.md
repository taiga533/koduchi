# ADR 0002: 接続ごとのアクタースレッドと実行の中止

- ステータス: 承認
- 日付: 2026-08-30

## 状況

`oracle` crate は ODPI-C の同期 API であり、クエリ実行はスレッドをブロックする。Tauri のコマンドを async として定義しても、その中で同期的にブロックすれば tokio のワーカースレッドを占有し、UI の応答が止まる。

またデザインには実行中の状態（状態 5a）に「中止」ボタンがあり、走っているクエリを外部から止める経路が必要である。

docs.rs で確認した事実:

- `oracle::Connection` は `Send` と `Sync` の両方を実装する。
- `pub fn break_execution(&self) -> Result<()>` が存在し、"Cancels execution of running statements in the connection" と記載されている。公式ドキュメント自体が `Arc<Connection>` を別スレッドに渡してキャンセルする例を載せている。

## 決定

**接続ごとに専用の OS スレッドを立て、mpsc チャネルで命令を送るアクター方式**を採用する。

- 各アクタースレッドが `Arc<Connection>` を所有し、実行・スキーマ取得・実行計画生成をそのスレッド上で同期的に行う。
- 結果は oneshot チャネルで呼び出し元に返す。
- 中止は `Arc<Connection>` の複製を保持する別の経路から `break_execution()` を呼ぶ。

データベース抽象化として、次の 5 メソッドを持つ狭い `Driver` trait を定義する。

```rust
trait Driver {
    fn connect(...);
    fn execute(...);   // チャンク取得用のカーソルを返す
    fn cancel(...);
    fn fetch_schema(...);
    fn explain(...);
}
```

Oracle 固有の概念 — `DBMS_OUTPUT` の取得、tnsnames.ora の解決、Instant Client の検出 — は **trait の外**に置き、Oracle モジュールに閉じ込める。

## 理由

- アクター方式だけが、接続をまたいだ状態（トランザクション）の保持と、外部からの中止の両方を満たす。
- `Connection` が `Sync` であることを確認済みのため、中止経路の実現に不確実性はない。
- Driver trait を 5 メソッドに絞ることで、上位層（Tauri コマンド、履歴記録、CSV 書き出し）をデータベース非依存に保ちつつ、Oracle の都合が trait に漏れるのを防げる。実装が 1 つしかない段階で広い trait を定義すると、PostgreSQL 追加時に必ず作り直しになる。

## 却下した案

**`tokio::task::spawn_blocking` に毎回投げる**: 実装は素直だが、接続をまたいだ状態を保てず、実行中のクエリを中止する経路も作れない。

**trait を切らず Oracle 実装だけを作る**: 上位層に Oracle の型が漏れ、PostgreSQL 追加時の影響範囲が読めなくなる。

**最初から全機能を網羅する広い trait を定義する**: 実装が 1 つしかない現時点の情報量では、境界を必ず外す。

## 結果

- Tauri コマンドは薄い層になり、アクターへ命令を送って結果を待つだけになる。
- 接続の本数と寿命の管理は [[0003-結果セットのカーソル保持と接続プール]] で扱う。
- `DBMS_OUTPUT` は Oracle モジュール内で実行後に `GET_LINES` を呼び、実行結果に添えて返す。
