# ADR 0021: オブジェクトのソース検索

- ステータス: 承認
- 日付: 2026-09-08

## 状況

業務で最も多い「調べもの」のもう 1 つが、**この表を触っているのはどの処理か**を突き止めることである。列を 1 本足す前に、あるいは値がいつの間にか書き換わる理由を探すときに、まず知りたいのは「その名前を本文に含む処理の一覧」である。小槌にはその導線が無く、利用者は `ALL_SOURCE` を叩く SQL を手で書くことになる。書けたとしても、当たった行の前後を読むにはもう 1 本問い合わせが要る。

スキーマツリー（[[0007-スキーマ取得の段階的ロード]]・[[0014-スキーマツリーのオブジェクト種別拡張]]）は名前しか持たず、補完（[[0013-補完の候補生成と識別子の出力スタイル]]）とコマンドパレット（[[0018-保存済みクエリとコマンドパレット]]）も名前を絞るだけである。**本文は今のところどこからも探せない。**

Oracle のドキュメントで確認した事実:

- `ALL_SOURCE` は PL/SQL の本文を 1 行 1 レコードで持ち、`OWNER` / `NAME` / `TYPE` / `LINE` / `TEXT` を返す。`TYPE` に並ぶのは `FUNCTION` / `PROCEDURE` / `PACKAGE` / `PACKAGE BODY` / `TRIGGER` / `TYPE` / `TYPE BODY` と `JAVA SOURCE` である。
- **ビューの本文は `ALL_SOURCE` に無い。** `ALL_VIEWS.TEXT` にあり、その型は `LONG` である。`LONG` の列は `where` 句で `like` に掛けられない。12.2 以降にある `TEXT_VC` は `VARCHAR2(4000)` であり、それより長いビューは先が落ちる。どちらも行番号を持たない。
- `ALL_*` ビューは**参照権限のあるオブジェクトしか返さない**。権限が無いときは `ORA-00942` になる。
- `ALL_SOURCE` は中規模のデータベースでも数十万〜数百万行になる。`upper(text) like upper('%語%')` は索引の当たらない全表走査であり、絞りを入れないと数十秒帰ってこない。

既存の決定と噛み合わせる必要のある点が 3 つある。

1. **結果セットのカーソルは接続 1 本につき高々 1 つである**（[[0003-結果セットのカーソル保持と接続プール]]）。重い検索のために利用者が見ている結果セットを壊してはならない。
2. **`PACKAGE BODY` と `TYPE BODY` はツリーに出していない**（[[0014-スキーマツリーのオブジェクト種別拡張]]）。仕様と同じ名前で 2 行並ぶだけだからである。しかしソース検索では**本体こそが探し先**である。
3. **`⌘K` のコマンドパレットが既にある**（[[0018-保存済みクエリとコマンドパレット]]）。あれは取得済みのものを打鍵ごとに絞る道具であり、ソース検索はデータベースへ投げて待つ道具である。

## 決定

### `Driver` trait に `search_source` と `source_context` を足し、プールの背面の接続で走らせる

スキーマ取得・実行計画・セッション一覧（[[0017-セッションとロックの確認]]）と同じく、`ConnectionPool::background_handle()` が選んだ接続で読む（[[0003-結果セットのカーソル保持と接続プール]]）。この経路は `Connection::query` を直接使い、`OracleDriver` が持つカーソルには一切触れない。**利用者が見ている結果セットは、何度探し直しても壊れない。**

`search_source` は当たり行を、`source_context` は当たった行の前後を返す。問い合わせの組み立ては `src-tauri/src/db/oracle/source.rs`、結果のまとめ方と型は Oracle に依存しない `src-tauri/src/db/source.rs` に置く。[[0017-セッションとロックの確認]] の `sessions.rs` と同じ切り方である。

### 探し先は `ALL_SOURCE` の PL/SQL 7 種別。ビューは対象にしない

`FUNCTION` / `PROCEDURE` / `PACKAGE` / `PACKAGE BODY` / `TRIGGER` / `TYPE` / `TYPE BODY` を探す。`JAVA SOURCE` は `ALL_SOURCE` に載るが PL/SQL ではなく、PL/SQL を探しに来た利用者の一覧を汚すだけであるため拾わない。

**ビューの本文は探さない。** `ALL_VIEWS.TEXT` は `LONG` であり、`where` 句で `like` に掛けられない。掛けるには全ビューの本文をいったん取り出すか、`TO_LOB` で一時表へ写すか、PL/SQL のループを書くしかない。どれも「重い問い合わせを軽くする」という本 ADR の主目的と正面から衝突する。`TEXT_VC` を使う道もあるが、4000 字を超えるビューでは先が黙って落ちる。**当たらなかったのか、見ていないのかを利用者が見分けられない。** これは [[0004-認証情報と接続設定の保存先]] が退けた「表示が嘘になる」のと同じ害である。加えて `ALL_VIEWS` には行番号が無く、当たった行とその前後という結果の形も作れない。

対象外であることは画面に書く。**黙って外さない。**

### `PACKAGE BODY` と `TYPE BODY` は結果に出す。ツリーの決定とは矛盾しない

検索結果の種別は `SourceKind` という**別の列挙**で持ち、ツリーの `ObjectKind`（[[0014-スキーマツリーのオブジェクト種別拡張]]）とは共有しない。

[[0014-スキーマツリーのオブジェクト種別拡張]] が本体を落としたのは、**ツリーに仕様と本体が同じ名前で 2 行並ぶと区別が付かない**からである。名前だけを並べる場所での判断であった。ソース検索が返すのは名前ではなく**当たった行**であり、仕様に無い行が本体に当たったという事実そのものが結果である。同じ名前で 2 件出ても、それぞれ違う行を提げているため紛れない。念のため、結果の各行には「パッケージ本体」「型の本体」と種別の印を添える。

語彙を分けたことで、ツリーに 1 つも表れない種別を検索が出しても矛盾しない。ツリーは「どんなオブジェクトがあるか」、ソース検索は「どこに書いてあるか」を答える別々の道具である。

### 重さは 3 つの関所で抑える

1. **検索語は 2 文字以上。** 1 文字は `ALL_SOURCE` のほぼ全行に当たり、上限まで拾って終わるだけである。Rust 側で弾き、画面でも押せなくする。
2. **所有者と種別の絞り込みを `like` より先に効かせる。** 種別は `type in (...)` として問い合わせに組み込み、**落とした種別は問い合わせにも行かない**（[[0014-スキーマツリーのオブジェクト種別拡張]] と同じ考え方）。所有者はスキーマを 1 つ選べる。既定は「すべてのスキーマ」だが、その場合も**システムスキーマは外す**。外さないと `SYS` の PL/SQL だけで上限が埋まる。除外の一覧は [[0007-スキーマ取得の段階的ロード]] の「システムスキーマを除外」と同じものを使う。
3. **当たり行に上限を置く（既定 500）。** `where rownum <= 上限 + 1` を外側に掛け、Oracle に上限へ達した時点で走査を止めさせる（`COUNT STOPKEY`）。**そのために `order by` を付けない。** 付けると全件を拾ってから並べることになり、上限が効かなくなる。並べ直しは Rust 側の純粋な関数で行う。上限より 1 行多く取るのは、打ち切りが起きたかどうかを見分けるためである。

**打ち切ったことは必ず伝える。** 「上限に達しました。語を絞り込んでください」と出す。黙って切り詰めると、出ていないものを「無い」と読まれる。

### 中止は付けない

`⌘.`（[[0002-接続ごとのアクタースレッドと中止]]）はソース検索には効かない。中止の手綱はタブへの割り当ての表を辿って引くが、背面の接続はその表に載らないためである。**中止のために手綱の指し方を作り変えることはしない。** 上に挙げた 3 つの関所で待ちは有界になっており、パネルを閉じれば利用者は他の作業へ戻れる（返ってきた結果は捨てられる）。この点はスキーマ取得・実行計画・セッション一覧と同じ扱いである。

### 大文字と小文字は既定で区別しない。切り替えられる

Oracle の識別子は大文字で格納されるが、**ソース本文には利用者が書いたままの綴りが入る。** `koduchi.user_traits` と書かれた本文を `USER_TRAITS` で探せないのでは道具にならない。既定は区別しない。

畳むのは**両辺とも Oracle 側**で行う（`upper(s.text) like upper(:needle)`）。片方を Rust の `to_uppercase` で畳むと、Oracle の畳み方とずれる文字で当たるはずのものを取りこぼす。

区別する切り替えも用意する。`SetSegment` のような綴りを狙って探したい場面はあり、その 1 つを足すのに要るのは条件式の分岐 1 本だけである。

### 検索語はバインド変数。`like` の記号は打ち消す

検索語は `:needle` として渡し、**SQL へ直に埋め込まない。** 埋め込むのは種別の綴りとシステムスキーマの名前だけであり、どちらもプログラムが持つ定数である。所有者もバインド変数で渡す。

`%` と `_` と `\` は `like` にとって特別な文字であるため、打ち消したうえで `escape '\'` を添える。打ち消さないと `user_traits` の検索が `userXtraits` にも当たる。

### 結果はオブジェクト単位に束ね、前後は選んだときに読む

行単位に平らに並べると、同じパッケージ本体の 30 行が画面を埋めて他のオブジェクトが見えなくなる。**オブジェクト（所有者・名前・種別）で束ね、その下に当たった行を行番号順に並べる。**

**前後の行は、当たり行を選んだときに読みに行く。** 検索と同時に取らないのは、`ALL_SOURCE` の窓関数（`lag` / `lead`）が `where` の後に効くため、絞ってから前後を取ることができないからである。取るには絞る前の全行に窓関数を掛けることになり、上限が効かなくなる。**全文を読むこともしない。** 数千行のパッケージ本体を丸ごと運ぶと、当たり 1 件を覗くたびに待たされる。読むのは当たった行の前後 5 行、`line between :from_line and :to_line` の 1 本である。

**エディタでその処理を開く導線は、この波では作らない。** テーブル定義ビュー（`adr/README.md` の機能スコープでは今のところ「器だけ」）に DDL タブが付く見込みであり、PL/SQL の全文を出す場所はそちらと揃えるべきである。先取りして別の器を作ると、後で 2 つになる。

### 出す場所はステータスバーの接続メニューから開くオーバーレイ。`⇧⌘F` を割り当てる

[[0017-セッションとロックの確認]] のセッションパネルと同じ器に載せる。「接続中」のメニューへ「ソースを検索…」を足し、設定画面と同じ作りのオーバーレイを開く。

**`⇧⌘F` を割り当てる。** [[0017-セッションとロックの確認]] はキーを割り当てなかったが、あれは詰まったときだけ開く画面である。ソース検索は名前を思いついたその場で叩く道具であり、メニューを 2 段たどらせるのでは足が遅い。`⌘F` / `⌘G` / `⇧⌘G` / `⌥⌘F` はエディタ内の検索が使っているが（`@codemirror/search` の keymap）、`⇧⌘F` は空いている。CodeMirror の keymap は修飾を厳密に見るため `⌘F` の枝と食い合わない。置き場所は `App.tsx` の `keydown` である（CLAUDE.md の「キーバインドの置き場所」）。

### `⌘K` のパレットとは混ぜない。パレットからは「開く」だけ

[[0018-保存済みクエリとコマンドパレット]] のパレットが探すのは**取得済みの 4 種**（コマンド / スキーマ / 保存済みクエリ / 履歴）であり、打鍵のたびに手元で絞る。ソース検索を 5 つ目として足すと、1 文字打つごとに `ALL_SOURCE` へ問い合わせが飛ぶか、飛ばないなら候補が出ない見出しが並ぶかのどちらかになる。**パレットの「打てば即座に絞れる」という性質を壊す。**

代わりに、パレットのコマンドとして「オブジェクトのソースを検索」を出す。キーを覚えていなくても辿り着ける、というパレット本来の役目に収まる。

### 検索は押したときだけ走る

検索欄の打鍵では投げない。`⏎` か「検索」ボタンで走らせる。上と同じ理由である。

## 理由

- **背面の接続で走らせる**のは、ソース検索が小槌で最も重い問い合わせになりうるためである。これを利用者のカーソルと同じ接続で走らせると、「表を探したら結果テーブルが消えた」という取り返しの付かない体験になる。既に 3 つの機能が通っている経路に相乗りすれば、新しい接続も張らずに済む（[[0003-結果セットのカーソル保持と接続プール]]）。
- **上限を Oracle 側で効かせる**のは、行数を持ち帰ってから捨てても遅さは変わらないからである。`rownum` を外側に掛けて `order by` を捨てるという形は、「速さのために並び順をデータベースへ求めない」という 1 つの割り切りであり、その代償（Rust 側で並べ直す）は数百行なら無に等しい。
- **ビューを外す**のは、`LONG` を相手に「速い検索」と「嘘をつかない表示」を両立できないためである。どちらか一方を捨てるくらいなら、対象外だと書くほうが利用者を裏切らない。
- **種別の語彙を分ける**ことで、[[0014-スキーマツリーのオブジェクト種別拡張]] の決定を覆さずに本体を出せる。同じ列挙を広げると、ツリーに `PACKAGE BODY` の束が現れてしまう。
- **前後を選んだときに読む**のは、[[0007-スキーマ取得の段階的ロード]] が段階的ロードで解いたのと同じ問題だからである。「全部欲しい」と「待たされたくない」は、要るときに要るぶんだけ取ることで両立する。
- **パレットと混ぜない**のは、道具の速さがその道具の使われ方を決めるからである。パレットは手が覚えて叩く場所であり、1 度でも待たされるとその信頼が壊れる。

## 却下した案

**`ALL_SOURCE` と `ALL_VIEWS` の両方を探す**: ビューの定義に表名が出るのは事実であり、探せると便利ではある。しかし `LONG` を `like` で絞る手段が無く、`TEXT_VC` は 4000 字で黙って切れる。「検索したが見つからなかった」と「4000 字より先にあった」を利用者が区別できない。

**`DBA_SOURCE` を使う**: 権限のあるものだけに絞られないため取りこぼしが無い。しかし `SELECT ANY DICTIONARY` を要し、普段の接続では通らない。`ALL_SOURCE` が返すのは「その接続で参照できるもの」であり、道具として筋が通っている。

**`order by owner, name, line` を付けて上限を掛ける**: 出力の順序がデータベース側で決まって気持ちがよいが、並べるために全件を拾うことになり、上限を置いた意味が消える。並べ直しは手元で数百行を触るだけである。

**検索と同時に前後の行も取る（`lag` / `lead` の窓関数）**: 1 往復で済むが、窓関数は `where` の後に効くため、絞る前の全行に対して窓を張ることになる。`ALL_SOURCE` 全体のソートであり、上限が効かない。

**当たったオブジェクトの全文を持ち帰る**: 前後を何行でも読めるようになるが、数千行のパッケージ本体を 1 件覗くたびに運ぶことになる。前後 5 行で足りる場面が大半である。

**検索結果から直接エディタのタブへソースを流し込む**: 便利ではあるが、PL/SQL の全文を出す器はテーブル定義ビューの DDL タブと揃えるべきであり、先取りすると器が 2 つになる。

**行単位に平らに並べる**: 実装は単純だが、同じパッケージ本体の 30 行で画面が埋まり、他のオブジェクトが下へ押し出される。「どの処理が触っているか」を知りたいのに、処理の一覧が読めなくなる。

**`⌘K` のパレットに 5 つ目の見出しとして足す**: 入口が 1 つにまとまるが、パレットの絞り込みは打鍵ごとに手元で走る（[[0018-保存済みクエリとコマンドパレット]]）。データベースへの往復を混ぜると、そこだけ遅れて出るか、遅れないなら候補が出ない。器の意味が壊れる。

**サイドバーの新しいセグメントとして出す**: サイドバーは 180〜480px であり（`adr/README.md` の「ペインの大きさ」）、当たった行の本文を出す幅が無い。そのうえサイドバーの検索欄は「打てば絞れる」ものとして 3 セグメントで共有されており（`SidebarSegment`）、押したときだけ走る欄をそこへ混ぜると規則が 1 つ増える。

**結果ペインの動的タブとして出す**: 結果ペインのタブはエディタタブごとの実行結果に紐付いている（[[0009-ウィンドウモデルとタイトルバー]]）。ソース検索はどのエディタタブにも属さないため、タブを切り替えるたびに消えたり現れたりする。[[0017-セッションとロックの確認]] が同じ理由で退けた。

**打鍵のたびに検索する**: 探し先が手元にあるならそれでよいが、`ALL_SOURCE` への往復を打鍵ごとに投げるのは論外である。1 文字打つたびに数秒の問い合わせが積み上がる。

**中止を作る**: 背面の接続を指す手綱を `AppState` に持たせれば作れる。しかし最短 2 文字・種別と所有者の先出し・上限 500 の 3 つで待ちは有界であり、取り返しの付かない操作でもない。中止のためだけに手綱の指し方を作り変える値打ちが無い。必要になったら、同じ経路を使うスキーマ取得と実行計画とまとめて作るのが筋である。

**既定で大文字と小文字を区別する**: 綴りに忠実だが、本文の綴りは書いた人任せである。`user_traits` を `USER_TRAITS` で探せない道具は使われない。

**`Driver` trait に足さず Oracle 専用のコマンドにする**: `DBMS_OUTPUT` や tnsnames.ora と同じ扱いにする案。しかし「本文に文字列を含む処理を探す」は PostgreSQL にも `pg_proc.prosrc` という対応物があり、データベース非依存の概念である。[[0002-接続ごとのアクタースレッドと中止]] の「実装済みの操作だけを載せる」に従い、実装と同時に trait へ足す。

## 結果

- `Driver` trait のメソッドが 2 つ増えた（`search_source` / `source_context`）。PostgreSQL を足すときは `pg_proc.prosrc` を行に割って同じ形を満たすことになる。`ALL_SOURCE` のような行単位の格納ではないため、行番号はこちら側で数えることになる。
- `DbErrorKind::Permission`（[[0017-セッションとロックの確認]]）を 2 つ目の機能が使うことになった。`ORA-00942` / `ORA-01031` を写す処理は `src-tauri/src/db/oracle/errors.rs` へ切り出し、セッションとソース検索の両方から使う。
- zustand のストアは 9 つになる（`connection` / `tab` / `execution` / `history` / `savedQuery` / `schema` / `sessions` / `sourceSearch` / `ui`）。検索条件と結果は接続に属するため、切断時に捨てる。
- キーバインドが 1 つ増えた（`⇧⌘F`）。`⌘I`（Ask AI）の予約は変わらない。
- ステータスバーの接続メニューの項目が 4 つになった（切断 / 切り替え / セッションとロック / ソースを検索）。
- 検索条件（所有者・種別・大小の区別）は**保存しない。** スキーマツリーのフィルタ（[[0014-スキーマツリーのオブジェクト種別拡張]]）と違い、調べもの 1 回ごとに変えるものだからである。パネルを閉じても条件は残り、切断で消える。
- 開発用データベース（`dev/oracle/initdb/006_source_search.sql`）に型の本体と、探し先になるパッケージを足した。統合テストが当てにする目印（`KODUCHI_SOURCE_MARK`）は**本体だけ**に置いてあり、本体が結果に出ることを実機で確かめられる。
- ビューの本文が探せないことは、パネルの初期状態にそのまま書いてある。`ALL_VIEWS` の扱いを覆すなら、本 ADR の「ビューを対象にしない」を覆す形になる。
