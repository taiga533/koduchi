# ADR 0016: バインド変数の型指定

- ステータス: 承認
- 日付: 2026-09-08

## 状況

バインド変数の値はすべて `VARCHAR2` としてバインドしていた（`adr/README.md` の「バインド変数」節）。まずは動くことを取った割り切りであり、同じ節に「型指定が要るようになったら、そのときにダイアログへ型の欄を足す」と書いてある。

割り切りの代償は索引である。`WHERE created_at >= :from` の `created_at` が `DATE` の列であれば、Oracle は**列の側**を文字列へ変換して比べる（`TO_CHAR(created_at) >= :from` と同じ形になる）。列に変換が掛かった時点でその列の索引は使えず、数十万行の表が全件走査になる。数値の列も同じである。実行計画（`⌘E`）を見ると `INDEX RANGE SCAN` が `TABLE ACCESS FULL` へ落ちているのが見える。

加えて、比較そのものが意図とずれる。`'2024-9-1' < '2024-10-1'` は文字列としては真だが、`'2024-9-1' > '2024-11-1'` も文字列としては真である。日付として比べたつもりの範囲指定が静かに誤る。

## 決定

### `Bind` を名前・型・値の 3 つ組にする

`Bind` は `(String, Option<String>)` の別名（`serde` では 2 要素の配列）だった。これを構造体へ変える。

```rust
pub struct Bind {
    pub name: String,
    pub kind: BindKind,          // varchar2 / number / date / timestamp
    pub value: Option<String>,   // None は NULL
}
```

`serde` では `{"name":"id","kind":"number","value":"42"}` になる。`kind` と `value` は省略でき、省いた `kind` は `varchar2` として読む。**値は今までどおり常に文字列で受け渡す。** 型は「その文字列をどう読むか」の指示であって、値の表現そのものは変えない。`NUMBER` を数値の型に載せれば 38 桁の精度が壊れる（`adr/README.md` の「値の受け渡し」節と同じ理由）。

`Driver::execute` / `explain_plan` / `actual_plan` の `binds: &[Bind]` という形は変えていない。

### 型は 4 つに絞る

`VARCHAR2` / `NUMBER` / `DATE` / `TIMESTAMP` の 4 つだけを出す。索引が効かなくなるのはこの 3 種類の列（文字列・数値・日時）と型が食い違うときであり、4 つあれば塞げる。

`TIMESTAMP WITH TIME ZONE` と `INTERVAL` は出さない。時間帯の入力欄が要るうえ、ダイアログは 1 行 1 変数の狭い作りである。`RAW` と `CLOB` も出さない。バインド変数へ貼り付ける値ではない。`NVARCHAR2` は出さない。`VARCHAR2` の列と比べるとかえって変換が挟まる（この理由で既存の実装も `String` を素通しせず `VARCHAR2` を明示していた）。

### 変換は Rust 側で行い、失敗したら実行を始めない

`src-tauri/src/db/oracle/bind.rs` が、選ばれた型に従って文字列を Oracle の値へ直す。

- `NUMBER` は表記を検証したうえで**文字列のまま** `OracleType::Number` へバインドする。前後の空白と先頭の `+` は落とし、`.5` は `0.5` に整える。桁区切りの `,` と全角数字は受け付けない。
- `DATE` と `TIMESTAMP` は `YYYY-MM-DD` / `YYYY/MM/DD` を読み、続けて空白か `T` を挟んで `HH:MI`・`HH:MI:SS`・`HH:MI:SS.ffffff` を書ける。時刻を省けば 0 時 0 分 0 秒になる。暦として成り立たない日（`2023-02-29`）は弾く。`DATE` は小数秒を持てないため落とす。時間帯の表記（`Z` や `+09:00`）は受け付けない。Oracle の `DATE` と `TIMESTAMP` は時間帯を持たないためである。

読めない値は `ORA-` の文言ではなく、**どの変数のどの値をどの型として読めなかったか**を書いたエラーにする。

> バインド変数 :day の値「きのう」を DATE として読み取れません。YYYY-MM-DD または YYYY-MM-DD HH:MI:SS の形式で書いてください。

NULL のチェックは型より優先する。型に関わらず NULL は NULL であり、`Option` の `None` としてバインドする。

文に無い名前を捨てる既存の挙動（`Statement::bind_names()` に載っている名前だけを束ねる）はそのまま残す。**捨てたあとの値だけを変換する。** 使われない変数の値が読めなくても実行を妨げる理由は無い。

### 既定の型は「比べている列」から推し量る

ダイアログを開くとき、変数ごとの既定の型を次の順で決める。

1. その変数に**前回選んだ型**（タブが覚えている）
2. その変数が**比べられている列**の型（取得済みのスキーマから引く。[[0007-スキーマ取得の段階的ロード]] の段階 2）
3. `VARCHAR2`

列を拾うのは `src/sql/statements.ts` の `collectBindOccurrences` である。`collectBindVariables` と同じ走査を使い回し、`列 = :名前` のように比較演算子・`LIKE`・`BETWEEN` の右に置かれた形だけを拾う。`t.col` は最後の部分を列名とする。関数を挟んだ形（`trunc(:d)`）と `IN` の並びは拾わない。型を引くのは `src/sql/bindTypes.ts` で、**同じ名前の列が表ごとに違う型であれば推し量らない**（`CODE` が片方で `NUMBER`、片方で `VARCHAR2` のような場合）。同じ変数が別の型の列と比べられているときも同じである。取り違えて誤った型を既定にするより、これまでどおり `VARCHAR2` に落とすほうが害が小さい。

### 値の見た目にも型が追う。ただし選び直したら追わない

値を打つと、`42` なら `NUMBER`、`2024-01-02` なら `DATE`、`2024-01-02 03:04:05` なら `TIMESTAMP` へ型が変わる。**利用者が型を選び直したあとは変わらない。** 選び直したかどうかは旗を持たずに判定する。今の型が「値の見た目だけで決まる型」と一致していればまだ追っている、違っていれば選び直したあとである、と見る（`applyBindText`）。列から `DATE` が既定に入った変数は、空の値の見た目（`VARCHAR2`）と食い違うため、打鍵で型が上書きされない。

### 前回の型はタブが覚える。履歴とセッションには書かない

`tab` ストアの `BindInput` に `kind` を足す。値と同じ置き場所であり、同じくセッション（[[0005-クエリ履歴とセッション復元のsqlite]]）には保存しない。

**型も履歴とセッションには書かない。** 型だけなら個人情報ではないが、値と切り離して型だけを残しても使い道が無い。値を復元しないのに型だけ復元しても、そのとき打つ値に合っているとは限らない。保存する物を増やすなら、それで何が良くなるかが要る。

### ダイアログの見た目は変えない

型の欄は行の中に収める。1 行は左から「型の選択」「値の入力」「NULL のチェック」であり、行数も枠の大きさも今までどおりである。`⏎` で実行、`esc` で取り消しも変わらない。キーバインドは足さない。

## 理由

- **索引が効かないことは、遅いだけでは済まない。** 業務のデータベースで数十万行の全件走査を撃つと、遅いだけでなく他の利用者の資源まで奪う。クライアントが黙って暗黙変換を起こしているのは、道具として筋が悪い。
- **値を文字列で渡し続ける**のは、`NUMBER` の 38 桁を壊さないためである。型は解釈の指示に留め、表現は変えない。この判断は「値の受け渡し」節の裏返しであり、同じ理由を往復方向で繰り返している。
- **変換を Rust 側で行う**のは、失敗の文言を利用者に届けるためである。文字列のまま Oracle へ渡すと `ORA-01858: 数値を指定する箇所に数値以外が指定されました` のような、どの変数のことか分からない文言だけが返る。
- **推し量りを控えめにする**のは、既定が外れたときに気づけないためである。型は選び直せるが、選び直すには「今おかしい」と気づく必要がある。曖昧な場面で当てにいくより `VARCHAR2` に落としたほうが、外れたときの姿が今までと同じで済む。

## 却下した案

**`Bind` の 2 要素配列に 3 つ目を足して `[name, value, kind]` とする**: 互換は保てるが、位置で意味が決まる配列は 3 つ以上になると読めない。フロントエンドと Rust の両方で `bind[2]` を書くことになる。名前の付いた構造体にした。

**型を選ばせず、値の見た目だけで決める**: 欄が増えないのは利点だが、`0120` のような文字列の値（電話番号・郵便番号・伝票番号）が数値として渡り、先頭の 0 が落ちる。しかも利用者にはその決定が見えない。**見えない推し量りは直せない。**

**列の型を必ず引き当てるために `FROM` 句を解析する**: 表を特定できれば同名の列の食い違いは解ける。しかし別名・副問い合わせ・結合・`WITH` 句まで追うことになり、補完で `schemaCompletionSource` を捨てたとき（[[0013-補完の候補生成と識別子の出力スタイル]]）と同じ道を歩む。既定を良くするためだけに払う額としては高い。当てられない場面は `VARCHAR2` に落とす。

**型を接続やアプリの設定として持つ**: 「日付は必ず `DATE`」のような設定は、1 つの SQL に文字列の列と日付の列が混ざる以上、変数ごとの選択には代われない。

**変換せずに `TO_DATE(:from, 'YYYY-MM-DD')` を SQL へ埋め込む**: 利用者の書いた SQL を書き換えることになる。`⇧⌘E` のヒント注入と違い、これは意味を変える書き換えである。実行計画に出る SQL も利用者の書いたものと変わってしまう。

**型ごとに入力欄を変える（日付ならカレンダー）**: 貼り付けで済ませたい利用者の手を止める。1 行 1 変数の狭い作りにも収まらない。

## 結果

- `Bind` の形が変わったため、`invoke("execute" | "explain_plan" | "actual_plan")` を呼ぶ側は 3 つ組で渡す。`kind` を省けば今までどおり `VARCHAR2` である。
- 変換の失敗は `DbErrorKind::Execute` として届く。実行前に弾くため、失敗した文はデータベースへ届かない。
- 型の選択は接続ごとの設定ファイル（`connections.toml`）には保存しない。タブの記憶に留まり、再起動すれば消える。
- 列から型を引けるのはスキーマの段階 2 が終わってからである（[[0007-スキーマ取得の段階的ロード]]）。読み込みの途中でダイアログを開くと `VARCHAR2` に落ちる。段階 2 を待たせるほどの価値は無い。
- `collectBindOccurrences` は `collectBindVariables` の土台になった。名前の重複除去は前者の結果を畳んで行う。走査を 2 つに分けると、片方だけ直して食い違う。
